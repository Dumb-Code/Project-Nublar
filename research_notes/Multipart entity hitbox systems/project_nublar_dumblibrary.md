## Q1. Which classes implement multipart hitboxes, and is there a reusable API in DumbLibrary?

### Takeaway
The multipart system lives in **ProjectNublar**, not in DumbLibrary. It has four parts. `EntityPart` is a real, spawned, saved and tracked `Entity`, one per model cube. `MultipartEntityComponent` is an ECS component that holds (cube name, part UUID) links. `DinosaurMultipartStorage` is a per-age list of cube names. `MultipartSystem` is an ECS system that moves and resizes the parts from animated model cubes. DumbLibrary supplies only the building blocks: the ECS, the server-side model cube tree, the cube-to-model-space transform and animation sync. It has no generic multipart or part-entity API.

### Inferences
- The design is "one real Entity per model cube, glued to the parent through an ECS component". It is the opposite of vanilla's `EntityDragon`/`MultiPartEntityPart` pattern, where parts are unspawned and live in the parent's array. Every part is a full world entity: it is ticked, tracked, saved to the chunk and found by UUID.
- Anyone who wants a "DumbLibrary multipart API" must lift it from ProjectNublar. There is no library-level abstraction to depend on.

### Gaps

## Q2. Were hitboxes driven by the animation system, with cube/bone transforms computed server-side? How?

### Takeaway
Yes. Each part's box is the **axis-aligned envelope of one animated model cube**. The server computes it from its own copy of the model hierarchy, posed by DumbLibrary's animation system. The client runs the same maths on its render-model cubes. In 1.12, the server re-poses the whole model every 3 ticks with `layer.animate(1)`. In 1.16, the server re-poses every 5 game ticks with a 0.25 s step, and the parts are re-laid every 3 ticks.

### Cited Findings
- **Server-side model (1.12)**. `AnimationComponent.getAnimationLayer(e)`: on the client, it builds the `AnimationLayer` over the client `TabulaModel` cubes. On the server, it loads the `.tbl` zip through `TabulaUtils.getServersideCubes(modelLocation)` and builds the layer over `ServerAnimatableCube`s. — [DL master ecs/component/impl/AnimationComponent.java#L144-L160](https://github.com/Dumb-Code/DumbLibrary/blob/791ada6afea65e284e4f9e534dd64b15a1815afe/src/main/java/net/dumbcode/dumblibrary/server/ecs/component/impl/AnimationComponent.java#L144-L160)
- `ServerAnimatableCube` is a minimal pose holder. It keeps the parent link, the default and actual rotation point, the default and actual rotation, and the offset and dimension from the Tabula cube. `reset()` restores the defaults. — [DL master server/info/ServerAnimatableCube.java#L9-L92](https://github.com/Dumb-Code/DumbLibrary/blob/791ada6afea65e284e4f9e534dd64b15a1815afe/src/main/java/net/dumbcode/dumblibrary/server/info/ServerAnimatableCube.java#L9-L92). `parseCube` builds the parent/child tree recursively. — [TabulaUtils.java#L49-L64](https://github.com/Dumb-Code/DumbLibrary/blob/791ada6afea65e284e4f9e534dd64b15a1815afe/src/main/java/net/dumbcode/dumblibrary/server/animation/TabulaUtils.java#L49-L64)
- **Server pose step (1.12)**. In `MultipartSystem.updatePart`:
  1. It returns early unless `entity.ticksExisted % 3 == 0`.
  2. On the server only, it `reset()`s every cube and calls `layer.animate(1)` (lines 53-72).
  3. The client does not animate here. Its layer is animated in the render pre-callback, which resets the cubes and calls `animate(partialTicks)`. — [MultipartSystem.java#L52-L72](https://github.com/Dumb-Code/ProjectNublar/blob/e525ed7b69aaaa9de5234de9875f50d3822a25af/src/main/java/net/dumbcode/projectnublar/server/entity/system/impl/MultipartSystem.java#L52-L72); [DL master AnimationComponent.java#L162-L174](https://github.com/Dumb-Code/DumbLibrary/blob/791ada6afea65e284e4f9e534dd64b15a1815afe/src/main/java/net/dumbcode/dumblibrary/server/ecs/component/impl/AnimationComponent.java#L162-L174)
- Animation time is delta-based on a global tick counter (`TickHandler.getTicks()`, AnimationWrap lines 105-124). So a server that calls `animate` only every 3 ticks still advances the correct amount. — [DL master animation/objects/AnimationWrap.java#L100-L125](https://github.com/Dumb-Code/DumbLibrary/blob/791ada6afea65e284e4f9e534dd64b15a1815afe/src/main/java/net/dumbcode/dumblibrary/server/animation/objects/AnimationWrap.java#L100-L125). An April 2020 commit changed the server call from `layer.animate(entity.ticksExisted)` to `layer.animate(1)`. — [commit b6ef7910 "Fixed lots of animationbugs"](https://github.com/Dumb-Code/ProjectNublar/commit/b6ef7910)
- **Cube → hitbox maths (1.12)**. For each `LinkedEntity`:
  1. Take the 8 corners of the cube with `TabulaUtils.getModelPosAlpha(cube, x∈{0,1}, y∈{0,1}, z∈{0,1})`. This walks the parent chain and applies rotX, rotY(−), rotZ(−) and the rotation-point translation (/16) at each level. — [TabulaUtils.java#L118-L155](https://github.com/Dumb-Code/DumbLibrary/blob/791ada6afea65e284e4f9e534dd64b15a1815afe/src/main/java/net/dumbcode/dumblibrary/server/animation/TabulaUtils.java#L118-L155)
  2. Add 1.5 blocks to y (the 24-px model origin).
  3. Multiply by the `RENDER_ADJUSTMENTS` scale (T. rex 2.5, raptor 0.75).
  4. Rotate by `-rotationYaw` about Y.
  5. Take the min/max envelope and add 0.1 padding. This is synced as the part size.
  6. The position is the midpoint of corner 0 and corner 7, plus the entity position, minus half the height (the AABB grows upward from y).
  — [MultipartSystem.java#L74-L133](https://github.com/Dumb-Code/ProjectNublar/blob/e525ed7b69aaaa9de5234de9875f50d3822a25af/src/main/java/net/dumbcode/projectnublar/server/entity/system/impl/MultipartSystem.java#L74-L133)

### Inferences
- Hitboxes follow the animated pose on both sides with no per-tick server-to-client transfer of the pose. Each side derives the boxes from the same synced animation entries. This works only because DumbLibrary can load and pose the model on a dedicated server (Tabula `.tbl` in 1.12, `.dcm` via Studio in 1.16).
- Each box is an AABB that encloses a rotated cube. For long diagonal cubes (a raised neck, an angled tail segment) the box is much larger than the visible geometry. The design trades accuracy for vanilla-compatible AABB hit-testing.
- Yaw uses `rotationYaw` (1.12) / `yRot` (1.16), not the body-render yaw (`renderYawOffset`/`yBodyRot`). Where the two differ, the hitbox layout may lead or lag the rendered body. This is an inference from the code. I found no issue that confirms it.
- The 1.16 server poses at 4 Hz (every 5 ticks), but the parts move every 3 ticks. So the server's boxes step in coarse increments relative to the client's per-frame pose.

### Gaps
- I did not inspect the DumbCode Studio library (`net.dumbcode.studio`, `CubeUtils.getWorldPosition`, `ModelAnimationHandler`). It is an external dependency, so the exact 1.16 transform order is unverified.
- No design document or comment states why per-cube boxes were chosen over a few hand-tuned boxes.

## Q3. How were parts networked, and how did they interact with collision, damage, pathfinding, rendering and performance?

### Takeaway
Parts are vanilla-tracked entities. Spawn data carries the parent UUID and the part name, and the size is a synced `DataParameter`. Both sides run the layout locally, and the vanilla 20-tick position packets act as a coarse correction. Damage forwards the same source and amount to the parent. Parts can be hit (`canBeCollidedWith`) and push other entities (1.12). Parts have no block collision and play no role in pathfinding: the dinosaur's own box stays the default 0.6×1.8. Rendering is a debug-only AABB. Performance is weak: loaded-entity-list scans per part, 15–17 full entities per dinosaur, and a full server re-pose every few ticks.

### Inferences
- **Block collision**. Parts pass through blocks (heads and tails clip into walls). All block collision depends on the dinosaur's own small default box.
- **Pathfinding**. Pathfinding treats a T. rex like a player-sized mob. It can plan routes through 1-wide gaps that the visible body and its part boxes overlap. The parts do not block movement either.
- **Damage**. Because the source and amount are passed through unchanged, the parent's invulnerability frames prevent double hits when several parts are struck. There is no headshot or weak-point multiplier.
- **Interaction**. The crosshair ray picks the part, and the part does not forward right-click interactions. So item or tablet interactions aimed at a body part most likely do nothing. This needs in-game confirmation.
- **Client positioning**. With a 20-tick tracker interval and both sides computing the same layout, the client's own computation produces almost all visible part motion. Server packets act as a drift correction. This would explain the commit title "Vastly improved multipart system syncing" (c156b05b).
- **Cost**. Per adult dinosaur, the cost is 15–17 extra entities. Each part is ticked, tracked to clients within 128 blocks, saved to region files and given a spawn packet. In 1.12, each part also runs an AABB entity query every tick. A herd of 10 raptors adds about 150 entities.
- **UUID swap bug (1.12)**. The bug was probably masked: the client also adds correct links from `EntityJoinWorldEvent` and `EntityPart.onUpdate`, so the bad entries in the `HashSet` never match a part and are only wasted iterations.

### Gaps
- I found no profiling data, benchmarks or performance discussion in commits.
- I did not confirm in a running game whether parts visibly jitter on clients. Assets and build were out of scope.

## Q4. Do issues or commits explain why it was built this way, or what went wrong?

### Takeaway

Wyn Price built the system in a burst on 15–19 Feb 2019: entity handling, then cube-centre positioning, then the 8-corner envelope, syncing and rendering/collision. ## Q5. What did the current 1.20.1 code (`DinosaurPart`/`PartEntity`, T. rex head part) inherit?

### Takeaway
Effectively nothing structural. The current `PartEntity` is a near-copy of **Ice and Fire's `EntityMutlipartPart`**: fixed radius, yaw and Y offset, a damage multiplier, and synced `PARENT_UUID`/`SCALE_WIDTH`/`SCALE_HEIGHT`/`PART_YAW`. It is not derived from DumbCode's ECS `EntityPart`, and it has no `MultipartEntityComponent`, `MultipartSystem` or animation-cube envelope. The only conceptual overlap is "position a part from a model bone" (the T. rex head) and "forward damage to the parent". The current head-bone path is set client-side.

### Cited Findings
- The current `common/.../entity/dinosaur/PartEntity.java` (worktree `herd-leader-sample`, HEAD `4244f62`) matches IaF field for field and method for method:
  - Shared fields and synced keys: `PARENT_UUID` (OPTIONAL_UUID), `SCALE_WIDTH`, `SCALE_HEIGHT`, `PART_YAW`, `radius`, `angleYaw = (angleYaw + 90) * π/180`, `offsetY` and `damageMultiplier`.
  - Shared methods: `collideWithNearbyEntities` (pushes non-part entities into the parent), `sharesRider`, `isSlowFollow`, `limitAngle` and `shouldContinuePersisting`.
  - Matching code: [IaF EntityMutlipartPart.java lines 33-41, 63-73, 172-177, 232-236](https://github.com/AlexModGuy/Ice_and_Fire/blob/0526aad94119b705a86207623481b087c4d052ca/src/main/java/com/github/alexthe666/iceandfire/entity/EntityMutlipartPart.java). I compared against a local IaF clone of branch `1.20` @ `0526aad9`.
  - Current file: `common/src/main/java/net/dumbcode/projectnublar/entity/dinosaur/PartEntity.java` lines 25-247 (local file in this repo).

### Inferences
- Vanilla `SynchedEntityData` is server-authoritative: a value set on the client is not sent to the server. So on the server, `getHeadBonePos()` probably returns its default `(0,0,0)`, or a stale value, and the server-side head part would sit near the world origin rather than at the T. rex's head. Even on the client, the pivot-in-pixels-without-rotation maths would misplace it. This needs in-game verification, for example with F3+B.
- The original DumbCode approach (server-side posed model, 8-corner envelope per cube, yaw rotation, render-scale multiply) is a working reference for the missing pieces in the current head-bone path. GeckoLib has no server-side bone pose by default, so porting the idea would need an equivalent server-side bone evaluator. The 1.12/1.16 code obtained that from DumbLibrary's server cube loading.
