# Mowzie's Mobs (1.20 branch): multipart entities, hitboxes and animation-driven hit regions

Source snapshot: shallow clone of `BobMowzie/MowziesMobs-Public`, branch `1.20`, HEAD commit `64d15248c4421fdf8555165134b306e8cfc0a6c6` (committed 2026-04-22). The clone was only read; nothing was built or run. All line ranges below refer to that commit. Abbreviation used in links: `MM/` = `src/main/java/com/bobmowzie/mowziesmobs/`.

Two animation stacks live in this codebase:
- **Older mobs** (Ferrous Wroughtnaut, Frostmaw, Naga, Grottol, Foliaath) use a vendored copy of LLibrary's tick-based animation system (`com.ilexiconn.llibrary`), with Java-coded models (`AdvancedModelRenderer`).
- **Newer mobs** (Sculptor, Umvuthi, Umvuthana, Elokosa) use GeckoLib 4 (`build.gradle` line 110 pulls `curse.maven:geckolib-388172:7553267`), driven by the mod's own "Ability" system.

Neither stack has a server-side model.

## Q1. Does it use part entities (Forge `PartEntity` / `EnderDragonPart` pattern) for any mob?

### Takeaway
No. None of the mobs (Wroughtnaut, Frostmaw, Naga, Sculptor, Umvuthi, Grottol and the rest) is multipart. Each one is a single vanilla `LivingEntity` with one AABB set in `EntityType.Builder.sized(...)`. The only `PartEntity` reference in the codebase is defensive: when the Wrought Axe's attack hits another mod's part entity, the code redirects to the parent.

### Cited Findings
- A text search of the whole 1.20 source tree for `PartEntity`, `EnderDragonPart`, `isMultipartEntity` and `getParts()` matched only one file, `EntityAxeAttack.java`. ### Inferences
- Body-region effects are coded as rules inside `hurt()` on the single box, not as separate hitboxes. Wroughtnaut has a front-armour arc (see Q3) and Grottol takes damage only from pickaxes. "Where on the body you hit" is approximated by attacker bearing relative to `yBodyRot`, never by which part was struck.
- For a large mob like Frostmaw (4x4 box), players can hit only that box. Model parts that extend past it (Frostmaw's arms, Naga's wings and tail) are visual only.

- No developer post was found that explains why part entities were not used. ## Q2 (KEY). Does it evaluate animation bone positions on the server (server-side model, bone tracking, socket bones)?

### Takeaway
No. Socket bones exist, but only the **client renderer** computes their world positions. The renderer writes them into client-only `Vec3[]` arrays on the entity, and those arrays are used only for client particles and visual effects. The server never runs the model. It derives gameplay positions (breath origin, projectile spawn point, melee area) from hard-coded offsets rotated by `getYRot()`/`yHeadRot`/`getXRot()`. Animation state is kept in step by sending only the animation (or ability) index plus a tick counter that runs on both sides. Bone transforms are never replicated.

### Inferences
- The design is "server runs a timeline of integer ticks; client renders the matching keyframes". Hit frames are hard-coded tick numbers (e.g. Wroughtnaut tick 27, Frostmaw tick 9/21), tuned by hand to line up with the animation. Nothing checks that they match, so an edit to the animation file can silently desync visuals from damage.
- Socket positions depend on render-time `entityYaw` and partial ticks, and on the entity being rendered at all. They are stale or absent off-screen, on dedicated servers, and while a model-replacement mod is active. That limits them to cosmetic use. (The Umvuthi/Umvuthana `shouldRender` fallback shows the author handling the off-screen case.)
- GeckoLib 4 `GeoBone` matrices are recorded only for bones with tracking turned on. In this codebase only `GeckoDynamicChain` calls `setTrackingMatrices(true)` explicitly. I could not confirm in the mod source how `sunRender`/`superNovaCenter`/`head` get tracking turned on. One possibility is that GeckoLib's world-space getter turns it on lazily on first access, which would leave the first frame's value stale. This is unverified.

### Gaps
- I did not inspect the GeckoLib library source to confirm when `getWorldPosition()` turns tracking on.
- No issue or developer comment discusses server-side bone evaluation.

## Q3. How are melee and attack hitboxes done (body-yaw sweeps vs bone positions)?

### Takeaway
All melee is **instant area queries at a fixed animation tick**: an AABB inflated around the entity's main box, filtered by horizontal distance and by an **angular arc relative to `yBodyRot`**. No attack sweeps along a bone or limb path, and nothing is interpolated between ticks. The "defensive hitbox" logic (Wroughtnaut armour, Grottol, Naga interrupt) is also bearing- or state-based inside `hurt()`.

### Cited Findings

### Inferences
- In `AnimationAreaAttackAI` L58 and the Wroughtnaut equivalents, the condition reads `dist <= range && (inArc) || (wrapArc)`. By Java operator precedence, the wrap-around branch skips the distance check. The preceding `getEntitiesNearby` filter (`distanceTo <= r + width/2`) still bounds range roughly, so the practical effect is small. It is a sign that the arc code is copy-pasted, not a shared tested utility.
- Because the hit test centres on the entity's position and body yaw, the visible claw or axe can miss or overlap targets when the model's reach differs from `range`. The design accepts this in exchange for simplicity and server authority.

### Gaps
- I did not trace every ability (e.g. Sculptor's boulder and pillar attacks, Umvuthi's solar beam ray) in detail. These use separate effect entities with their own box or ray logic, which is outside the "body hitbox" question.

## Q4. How do large mobs path and collide with blocks? Main bounding box vs model?

### Takeaway
Block collision and entity collision use only the single vanilla AABB. For width, Wroughtnaut, Frostmaw and Grottol use a custom `MMPathNavigateGround`: a voxel-AABB sweep for path shortcutting, and a `PatchedPath` that centres node targets for wide boxes. The custom node evaluator is a stub; all its overrides are commented out. Visual adaptation to terrain is client-only (leg solver). Naga uses its own flight move helper with box-swept `noCollision` checks.

### Cited Findings
- `MMPathNavigateGround` overrides `createPathFinder` to use `MMWalkNodeProcessor` + `MMPathFinder`, and overrides `followThePath`. `followThePath` builds the mob's AABB (`getBbWidth`, `getBbHeight`) and tries to shortcut to the furthest same-Y node with `sweep(vec, base, max)`. `sweep` is an AABB-through-voxel sweep "based off of andyhall/voxel-aabb-sweep" that rejects non-pathfindable blocks and water, lava or open floor below. Node advancement uses `isAt(path, 0.5)` or a width-scaled threshold at elevation changes — [MMPathNavigateGround.java L17-L140](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/ai/MMPathNavigateGround.java#L17-L140)
- `MMPathFinder.PatchedPath.getEntityPosAtNode` centres the target at `node + floor(bbWidth + 1) * 0.5` on X and Z (vanilla uses +0.5). Wide mobs therefore aim at the centre of their footprint, not a block corner — [MMPathFinder.java L19-L43](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/ai/MMPathFinder.java#L19-L43)
- `MMWalkNodeProcessor extends WalkNodeEvaluator`. Its whole body (custom start node, 8-way neighbours, step-height logic) sits under `// TODO: Put this back on` inside a block comment, so at runtime it is vanilla — [MMWalkNodeProcessor.java](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/ai/MMWalkNodeProcessor.java)
- Users of `MMPathNavigateGround`: `EntityFrostmaw`, `EntityGrottol`, `EntityWroughtnaut` (text search of `server/entity`). Frostmaw also sets `setMaxUpStep(1)` and a custom `MMEntityMoveHelper(this, 7)` — [EntityFrostmaw.java L116-L127](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/entity/frostmaw/EntityFrostmaw.java#L116-L127)
- Naga flight-target validation moves its bounding box to the candidate (`getBoundingBox().move(offset)`). It accepts the point only if `level().noCollision(newBB)` and a block-collider `clip` from current to target is clear — [EntityNaga.java L1015-L1027](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/entity/naga/EntityNaga.java#L1015-L1027)
- Entity-entity pushing is coded by hand where needed: `repelEntities(x, y, z, radius)` sets nearby pickable entities' velocity away from the mob — [MowzieEntity.java L516-L524](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/entity/MowzieEntity.java#L516-L524)
- Known issue: Ferrous Wroughtnaut is "heavily slowed" by flowing water near it (reported on 1.20.1 Forge 47.4.10 / MM 1.7.3, also on 1.21.1) — [Issue #19](https://github.com/BobMowzie/MowziesMobs-Public/issues/19). ### Inferences
- Issue #19 fits a single large AABB: a 2.5-wide box overlaps more fluid blocks, so vanilla fluid push and drag act on the whole box. This is my reading, not confirmed by the developer.

### Gaps

## Q5. Networking, rendering interaction, performance and known issues

### Takeaway
Network cost is very small: one packet of two to three VarInts per animation or ability change, plus vanilla entity tracking at update interval 1. No bone or hitbox data is ever sent. Per-frame cost on the client comes from building `PoseStack`s for a few sockets (LLibrary), recording tracked bone matrices (GeckoLib), and dynamic-chain physics. The server pays only for AABB queries on hit ticks. The tracker shows renderer-side fragility with model-altering mods, but no hitbox bugs.

### Inferences
- Issue #3 (crash during a Frostmaw attack with a model-replacement mod) is consistent with the attack-time socket lookup walking the mod's own model parts, which EMF may replace. I did not read the crash log. EMF fixed it on its side.
- The architecture scales well (no extra entities, no server model). The cost is fidelity: damage areas are cylinders or arcs around the main box, tuned by tick number and range constants.
- Lessons for a dinosaur mod: (1) keep server gameplay on body-yaw-relative offsets and tick-indexed hit frames; (2) use client socket bones only for particles and effects, with a fallback when culled; (3) widen the culling AABB for long-bodied models; (4) use a width-aware path follower (`PatchedPath` centring plus an AABB sweep) for wide mobs.

- I did not review the 1.21 branch to see whether later versions add multipart or server-side bones.
- A web search for developer commentary on Mowzie's hitbox design found nothing relevant; the results were release notes and third-party hitbox libraries ([CustomHitboxLib](https://www.curseforge.com/minecraft/mc-mods/customhitboxlib), [DoxHitbox](https://www.curseforge.com/minecraft/mc-mods/doxhitbox)), which Mowzie's Mobs does not use.
