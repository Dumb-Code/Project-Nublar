## Q1. How does vanilla 1.20.1 implement the Ender Dragon's multipart hitboxes (EnderDragon / EnderDragonPart)?

### Takeaway
The dragon is one real, tracked, saved entity (`noPhysics`, not pickable). It owns 8 `EnderDragonPart` objects that are plain `Entity` subclasses. These parts are never added to the world. Each side (server and client) computes their positions on its own every tick in `aiStep`, from the dragon's position, yaw and a 64-entry yaw/Y history ring buffer (`getLatencyPos`). Parts only find their way into hit detection through special-case code in `Level.getEntities` and a server-side `dragonParts` ID map. Damage on any part goes to `EnderDragon.hurt(part, …)`: hits on the head take full damage and hits on other parts are reduced. Parts never collide with blocks. Instead, the dragon destroys blocks that intersect the head, neck and body boxes (`checkWalls`), and it shoves or damages entities near the wing, head and neck boxes. Client part IDs are assigned off by one compared with the server, which is a long-standing vanilla bug (MC-158205, fixed in 24w44a, i.e. after 1.20.1).

### Cited Findings

**Part class (`EnderDragonPart`)**
- `EnderDragonPart extends Entity`, not `LivingEntity`. It holds `parentMob` (the dragon), a `name` string and a fixed `EntityDimensions.scalable(w, h)` size. Its constructor calls `super(dragon.getType(), dragon.level())`, so it reports the dragon's EntityType. — [V EnderDragonPart.java L14-25](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/EnderDragonPart.java#L14-L25)
- `defineSynchedData`, `readAdditionalSaveData` and `addAdditionalSaveData` are all empty. `shouldBeSaved()` returns false. `getAddEntityPacket()` throws `UnsupportedOperationException`, so a part can never be sent as its own entity. — [V EnderDragonPart.java L27-34, L53-63](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/EnderDragonPart.java#L27-L63)
- `isPickable()` returns true and `getPickResult()` returns the parent's result. `hurt(src, amt)` returns false if the part is invulnerable to the source, otherwise it calls `parentMob.hurt(this, src, amt)`. `is(entity)` is true for the part itself or for the parent, so a part never targets or damages its own dragon. — [V EnderDragonPart.java L36-51](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/EnderDragonPart.java#L36-L51)

**Which parts exist and their sizes** (width × height, in blocks)
- head 1×1, neck 3×3, body 5×3, tail1/tail2/tail3 2×2 each, wing1/wing2 4×2 each. These form `subEntities = {head, neck, body, tail1, tail2, tail3, wing1, wing2}`. The dragon constructor also sets `noPhysics = true` and `noCulling = true`. — [V EnderDragon.java L90-105](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L90-L105)
- The dragon overrides `isPickable()` to return false, so the crosshair and projectiles can only hit the parts, never the dragon's own AABB. — [V EnderDragon.java L753-755](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L753-L755)

**Movement history ring buffer (`positions` / `posPointer` / `getLatencyPos`)**
- `positions` is a `double[64][3]` array and `posPointer` starts at -1. — [V EnderDragon.java L62-63](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L62-L63)
- In `aiStep`, only when the dragon is not `isNoAi()`: on the first use every slot is filled with the current yaw and Y. After that the pointer advances (wrapping at 64) and stores the current `getYRot()` and `getY()`. This runs on both sides, because it comes before the `isClientSide` branch. — [V EnderDragon.java L200-216](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L200-L216)
- `getLatencyPos(i, partialTick)` reads the sample `i` ticks ago and the one before it, using `& 63` wrap-around. It returns the interpolated yaw (wrapped), Y, and the unused third component. When the dragon is dead or dying the partial tick is forced to 0. — [V EnderDragon.java L141-158](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L141-L158)
- On the client, the renderer reads the same buffer (`getLatencyPos(7,…)`, `(5)-(10)` for pitch, and `getHeadPartYOffset` per neck segment) to pose the model. As a result, the hitboxes and the visual model are both driven by the same history and stay roughly in step. — [V EnderDragonRenderer.java L45-46, L262-285](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/client/renderer/entity/EnderDragonRenderer.java#L45-L46)

**How and when part positions are set each tick (in `aiStep`, still inside the not-NoAI branch)**
- `yBodyRot` is set to `getYRot()`. Then the current position of every part is saved into a temporary `Vec3[]`. — [V EnderDragon.java L277-283](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L277-L283)
- A body pitch term is computed as `(latencyY(5) − latencyY(10)) × 10°`, giving `f10 = cos` and `f11 = sin`. Yaw sine and cosine come from `getYRot()`. — [V EnderDragon.java L285-290](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L285-L290)
- `tickPart(part, dx, dy, dz)` just calls `part.setPos(dragon.x + dx, dragon.y + dy, dragon.z + dz)`. There is no part rotation; each part is an axis-aligned box whose centre is placed by trigonometry. — [V EnderDragon.java L351-353](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L351-L353)
- Body: 0.5 block forward from the yaw. Wings: ±4.5 blocks sideways (perpendicular to the yaw) and 2 blocks up. — [V EnderDragon.java L291-293](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L291-L293)
- Head and neck: these use the yaw minus `yRotA × 0.01` (a turn-lag term). The head sits 6.5 blocks out and the neck 5.5 blocks out, scaled by pitch `f10`. Their Y is `getHeadYOffset()` plus the pitch term times the same distance. `getHeadYOffset()` returns -1 while the dragon is sitting, and otherwise uses the latency difference between samples 5 and 0. — [V EnderDragon.java L300-305, L355-360](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L300-L305)
- Tail: for k = 0..2, the yaw is `getYRot() + wrap(latencyYaw(12 + 2k) − latencyYaw(5))` and the distance is `(k + 1) × 2`. The segment is placed behind the body. Its Y is the latency Y difference minus a pitch term, plus 1.5. Each tail segment therefore follows where the dragon was pointing 12, 14 and 16 ticks earlier, which gives a trailing tail. — [V EnderDragon.java L306-329](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L306-L329)
- After placement, each part's `xo/yo/zo` and `xOld/yOld/zOld` are set to the saved pre-move positions. This makes render interpolation and the hitbox debug draw between the old and new positions work for the parts, even though the parts are never ticked themselves. — [V EnderDragon.java L338-344](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L338-L344)
- On the client, the same `aiStep` first lerps the dragon toward the server-sent position and rotation (`lerpSteps`) and then places the parts locally. No part position is ever sent over the network. — [V EnderDragon.java L217-229](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L217-L229)

**Entity-to-entity effects (server only, when `hurtTime == 0`)**
- `knockBack`: living entities inside each wing box (inflated 4, 2, 4 and moved down 2) are pushed away from the body centre with horizontal strength 4 and vertical 0.2. If the dragon is not sitting, they also take 5 `mobAttack` damage. — [V EnderDragon.java L294-296, L392-409](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L392-L409)
- `hurt(List)`: living entities inside the head or neck box (inflated by 1) take 10 `mobAttack` damage. — [V EnderDragon.java L297-298, L411-418](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L411-L418)

**Blocks: no collision, only destruction**
- The dragon has `noPhysics = true` and the parts do no movement or collision of their own. On the server, `inWall` is the OR of `checkWalls(head box)`, `checkWalls(neck box)` and `checkWalls(body box)`. — [V EnderDragon.java L331-332](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L331-L332)
- `checkWalls(aabb)` loops over every block position in the box and skips air and `#dragon_transparent`. If `mobGriefing` is on and the block is not in `#dragon_immune`, the block is removed. Otherwise the method reports being blocked, and the caller then slows the dragon's flapping (`inWall` reduces `flapTime` gain). — [V EnderDragon.java L425-457](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L425-L457), [V EnderDragon.java L192-198](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L192-L198)

**Damage routing**
- `EnderDragon.hurt(part, src, amt)`: does nothing while the dragon is in the DYING phase. The current phase's `onHurt` modifies the amount first. **If the part is not the head, damage becomes `amt/4 + min(amt, 1)`**, so the head takes full damage. Damage under 0.01 is ignored. Health is reduced (via `reallyHurt` → `LivingEntity.hurt`) only if the source entity is a Player or the source has the `#always_hurts_ender_dragons` tag. There is also bookkeeping for leaving the sitting phase (more than 25% of max health taken while sitting) and for entering DYING. — [V EnderDragon.java L459-491](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L459-L491)
- A plain `EnderDragon.hurt(src, amt)` (for example from area damage that hits the dragon's own box) is routed as `hurt(body, …)` on the server and returns false on the client. — [V EnderDragon.java L493-499](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L493-L499)
- End-crystal destruction calls `hurt(head, explosion, 10)`. — [V EnderDragon.java L831](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L831)

**Entity IDs and how parts reach the client**
- Every `Entity` takes its ID in a field initialiser, `id = ENTITY_COUNTER.incrementAndGet()` (a static AtomicInteger), and `setId` overwrites it. Because the dragon constructs its parts inside its own constructor, on the server the dragon gets ID N and the parts get roughly N+1 … N+8, in array order. — [V Entity.java L127, L145, L302-304](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/Entity.java#L127)

On the client, `Entity.recreateFromPacket` applies the packet's ID and position. `EnderDragon.recreateFromPacket` then sets `part[i].setId(i + packetId)`, so **the client head gets the dragon's own ID N and every part is one lower than on the server**. — [V EnderDragon.java L866-873](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L866-L873), [V Entity.java L3177-3185](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/Entity.java#L3177-L3185), [V ServerEntity.java L230](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/server/level/ServerEntity.java#L230)
- Mojira MC-274526 ("EnderDragonPart Entity ID Desync", reported on 1.21) describes exactly this off-by-one in `recreateFromPacket`. It was closed as a duplicate of MC-158205. — [mojira.dev MC-274526](https://mojira.dev/MC-274526)

Two causes are given: (1) the part-ID desync (one comment says the wing IDs were effectively swapped, so the server judged a hit on one wing as a hit on the far wing, out of reach), and (2) chunk-section-based hit detection missing large entities whose centre is in a section the ray does not cover (MC-261638). — [mojira.dev MC-158205](https://mojira.dev/MC-158205)

### Inferences
- Server and client keep their own `positions` buffers, fed by different inputs: the server uses its authoritative motion, and the client uses lerped positions with a 3-tick interpolation lag. Part boxes can therefore differ slightly between the two sides, especially for the tail, which reads samples 12-16 ticks old. Vanilla accepts this because the client picks locally and the server only resolves the ID and checks reach.
- The design has four building blocks: a fixed set of parts created in the parent's constructor; a shared deterministic placement function run on both sides; IDs assigned in a fixed order relative to the parent ID; and level hooks so queries can find parts. This is the template Forge generalised, and the one Alex's Mobs (cachalot), Untamed Wilds and MoreHitboxes copy.
- For a large-dinosaur mod: the dragon pattern gives hit precision at no network cost. It gives nothing for terrain collision or pathfinding, and the body's main AABB still governs movement and collision.

### Gaps
- The exact 24w44a code change for MC-158205 (whether `recreateFromPacket` was changed to `i + id + 1` or IDs were otherwise reworked) was not verified from source. This is out of scope since the fix is post-1.20.1.
- `ENTITY_COUNTER` contiguity is assumed: in normal operation entity construction happens on the server thread, but any concurrent construction could interleave IDs. No public source discusses this.

## Q2. What does Forge 1.20.1 (and NeoForge) add: `PartEntity`, `isMultipartEntity`, `getParts`, and how parts are synced, hit-detected, collided and tracked?

### Takeaway
Forge removes vanilla's hard-coded `instanceof EnderDragon` checks and replaces them with `isMultipartEntity()` / `getParts()` plus an abstract `PartEntity<T>`. It keeps a per-level map of all parts (server `dragonParts`, client `partEntities`) so `Level.getEntities` can find parts even when the parent's chunk section is outside the query. It skips parts in the chunk tracker and the tick loop. Forge does **not** sync part IDs, positions or state, does not save parts, and gives them no block collision. The mod owns placement and ID alignment. NeoForge 1.21.1 keeps the same API under `net.neoforged.neoforge.entity.PartEntity`.

### Inferences
- A Forge `PartEntity` gets a fresh `ENTITY_COUNTER` ID on each side. Unless the mod aligns IDs (as vanilla tries for the dragon, and MoreHitboxes does with `id + i + 1`), a client melee hit sends a part ID that the server's `dragonParts` map does not have, or that belongs to a different entity's part. That explains why Alex's Mobs sends its own C2S damage packet (Q4).
- The Forge `Level.getEntities` part loop is O(total parts in level) for every AABB query. With many multipart mobs loaded (for example herds of sauropods) this adds cost to every entity query, including AI sensors, pushing and projectiles.
- Because `onTrackingStart` registers parts by their ID at that moment, any later `setId` on parts (as in MoreHitboxes' mixin, or vanilla's `recreateFromPacket`) must happen before tracking starts, or the map key becomes stale.
- No part block collision: like vanilla, Forge adds nothing. Mods must implement terrain interaction themselves (vanilla dragon `checkWalls`; Alex's Mobs anaconda height probing).

### Gaps
- Forge's `Entity.java.patch` was not inspected for any additional part hooks (for example `canUpdate` or capabilities). The specific multipart hooks were found in the files listed.
- I did not verify whether NeoForge later releases (1.21.2+) changed part registration in `ServerLevel` or `ClientLevel`. Only `PartEntity` and `IEntityExtension` were read on 1.21.1.

## Q3. Fossils & Archeology Revival (1.20.1): do its dinosaurs use parts, and how does its system (MoreHitboxes) work?

### Takeaway
Yes. The official TeamFossilsArcheology repo is public, and its 1.20.1 branch (Architectury, Forge and Fabric) gives every `Prehistoric` mob multipart hitboxes through DarkPred's **MoreHitboxes** library (MIT, v1.9.2+). Hitboxes are defined per species in datapack JSON (`data/fossil/hitboxes/*.json`, 54 files, all bone-referenced). Each one becomes a Forge `PartEntity` (or a custom Fabric equivalent). On the server, parts sit at fixed yaw-rotated, scaled offsets. On the client they are moved to the live GeckoLib bone positions captured during rendering. Damage on any part goes straight to the parent's `hurt` with no per-part multiplier. The library also handles part IDs, section indexing, picking redirects, culling bounds, "anchors" (rider and eat positions), and client-detected "attack boxes".

The Javadoc says the code "is purely clientside and there is no coordination with the server". `clientTick` tests the active boxes against the local player and clears them after a hit or when they expire. — [MH MultiPartEntity.java L72-84](https://github.com/DarkPred/MoreHitboxes/blob/012edbb4258120161c96103e51dac6374b78cab8/common/src/main/java/com/github/darkpred/morehitboxes/api/MultiPartEntity.java#L72-L84), [MH AttackBoxDataInternal.java L50-72](https://github.com/DarkPred/MoreHitboxes/blob/012edbb4258120161c96103e51dac6374b78cab8/common/src/main/java/com/github/darkpred/morehitboxes/internal/AttackBoxDataInternal.java#L50-L72)

### Inferences
- **Server and client hitboxes diverge during animations.** The animation override is written only by the client-side GeckoLib renderer mixin. The server never renders, so it always uses the static yaw-rotated JSON offsets. The client picks against animated boxes, while server-side queries (projectiles, explosions, AI `getEntities`) use the rest-pose boxes. Melee still works because the server resolves the aligned part ID and the Forge reach check is generous.
- Damage localisation is available (`partHurt` receives the part), but Fossils does not use it. All parts deal equal damage.
- There is no block collision or pathing based on the parts. Movement, navigation and suffocation use the single scaled AABB, and Fossils even refuses AABB growth into walls.
- Performance cost: part entity objects (about 3-8 per dinosaur), an `updatePosition` call per part per tick, and Forge's global part iteration in every `Level.getEntities` query. On the client, the section-manager bookkeeping is extra, while the bone reads come for free from rendering. Off-screen mobs keep stale override positions, because no render happens for them.
- Exploit surface: since attack boxes rely on the client reporting a hit (`C2SHitPlayerMessage`), a modified client can simply never report hits for attack-box attacks. That species set is tiny (1 JSON uses `is_attack_box`).

### Gaps
- Fossils 1.19.x branches were not checked to see whether MoreHitboxes was already used there. Only 1.20.1 was examined.
- I could not find any public statement from the Fossils or MoreHitboxes authors about known issues, such as the server/client animation divergence. The divergence is inferred from the code.
- The MoreHitboxes wiki (setup instructions) and Blockbench plugin were not fetched.

## Q4. Alex's Mobs (1.20): how do its multipart creatures work (cachalot, giant squid, laviathan; anaconda, bone serpent, centipede, void worm)?

### Takeaway
Alex's Mobs uses two separate designs. (A) **Forge `PartEntity` bodies** (cachalot whale, giant squid, laviathan): parts are placed every tick on both sides with dragon-style yaw trigonometry and a yaw ring buffer, they are not saved or tracked, and a custom client-to-server `MessageHurtMultipart` packet works around the unaligned part IDs. (B) **Segment chains made of real, saved, tracked entities** (anaconda, bone serpent, centipede, void worm): each segment is a `LivingEntity` or `Mob` spawned with `addFreshEntity`, linked to its parent by a synced UUID, and moved by the head on the server each tick. Its position reaches clients through normal entity tracking. Segments forward damage to the head (optionally with a multiplier), except void worm segments, which have their own health and can split the worm.

### Cited Findings
**(A) PartEntity bodies**
- `EntityCachalotPart extends PartEntity<EntityCachalotWhale>`, with a scalable size and a `scale` field (0.5 for babies). It is pickable, its pick result is the parent's, `is()` matches itself or the parent, its save methods are empty, and `getAddEntityPacket` throws. `collideWithNearbyEntities()` pushes pushable entities near the part away from the whale. — [AM EntityCachalotPart.java L24-111](https://github.com/AlexModGuy/AlexsMobs/blob/09755dade2cfbdf14839e026d3af446f9d3ff843/src/main/java/com/github/alexthe666/alexsmobs/entity/EntityCachalotPart.java#L24-L111)
- Part `hurt` on the client: if the parent is not invulnerable, it sends `MessageHurtMultipart(partId, parentId, amount, damageTypeKey)` to the server. On both sides it then calls `parent.attackEntityPartFrom(this, …)`, which in the whale is simply `this.hurt(src, amt)` (no per-part scaling). `interact` likewise sends `MessageInteractMultipart` from the client. — [AM EntityCachalotPart.java L48-79](https://github.com/AlexModGuy/AlexsMobs/blob/09755dade2cfbdf14839e026d3af446f9d3ff843/src/main/java/com/github/alexthe666/alexsmobs/entity/EntityCachalotPart.java#L48-L79), [AM EntityCachalotWhale.java L832-834](https://github.com/AlexModGuy/AlexsMobs/blob/09755dade2cfbdf14839e026d3af446f9d3ff843/src/main/java/com/github/alexthe666/alexsmobs/entity/EntityCachalotWhale.java#L832-L834)

### Inferences
- Why the client-to-server hurt packet exists: Forge part IDs are not aligned (Q2), so the vanilla attack packet carries a client part ID the server cannot resolve to the right part. Alex's Mobs sidesteps this by sending the parent ID plus damage directly. The cost is that the server **trusts a client-supplied damage amount and type** with no reach or rate check, which a modified client could exploit against any multipart mob. In addition, the server's `getEntity(clientPartId)` could resolve to an unrelated entity that happens to have that ID; if that entity is an `IHurtableMultipart` (for example an anaconda segment), it gets `onAttackedFromServer`. The giant squid's `getMsgId()` (for example `"mob"`) often does not match a damage-type registry key, so its message may be dropped.
- Design B (real segment entities) gives server-authoritative, persistent and naturally synced segments, plus per-segment AI-free terrain hugging. The costs are full entity overhead per segment (ticking, tracking packets, saving, entity count toward caps), orphan cleanup, UUID relinking on load, and separate renderers. Design A is cheaper but not persistent, and its hits depend on client and server computing the same placement.
- Neither design gives the parts block collision or pathfinding. Bodies move by the head's AABB and navigation. Anaconda segments only adjust pitch to hug terrain and otherwise use `moveTo`, which ignores collision.

### Gaps
- I did not verify whether the Alex's Mobs 1.20 networking registers `MessageHurtMultipart` with any server-side sanity checks elsewhere (for example in the channel registration). Only the handler was read.
- Bone serpent and centipede head spawning and update code was only skimmed. They follow the same pattern as the anaconda according to the method names (`tickMultipartPosition`, `addFreshEntity`).
- No public issue tracker evidence was collected for multipart bugs in Alex's Mobs.

## Q5. Other dinosaur and creature mods with multipart systems (one line each)

### Takeaway
Forge `PartEntity` subclasses are common across creature mods (a GitHub code search for `extends PartEntity` returns dozens of mods). Among dinosaur and creature mods, Untamed Wilds and Prehistoric Fauna use Forge `PartEntity`. JurassiCraft's public repo shows no part-entity use, and Prehistoric Nature's 1.12.2 dev repo only references vanilla 1.12 `MultiPartEntityPart`.

### Cited Findings
- **Untamed Wilds** (RayTrace082, default branch 1.18.2): `EntityBaleenWhale` (an inner `EntityWhalePart extends PartEntity`), `EntityWhaleShark` and `EntityAnaconda` use Forge `PartEntity`. The whale uses a ring-buffer yaw and `setPos(parent + offset × part.scale)`, so the approach is cachalot-like. — [UW EntityBaleenWhale.java](https://github.com/RayTrace082/untamedwilds/blob/1.18.2/src/main/java/untamedwilds/entity/mammal/EntityBaleenWhale.java)
- **Prehistoric Fauna** (superlord9362, branch 1.20.1): `CorruptedTheropodPart extends PartEntity<CorruptedTheropod>` for a boss creature. The regular dinosaurs were not observed to use parts. — [PF CorruptedTheropodPart.java](https://github.com/superlord9362/Prehistoric-Fauna/blob/1.20.1/src/main/java/superlord/prehistoricfauna/common/entity/henos/CorruptedTheropodPart.java)
- **Prehistoric Nature** (AechtRob/PNDEV1.12.2, 1.12.2): `LepidodendronBucketHandler` resolves `MultiPartEntityPart` to its parent, which shows awareness of vanilla 1.12 multipart parts. I could not confirm whether its creatures create parts. — [PN LepidodendronBucketHandler.java](https://github.com/AechtRob/PNDEV1.12.2/blob/master/src/main/java/net/lepidodendron/LepidodendronBucketHandler.java)
- **JurassiCraft** (JurassiCraftTeam/JurassiCraft, last push 2022-01): a code search for `PartEntity` / `MultiPart` found only a blockstate `MultipartStateMap`, with no entity multipart. — [JurassiCraft repo](https://github.com/JurassiCraftTeam/JurassiCraft)
- The same GitHub code search also lists PartEntity users including Alex's Caves (`SauropodPartEntity`, `TremorzillaPartEntity`, `HullbreakerPartEntity` via `ACMultipartEntity`), Ice and Fire CE (`MultipartPartEntity`), Twilight Forest (`TFPart` for the hydra and naga), Cataclysm (`Cm_Part_Entity`), Iron's Spells (`IceSpiderPartEntity`), EEEAB's Mobs, Advent of Ascension (`AoAEntityPart`), Draconic Evolution (`DraconicGuardianPartEntity`) and Minestuck (`BasiliskPartEntity`). — [GitHub code search "extends PartEntity"](https://github.com/search?q=%22extends+PartEntity%22&type=code)

### Inferences
- Forge `PartEntity` with parent-driven placement is the de facto approach in 1.18-1.20 creature mods. Data-driven and animation-driven boxes (MoreHitboxes) are the most advanced of the systems examined here.

### Gaps
- Naturalist and "Creatures" mods were not checked: the GitHub API rate limit was reached. Their use of multipart is unknown from this research.
- Jurassic Revival / Jurassic World Reborn style mods were not located in public repos during this pass.
- Prehistoric Nature's entity-side multipart usage was not confirmed (rate-limited before the follow-up search).
