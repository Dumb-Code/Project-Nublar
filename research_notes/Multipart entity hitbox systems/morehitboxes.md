## Q1. How are box positions computed on the server and on the client in 1.21.1, and do the two sides agree while an animation plays?

### Takeaway
1.21.1 uses exactly the same placement model as 1.20.1. There is no server-side bone evaluation, no position sync packet and no reconciliation. The server always places each part at the static JSON offset, rotated by `yBodyRot` and multiplied by `getScale()`. The client replaces that offset with the GeckoLib bone position that it reads during rendering, once per game tick. While an animation moves a bone, the client boxes and the server boxes are in different places. The library does nothing about this. Melee still works because the client picks against its own (animated) boxes and sends the part ID. Projectiles, explosions and AI queries are computed on the server against the static boxes.

### Cited Findings
**Server and shared tick path (both sides)**
- `MultiPart.updatePosition()` (default interface method) copies the current position into `xo/yo/zo` and `xOld/yOld/zOld`. If `getOverride()` is non-null it sets the position to `parent.position() + override.localPos()`, with no rotation or scale applied by the library. Otherwise it uses `parent.position() + offset.yRot(-yBodyRot × DEG_TO_RAD).scale(parent.getScale())`. A source comment says "Maybe unset animationOverride? I'm not sure if there is a scenario where the override is only set sometimes", so an override, once set, is never cleared. — [MH21 c/api/MultiPart.java L43-64](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/common/src/main/java/com/github/darkpred/morehitboxes/api/MultiPart.java#L43-L64)
- `MobMixin` (now in the common module, listed in the NeoForge and Fabric mixin configs as a non-client mixin) calls `updatePosition()` on every part, and then `AnchorData.updatePositions()`, at the RETURN of `Mob.aiStep`. This runs on both logical sides. — [MH21 c/mixin/MobMixin.java L14-22](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/common/src/main/java/com/github/darkpred/morehitboxes/mixin/MobMixin.java#L14-L22), [MH21 neoforge morehitboxes.mixins.json](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/neoforge/src/main/resources/morehitboxes.mixins.json)

**Client bone capture (render thread)**

- What `bone.getLocalPosition()` means in GeckoLib 4 (1.20.1 branch, 4.8.4): `preRender` saves `entityRenderTranslations` from the pose stack **before** model scaling and before `applyRotations` (body yaw). Matrix tracking is therefore switched on by the first read, and the values are filled in from the following render pass. — [GL GeoBone.java L321-389](https://github.com/bernie-g/geckolib/blob/7d6f32db9168a24e14b327c0ad9f8f87dfc204de/Forge/src/main/java/software/bernie/geckolib/cache/object/GeoBone.java#L321-L389)
- Only position and scale are taken from the bone. The part is still an axis-aligned `EntityDimensions` box. - The wiki confirms that rotation has no in-game effect. The Blockbench "Create Hitbox Animation" action "will visually rotate the bone to match, how it would look ingame. ### Inferences
- **The two sides disagree during animations, and the gap can be large.** The server box is a fixed yaw-rotated offset (the rest pose). The client box follows the bone. For example, a lowered head when drinking, a sleeping pose, or a tail swing moves the client box but not the server box. The size of the gap equals the animated pivot displacement × scale. There is no reconciliation, so the server's answer to any server-side query is always the rest pose.
- Effect by query type:
  - **Player melee:** client-authoritative in practice. The client picks an animated part and sends its aligned ID. On Forge/NeoForge the server checks reach against the parent with Forge's generous reach padding. The server does not check that the ray hits the part's server box.
  - **Projectiles (arrows, tridents):** server-authoritative. They hit the server's rest-pose boxes, while the player sees the arrow pass through or hit "air" during a pose.
  - **AI `getEntities` and area damage:** use the rest-pose boxes.
- On the client, the override is captured once per game tick, on the first render frame of that tick. It is relative to the parent's interpolated render position at that frame's partial tick, but is added to the parent's current-tick position in `aiStep`. This gives sub-tick jitter of up to one tick of parent motion. The overall lag is about 1 tick, which the author acknowledges for anchors only.
- Mobs that are not rendered (behind the camera, culled, or out of render distance) keep their **last** override forever (it is never cleared). Their client boxes then show a stale pose, offset from the current parent position. Mobs that were never rendered on this client use the static offsets.
- If the GeckoLib descriptor does not match (`require = 0`), the mixin silently does nothing. Boxes then stay static on both sides, which hides the problem instead of crashing.

### Gaps
- No issue, wiki page or commit message from the author discusses the server/client mismatch, so the author's intent (accepted limitation versus oversight) is unknown. The four wiki pages and all eight GitHub issues were read.
- The behaviour was not tested in game (by constraint). The size of the mismatch for any given animation is inferred from the code.

## Q2. What is the hitbox definition data format (with Fossils examples), and how are bone names bound?

### Takeaway
One datapack JSON file per entity type at `data/<namespace>/hitboxes/<path>.json`. The file's resource location must equal the `EntityType` registry key. It holds an `elements` array. Each element has `name`, `pos` [x, y, z] (model pixels; it is the bottom-centre of the box, with x and z negated from Blockbench space), `width` (x = z), `height`, an optional `ref` (GeckoLib bone name), and the optional flags `is_anchor` and `is_attack_box`. Binding uses an exact bone-name match on `ref`. By the Blockbench plugin's convention, the bone is named `<cube name>_hitbox`. There is no per-part damage multiplier, rotation or per-part flag beyond those listed. Damage localisation goes through code (`partHurt` receives the part, and `getPartName()` gives its name).

### Cited Findings
**Loader**
- `HitboxDataLoader extends SimpleJsonResourceReloadListener`, folder `"hitboxes"`, registered as SERVER_DATA. For each file it reads `elements`. Per element it reads `pos` (3 numbers), `ref` (default `""`), `name`, and then either `is_anchor` (giving a width/height-0 record) or `width`, `height` and `is_attack_box`. All lengths are divided by 16. Unknown keys are ignored. The map key is the file's `ResourceLocation`. — [MH21 c/internal/HitboxDataLoader.java L23-78](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/common/src/main/java/com/github/darkpred/morehitboxes/internal/HitboxDataLoader.java#L23-L78), [MH21 c/MoreHitboxesMod.java L17-19](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/common/src/main/java/com/github/darkpred/morehitboxes/MoreHitboxesMod.java#L17-L19)
- Lookup is `HITBOX_DATA.getHitboxes(EntityType.getKey(entity.getType()))`, called once in the `EntityHitboxDataInternal` constructor (that is, at mob construction). Elements are sorted there into attack boxes, anchors and parts. Parts with a non-blank `ref` are indexed by `ref`. `headRadius` comes from parts whose **name contains "head"**. — [MH21 c/internal/EntityHitboxDataInternal.java L31-74](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/common/src/main/java/com/github/darkpred/morehitboxes/internal/EntityHitboxDataInternal.java#L31-L74)

**Damage per part**
- `MultiPartEntity.partHurt(MultiPart<T>, DamageSource, float)` is abstract, and `MultiPart.getPartName()` returns the JSON `name`. The part's `hurt` checks `isInvulnerableTo` and then calls `parent.partHurt(this, …)`. Any multiplier is therefore left to the mob's code. ### Inferences
- The JSON `pos` and the bone pivot are two separate sources of truth. The static (server) position comes from `pos`, and the animated (client) position comes from the bone pivot. They agree only if the author aligned the pivot with the cube's bottom-centre. Misalignment adds a constant server/client offset even in the rest pose. In the Fossils T-rex, the head bone pivot z (-25.1, which is 25.1 after the Blockbench negation) and the JSON head z (22.6) differ by about 2.5 px, if both are in the same frame of reference. That has not been verified in game.
- Hitbox data is read once, at construction. Changing a file and running `/reload` affects only mobs constructed after the reload, on the server side, and on clients only after the data is re-synced (see Q3).

### Gaps
- No JSON schema or version field exists. Behaviour with malformed files (for example a missing `width`) is a thrown `JsonSyntaxException` from `GsonHelper` inside `apply`. Whether the whole reload then fails was not checked.

## Q3. Which loaders does each branch support, is 1.20.1 still maintained, and is its API compatible with 1.21.1?

### Takeaway
- **Loaders:** 1.20.1 = Forge + Fabric (MultiLoader-Template with a common module, not Architectury). 1.21.1 = NeoForge + Fabric. There is no Forge build for 1.21.1.
- **API compatibility:** the public `api` package is byte-for-byte identical between the two branches, so mob-side code ports unchanged.
- **Maintenance:** 1.20.1 is a release line that receives fixes merged down the branch chain 1.18.2 → 1.19.x → 1.20.1 → 1.20.6 → 1.21.1. Its last commit was 2025-09-14 (1.9.3). ## Q4. Other mechanics in 1.21.1: part entities, IDs, picking and hit redirection, attack boxes, collision, pathfinding, debug rendering, performance

### Takeaway
All of these behave as described for 1.20.1 in the baseline. The 1.21.1 changes are structural only: NeoForge `PartEntity` replaces Forge `PartEntity`, mixins moved to common, and the payload codec changed. Parts are never saved, tracked, ticked or physics-enabled. IDs are aligned as `parentId + i + 1`. Hits are redirected to the stored part. Attack boxes are client-detected. - **Performance per multipart mob per tick:**
  - k `updatePosition` calls, each a vector rotate plus `setPos`, which triggers Forge/NeoForge section move callbacks on the client;
  - one anchor pass;
  - on NeoForge, a fresh `PartEntity[]` allocation whenever the loader calls `getParts()`;
  - on the render thread, one hash lookup per bone per tick (render passes after the first are skipped by the guard).
  - On top of this, every `Level.getEntities` call in the world iterates all part entities: Forge's own global part loop plus the library's typed-query loop. That cost grows with the total number of parts loaded.
  - No profiler data was published.
- `MobMixin` and the NeoForge mixins test `this instanceof MultiPartEntity` for **every** `Mob`, which is a negligible cost per mob.

## Q6. What would integrating MoreHitboxes into Project Nublar (Forge 1.20.1 47.2.30, GeckoLib 4.7.3, multiloader) take, and what conflicts with the existing DinosaurPart?

### Takeaway
Mechanically, integration is small. You need to: (1) add the Cloudsmith repo and the `common` / `forge` (and `fabric`) 1.20.1 artifacts; (2) make `Dinosaur` implement `GeckoLibMultiPartEntity<Dinosaur>` with a field `EntityHitboxDataFactory.create(this)`, `getEntityHitboxData()` and `partHurt`; (3) write one `data/projectnublar/hitboxes/<entity_path>.json` per species; (4) add empty `<name>_hitbox` bones to each geo model. The real work is removing or quarantining Nublar's own part system and providing growth through `getScale()`. Nublar must also accept, or fix by forking, the server/client animated-box mismatch from Q1.

### Inferences
**Integration steps (Forge 1.20.1)**
1. Add the Cloudsmith Maven repository. Depend on `morehitboxes-common-1.20.1:1.9.2` in common (compileOnly), `morehitboxes-forge-1.20.1:1.9.2` in forge and `morehitboxes-fabric-1.20.1:1.9.3` in fabric, and declare `morehitboxes` as required in `mods.toml` and `fabric.mod.json`, as Fossils does.
2. `Dinosaur implements GeckoLibMultiPartEntity<Dinosaur>`. Add a field initialiser `hitboxData = EntityHitboxDataFactory.create(this)`. In `partHurt`, implement per-part damage multipliers keyed by `part.getPartName()`, since the JSON has no multiplier field. This replaces PN's `damageMultiplier`.
3. Make growth flow through `getScale()`. Override it with the age scale, and make `getDimensions` use it as Fossils does. Otherwise the static (server) offsets and part sizes will not grow.
4. For each species, write a hitbox JSON (Blockbench plugin export) and add empty `<name>_hitbox` bones (plus `rider_pos` if needed) whose pivots sit at the box bottom-centres. Use multiple boxes for long or tall bodies, because each part is an axis-aligned box that does not rotate.

**Conflicts with the existing DinosaurPart and how to resolve them**
- Retire the common `DinosaurPart` / `PartEntity` spawning (the T-rex head) when MoreHitboxes goes in. Otherwise each species has two overlapping pickable surfaces: a real tracked `dinosaur_part_entity` and a library part. Their damage routing also differs: PN's part resolves the parent only on the server, which yields a null parent on the client, so a client hit routes nowhere. PN's current part is also non-functional: `DINOSAUR_HEAD_POS` is never written, so the head part sits at the origin offset.
- Do not override Forge's `getParts()` / `isMultipartEntity()` in `Dinosaur`. The library adds those overrides to `Mob` with a mixin, and a subclass override would hide the library's parts from Forge's level part map, breaking picking. Delete or rename the unused forge `DinosaurPart`.
- PN's own class is named `PartEntity` (same simple name as Forge's). That causes no runtime conflict, but expect import ambiguity in forge sources.

**The animation mismatch (Q1) is the design decision**
- If server-authoritative accuracy during animations matters (for example, projectiles against a lowered head, or a server-side bite reach), the library alone does not provide it. Options:
  - (a) accept the mismatch, as Fossils does;
  - (b) author animations so that the hitbox bones barely move;
  - (c) fork the MIT code to compute the bone pivot on the server from the GeckoLib animation data. This is not provided anywhere in the library.
- Option (c) would conflict with the library's renderer-coupled design. The author's own TODO notes the GeckoLib coupling.
