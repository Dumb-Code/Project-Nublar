## Q1. What does the library provide, and what is the hitbox model (real part entities, virtual boxes, or something else)?

### Takeaway
It is a hybrid: each sub-hitbox is a real Forge `PartEntity<Entity>` subclass (`CustomEntityPart`, the Ender Dragon pattern), but the parts are never spawned or networked as entities. A mixin injects the whole multipart state into every `LivingEntity`, and a set of further mixins (picking, `Level.getEntities`, reach, collision, pushing, pathfinding, block placement) make vanilla code test the part AABBs and then resolve every hit to the parent entity.

### Inferences
- The `PartEntity` subclass is used mostly as a convenient AABB carrier with `getBoundingBox()`, `hurt()` and `push()`; the real work is done by mixins that walk `getCustomParts()` and substitute the parent. The parts are not in the level entity list, are not tracked, and have no network ID shared between sides (`getAddEntityPacket` is null and nothing sets matching IDs), which is why hit results are redirected to the parent rather than to the part (see Q4).
- Because it is a blanket mixin into `LivingEntity`, every living entity in a game pays for the extra fields and for the `instanceof ICustomMultipart` checks in the hot paths, even with no parts defined. Most hooks short-circuit cheaply when no parts exist (see Q6).

## Q2. How are hitboxes defined (data files or code)?

### Takeaway
Two ways: datapack JSON under `data/<ns>/custom_parts/*.json` selected by entity type id (plus a crude NBT match), or Java via `ICustomMultipart.addCustomPart(...)` / `MultipartHelper.addPart(...)` with an arbitrary `PartPositioner` lambda. Both can be per-`Pose`.

### Cited Findings
- `PartDefinitionLoader extends SimpleJsonResourceReloadListener` on folder `custom_parts`, registered through `AddReloadListenerEvent`; parsed definitions go into one static map. — [SRC datapack/PartDefinitionLoader.java L26-61](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/datapack/PartDefinitionLoader.java); [SRC CustomHitboxLib.java L41-44](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/CustomHitboxLib.java)
- JSON schema: top-level `id` or `selector{id,nbt}`, optional `pose`, `main_hitbox_pickable/pushable/collision`, and `parts[]` each with `name`, `width`, `height`, `offset[3]` or `positioner{type, offset}`, and booleans `pickable` (default true), `pushable`, `collision`, `suffocate` (default false). Positioner `type` is `offset` (default), `rotating` or `rotating_head`. — [SRC datapack/PartDefinitionLoader.java L83-161, L218-237](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/datapack/PartDefinitionLoader.java); [example zombie_wings.json](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/example_datapack/customhitboxlib/data/customhitboxlib/custom_parts/zombie_wings.json)
- NBT selector matching saves the whole entity to NBT and does string `split(",")`/`split(":")` comparisons of top-level keys (no nested compound support). — [SRC datapack/PartDefinitionLoader.java L186-216](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/datapack/PartDefinitionLoader.java)
- Datapack parts are attached in `EntityJoinLevelEvent` (fires on both logical sides), by looping over every loaded definition for every joining entity. — [SRC CustomHitboxLib.java L46-65](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/CustomHitboxLib.java)
- `/reload` does not update already-loaded entities; only new spawns get the new config. — [wiki/FAQ.md L37-39](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/wiki/FAQ.md)
- Java usage: cast any `LivingEntity` to `ICustomMultipart` and call `addCustomPart(name, PartDefinition.of(...), pose)`; `setMainHitboxCollision(false)` etc. to turn off the vanilla box's roles. — [wiki/Java-API.md L33-51](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/wiki/Java-API.md)

### Inferences
- **Dedicated-server risk (not tested):** the reload listener is registered on `AddReloadListenerEvent`, which is the server data-pack reload event, and the only network message the mod registers is the client-to-server rotation packet (Q5). Nothing sends datapack definitions to clients. On an integrated (single-player) server the static `LOADED_PARTS` map is shared by both sides in one JVM, so it works there; on a dedicated server the client's map is likely empty, so client entities would have no parts, and client crosshair picking of parts (Q4) would not work for datapack-defined parts. Java-API users who add parts in common code (for example in the entity constructor) on both sides avoid this.
- For a modded entity the natural integration point is to call `addCustomPart` in the constructor (runs on both sides) with a custom `PartPositioner` lambda.

### Gaps
- No issue or doc confirms or refutes the dedicated-server behaviour above; it is code inference only.

## Q3. How are hitboxes positioned and rotated? Are they tied to animation bones (GeckoLib or other)?

### Takeaway
Boxes are plain axis-aligned `AABB`s of fixed width/height (vanilla `EntityDimensions`); only their **centre position** moves. Position comes from a `PartPositioner` lambda evaluated each tick on each side independently. Built-ins rotate an offset by yaw only. There is **no** bone, animation, GeckoLib, oriented-box, pitch or roll support.

### Cited Findings
- Built-in positioners: `atOffset` (world-axis offset, no rotation), `rotating` (offset rotated by `yBodyRot` for living entities), `rotatingHead` (offset rotated by `entity.getYRot()`), `relativeTo(anchor,...)`, `following(distanceBehind, height)` (uses look vector), `lerpTo(target,..., speed)`. Y offset is never rotated. — [SRC api/PartPositioners.java L12-62](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/api/PartPositioners.java)
- Doc-vs-code mismatch: the wiki says `rotating_head` uses `yHeadRot`, but `rotatingHead` reads `entity.getYRot()`. — [wiki/Datapack-Guide.md L225-227](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/wiki/Datapack-Guide.md); [SRC api/PartPositioners.java L31-42](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/api/PartPositioners.java)
- Each tick (injected at `Entity.tick` HEAD) `tickCustomParts()` calls `positioner.getPosition(self, 1.0F)` for each active part, stores the previous position in `xo/yo/zo`, and calls `part.setPos(...)`, which recomputes the part AABB from its fixed dimensions. — [SRC mixin/EntityMixin.java L44-50](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/EntityMixin.java); [SRC mixin/LivingEntityMixin.java L242-287](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/LivingEntityMixin.java)
- The only "animation" coupling is per-`Pose` part sets (standing, crouching, swimming, fall_flying, sleeping, dying, etc.). — [wiki/Datapack-Guide.md L170-185](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/wiki/Datapack-Guide.md); [SRC mixin/LivingEntityMixin.java L117-130, L315-357](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/LivingEntityMixin.java)

### Inferences
- A mod could feed bone positions in through a custom `PartPositioner`, but the server would need its own source of bone transforms; the library gives no help with that. A long body that yaws will be approximated by a chain of axis-aligned cubes whose size does not change with yaw (a diagonal neck becomes fat cubes).
- Because `getPosition` is called with `partialTick = 1.0F` on tick, and the lambda reads live entity state, client and server compute positions independently and only agree to the degree their entity position/rotation agree.

- No examples or issues discuss GeckoLib or animation-driven placement.

## Q4. How do the parts interact with damage and hit detection (ray picking, melee, projectiles, reach)?

### Takeaway
Ray picking is fully replaced in `ProjectileUtil.getEntityHitResult` (both overloads): for each candidate entity it tests the main AABB (optionally skipped) and each pickable part AABB, keeps the nearest intercept, and **always returns an `EntityHitResult` on the parent entity** with the part's hit point. Melee reach is extended via Forge `IForgePlayer.isCloseEnough`. Damage goes to the parent with no per-part multiplier.

### Cited Findings
- `ProjectileUtilMixin` injects at `RETURN` of both `getEntityHitResult` overloads (the one used for crosshair picking with `Entity shooter`, and the `Level` one used by projectiles) and overwrites the result: iterate `level.getEntities(shooter, area, predicate)`, clip main box (skipped if `isMainHitboxPickable()` false), clip each pickable part box, keep the closest; result entity is the parent. — [SRC mixin/ProjectileUtilMixin.java L22-75, L77-123](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/ProjectileUtilMixin.java)
- `LevelMixin` appends to `Level.getEntities(Entity, AABB, Predicate)` the parent of any tracked part whose box intersects the query area (respecting the predicate), so area queries (picking candidates, sweeps, explosions, AI scans) find a parent whose own box is far away. — [SRC mixin/LevelMixin.java L17-37](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/LevelMixin.java); [SRC util/CustomPartTracker.java L30-47](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/util/CustomPartTracker.java)
- `PlayerMixin` implements Forge `IForgePlayer.isCloseEnough(entity, dist)` to pass if the eye is in range of the main box or of any pickable part box; added to fix issue #2 (server reach check failed when attacking a part ~4 blocks from the entity centre). — [SRC mixin/PlayerMixin.java L13-42](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/PlayerMixin.java); [issue #2](https://github.com/gawrmonster/CustomHitboxLib/issues/2); [commit 1970077](https://github.com/gawrmonster/CustomHitboxLib/commit/1970077)
- Issue #2 reporter also described client-side forwarding failures for far parts; the maintainer said it was fixed in 1.3.8 and later found and fixed an intermittent cause; issue closed. — [issue #2 comments](https://github.com/gawrmonster/CustomHitboxLib/issues/2)
- `CustomEntityPart.hurt` forwards full damage to the parent; the FAQ confirms there is no per-part damage system (extend `CustomEntityPart` for custom logic). — [SRC api/CustomEntityPart.java L140-145](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/api/CustomEntityPart.java); [wiki/FAQ.md L69-71](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/wiki/FAQ.md)
- Debug render: F3+B draws green boxes for parts (with `isMultipartEntity()` temporarily suppressed so vanilla does not draw them twice). — [SRC mixin/MixinEntityRenderDispatcher.java L18-90](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/MixinEntityRenderDispatcher.java)

### Inferences
- Since the hit result names the parent, not the part, the *identity of the part hit is lost* at the vanilla attack layer; extending `CustomEntityPart.hurt` only helps for code paths that call `part.hurt` directly. A consumer wanting "headshot" logic would have to derive the part from the hit location. Note also that the `ProjectileUtil` mixin returns the parent for projectile hits, so `Projectile.onHitEntity` sees the parent.
- Replacing the return value of `ProjectileUtil.getEntityHitResult` unconditionally (even for entities with no parts) means any other mod that hooks the same method may conflict.

### Gaps
- Whether Forge's own `PartEntity` attack path (client sends part ID) is ever used is unclear; given the hit result is the parent, it probably is not.

## Q5. How are hitboxes synced between server and client?

### Takeaway
They are not synced as entities. Both sides construct parts from the same definitions and run the same positioner each tick. The only packet is a client-to-server **player rotation** packet (yRot, xRot, yBodyRot, yHeadRot) so that a multipart player's server-side parts match the client's view.

### Cited Findings
- One `SimpleChannel` (protocol "2") with one message, `CustomPartPositionSyncPacket`, carrying four floats; handler applies them only if the sender is a `ServerPlayer` via `setSyncedRotation`. — [SRC CustomHitboxLib.java L24-39](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/CustomHitboxLib.java); [SRC network/CustomPartPositionSyncPacket.java L11-53](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/network/CustomPartPositionSyncPacket.java)
- Client side: in `tickCustomParts`, a multipart player sends the packet whenever any of the four angles changed; server side: the stored angles are written back onto the server player each tick before parts are positioned. — [SRC mixin/LivingEntityMixin.java L253-272, L289-302](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/LivingEntityMixin.java)
- The commit "better parts position sync" replaced an earlier `Map<String, Vec3> syncedPartPositions` (client-sent part positions) with this rotation-only packet. — [commit b3d1e43](https://github.com/gawrmonster/CustomHitboxLib/commit/b3d1e43)
- For multipart players, the server move-validation (`isPlayerCollidingWithAnythingNew` in `handleMovePlayer`) is redirected to test each colliding part box at the new position. — [SRC mixin/ServerGamePacketListenerImplMixin.java L27-68](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/ServerGamePacketListenerImplMixin.java)

### Inferences
- Mob parts rely entirely on vanilla position/rotation sync; client-side part positions will lag or differ slightly from the server (vanilla interpolates mob position and sends rotations quantised to 1/256 turn), which is acceptable for picking because the server re-checks reach with its own boxes.
- Server accepts client-supplied rotations without validation (same trust level as vanilla move packets).

### Gaps
- No network bandwidth figures; the packet is 16 bytes per change for players only.

## Q6. Do the parts affect block collision, movement, entity pushing, and pathfinding? Performance?

### Takeaway
Yes, optionally per part (`collision`, `pushable`, `suffocate` flags) and per main box. Block collision is a real compound-AABB sweep inside `Entity.collide` (with step-up), entities with colliding parts become solid to each other, pushing is reimplemented, and pathfinding gets only Y-level fixes plus a rewritten `MoveControl`; the node evaluator still uses the main entity width. The cost is linear in parts and has several hot-path extras.

### Cited Findings

### Inferences
- The `MoveControl` replacement and the `followThePath` `@Overwrite` apply to **every vanilla and modded mob** whenever this mod is installed, because the guard is `mob instanceof ICustomMultipart`, which is always true for a `Mob`. This changes movement for mobs without parts too (for example the jump condition), and conflicts with any other mod that overwrites or injects into those methods. Per-tick reflection on `MoveControl` for every mob is a measurable cost in mob-heavy worlds.
- `ProjectileUtil` result replacement also applies globally (Q4). So "lightweight / non-intrusive" in the README is a marketing claim, not a property of the code.
- Pathfinding treats the creature as having its main width; collidable parts are not considered in node passability (only start Y and move-control jumping), so a long body made of colliding parts can get stuck where the main box would fit.
