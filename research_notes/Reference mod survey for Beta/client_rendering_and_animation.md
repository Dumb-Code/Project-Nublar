## Key question 1: Entity Model Features. How does it parse, compile, evaluate, swap, vary, cull and stay compatible, and what runs on 26.x?

### Takeaway

EMF does all parsing and expression compilation once, at model bake time, through a single mixin on `EntityModelSet.bakeLayer`, then compiles a whole model's animation lines into one JVM bytecode method that reads and writes flat `float[]` and `boolean[]` arrays, so the per-frame cost is one method call per entity render plus the variable suppliers it actually reads. Its two performance tools are a distance LOD that holds the last pose for N frames (N grows with distance, shrinks for large mobs and low fps) and stripping redundant per-part texture overrides so a model uses one render type. Its biggest render-time cost is a vertex-buffer switch per part that has its own texture, which is the same cost class as Nublar's per-layer passes.

### Inferences

- Nublar does not need an expression compiler: GeckoLib 5 already compiles Molang once at resource load and caches constant sub-trees (see KQ3). The EMF lesson that transfers is the discipline, not the mechanism: compile at load, read only the variables an animation uses, allocate nothing per bone. **B25, B27. Perf: n/a (design rule).**
- EMF's LOD is the cheapest proven animation LOD in a shipping mod: hold the last pose and skip evaluation every N frames with N = distance / 20, scaled down for large mobs so a 12.5-block Brachiosaurus keeps detail at range. GeckoLib 5 has no LOD, so Nublar would implement it in its renderer (mechanism proposed in KQ4). **B25. Perf: good.**
- EMF's single biggest render cost, a vertex-buffer switch per part with its own texture, is the same cost class as Nublar's per-layer full-model passes; its mitigation (collapse to one render type when possible) points the same way as Nublar's baked-texture spec. **B09, B25.**
- EMF's variant pipeline (resource-pack `.properties`, per-entity UUID to variant cache, cadence re-check) is more than Nublar needs: a per-species JSON list of variants resolved once per animal and stored in `DinoData` costs nothing per frame, and resource packs still override textures by path. **B09, B24. Perf: good.**
- Model and animation overrides from resource packs come for free with GeckoLib because its loader uses the vanilla `ResourceManager` (KQ3); Nublar needs no `bakeLayer` mixin. **B24.**
- Vanilla feel: EMF's hold-pose LOD is visible as choppier motion at distance; EMF mitigates by exempting large mobs partially. Nublar should start skipping only beyond the IK cut-off (32 blocks) so near herds stay smooth. **B25.**

### Gaps

- The Java toolchain version for EMF's 26.2 builds was not found in the files read (`build.gradle.kts` lines 1-60 only set up loom); the mixin config says Java 17 compatibility and ASM emits V17 classes, but the actual compile target for 26.2 (which needs Java 25 in GeckoLib's case) was not confirmed.
- EMF publishes no frame-time measurements; all cost statements above are structural, not measured.
- The Entity Texture Features side (random texture rules, emissive textures) was read only through EMF's call sites; ETF itself was out of scope.

## Key question 2: Aquamirae. How does it animate and render large sea mobs and bosses, armour, world content, sound, and what is its multiloader and 26.x status?

### Takeaway

Aquamirae uses GeckoLib 4.8 for only three small or mid-sized mobs (Scuttler, Shellback, Golden Moth) and all 13 armour pieces; its large or complex creatures (Maw, Anglerfish, Maze Mother, Captain Cornelia boss, Eel, Tortured Soul) are vanilla `EntityModel`s driven by a hand-written procedural pipeline whose clips are server-owned tick counters synced once at start, and its largest creature (the 350-segment Shipbreaker) is not an entity at all but a client-side spline tube rendered from a `LevelRenderer` hook with per-segment frustum culling. There is no 26.x line.

### Inferences

- Aquamirae's choice not to use GeckoLib for its biggest or most-bone-heavy creatures, and to drive the ones it does use with one controller each, is consistent with GeckoLib 4's per-frame cost (KQ3) and is a data point, not a proof: a mod with real "many bones" content avoided the library's animation path for them. For Nublar the path is the opposite (GeckoLib 5 for all six species), so the lesson is to keep controller count low and bone count at 11 to 17. **B25. Perf: fair.**
- The `AnimState` design is a working model for B27's "synced pose state: animation id, start tick and loop flag, owned by the server": one small packet at clip start, local tick counters on both sides, no per-tick traffic, deterministic progress from the start tick. GeckoLib 5's `setAnimationTime` or triggered animations with a start-tick offset (KQ3) can play the same role inside GeckoLib. **B27. Perf: good.**
- Per-segment frustum culling with a generous AABB (10 blocks) is the pattern for a 12.5-block Brachiosaurus whose bounding box alone decides visibility: Nublar's B09 item "render culling box follows scaled size" is the cheap equivalent at entity level. **B09, B25.**
- The spline renderer's scratch-struct reuse and cached normals are the allocation discipline Nublar should apply to any custom geometry (leader crown, debug shapes). The per-frame ring list allocation shows what to avoid for 100 animals. **B25.**
- Vanilla feel: Aquamirae keeps vanilla `MobRenderer`, vanilla particles and vanilla fog hooks, so its creatures read as vanilla mobs; its only non-vanilla rendering concept (the tube body) is a boss event. Nothing here conflicts with vanilla feel for Nublar.

## Key question 3: GeckoLib 5. What changed in the render and animation pipeline, what does a frame cost per bone and per layer, how do texture layers work, and what does the 26.2 line require?

### Takeaway

GeckoLib 5 (package `com.geckolib`) split each frame into an extraction stage that copies everything into a `GeoRenderState` keyed by `DataTicket`s and runs the animation controllers to produce immutable `ControllerState`s, and a deferred submission stage that evaluates keyframes into per-pass `BoneSnapshot`s through an ordered list of `BoneUpdater`s (controllers first, then the renderer's `adjustModelBonesForRender`, then any added updater), applies them to the shared baked bones only while the submitted lambda runs, and emits pre-baked quads. Texture layers are either a full second model pass (`TextureLayerGeoLayer`, `AutoGlowingGeoLayer`) or a single-bone re-draw (`CustomBoneTextureGeoLayer`). There is no bone culling, no distance LOD and no off-screen skip inside GeckoLib; the vanilla `scale` attribute is applied to the model automatically; Molang is compiled once at resource load with constant folding and per-animation variable sets. The 26.2 line is 5.5.x on Java 25 for Fabric, NeoForge and Forge.

### Inferences

- **Per-animal, per-frame cost model (counted from the code above; not measured).** Extraction: one render state map with about 15 boxed ticket puts; per controller one `Actor`, one `AnimationTest`, one used-variable set, one query-value map and one `ControllerState`, plus one `AnimationPoint` when time advanced. Pass: one `RenderPassInfo` (two `Pose`s, three maps, one list), one lambda, one `BoneSnapshot` per animated bone, 9 keyframe evaluations per animated bone per controller (plus an `EasingState` per non-linear easing), then per bone one `Quaternionf` when rotated and per cube 6 `Vector3f` plus 24 `Vector4f`. For 12 bones with one cube each, roughly 370 small allocations and about 300 to 900 vertices per model pass. Each full-model texture layer repeats the geometry part (not the keyframe part, which is cached per pass). So a Nublar animal with a base pass and 5 full-model layers costs about 6 x geometry, and the keyframe work once. **B09, B25. Perf of full-model layers for a herd: poor; one pass: good.**
- Nublar's `DinosaurGeoModel.addIdleSway` (GeckoLib 4 `setCustomAnimations` writing bones after animation) maps to a `BoneUpdater` or an `adjustModelBonesForRender` override that adds to the snapshot rotation of the sway bones. Because snapshot rotation is added to base rotation at matrix time and updaters run after the controllers in a fixed insertion order, the add is additive to the baked clip and deterministic; this answers the hitbox design's open test item "whether bone updaters fight the controller" at the code level (not yet in game). The same hook carries B27's neck and tail bend delta and leg IK. **B27, B09. Perf: good (one snapshot write per bone).**
- The head-only idle question in B09 has a cheap answer in GeckoLib 5: a second, additive controller that plays a head-only clip on top of the body controller (9 evaluations per head bone per frame), or a `BoneUpdater` with a sine for the head, as today's sway does. Either avoids a second animation file per body clip. **B09. Perf: good.**
- Clip speed from body scale: with `setAnimationSpeedHandler` gone, set `controller.setAnimationSpeed(f(scale))` inside the state handler each frame; it is one field write, and `query.scale` is also available to Molang if the art team prefers to scale timing in the animation file. **B09, B16. Perf: good.**
- Smooth growth: GeckoLib 5 multiplies the vanilla scale attribute into the model automatically, so B16's attribute-driven growth needs no renderer code; the species base factor (target height / model height) goes in `withScale` once per species. **B16. Perf: good.**
- Server-owned pose state (B27) can reuse GeckoLib's own machinery: a triggered animation started from a synced start tick plays at the correct offset on a late-joining client, and `setAnimationTime` corrects drift; the stateless packets are the heavier alternative. Nublar still needs its own baked pose tables for server hitboxes; this is only about keeping the client clip in step. **B27. Perf: good.**
- Variant and gender textures: `getTextureLocation(renderState)` is called once per pass, so Nublar should resolve the texture `Identifier` at extraction from a small per-animal ticket (variant id, gender, bake key) and keep the `Identifier`s pre-built per species in a table, as `DinoLayer` does today. **B09, B24. Perf: good.**
- Threading caution: bone snapshots are set on shared singleton bones during the deferred lambda; any Nublar code that reads bone state must run inside that lambda (a `BonePositionListener` or `PerBoneRender`), never from a tick or another thread. **B27.**
- Vanilla feel: the 5.x pipeline keeps vanilla nameplates, shadows, hurt overlay and death roll through `postRenderPass` and `applyRotations`; nothing here changes how a mob reads in game.

## Key question 4: Cross-cutting. For six species, 11 to 17 bones, 4 to 6 layers and 20 to 100 animals, what is cheapest for colour compositing, animation LOD, smooth scale and resource-pack variants, and how does Nublar's current renderer compare?

### Takeaway

Nublar's current renderer draws every colour layer as one or two extra full-model passes (a Gallimimus with 11 layers draws the model 23 times a frame, measured at 26 to 28 fps for 20 animals against 138 fps with layers off), and the GeckoLib 5 layer API keeps that cost class. The cheapest design that survives the reference survey is: bake genome colours into one texture per colour key (the existing 2026-10-08 spec, which the GeckoLib 5 texture API supports), hold-pose animation LOD by distance in the renderer (EMF's proven scheme, absent from GeckoLib), scale through the vanilla attribute that GeckoLib 5 already multiplies in, and resolve variant textures from a data list at extraction so artists add skins by dropping files into resource packs.

**Reference facts reused here (cited in KQ1 to KQ3)**

- GeckoLib 5 full-model texture layers repeat the whole geometry emission per layer (KQ3, `TextureLayerGeoLayer`); the single-bone layer re-emits one bone (KQ3, `CustomBoneTextureGeoLayer`).
- GeckoLib 5 writes textures to the GPU through `GpuDevice.createTexture` and `CommandEncoder.writeToTexture` in its own animated-texture class (KQ3, `GeckoLibAnimatedTexture`), the same API a baked texture needs on 26.2.
- EMF's LOD: factor = distance / 20, scaled by FOV, fps and mob size, hold the last pose on skipped frames (KQ1).
- EMF collapses per-part textures to one render type when they are equal (KQ1); Aquamirae's spline renderer culls per segment and reuses scratch buffers (KQ2).
- GeckoLib 5 multiplies `LivingEntityRenderState.scale` into the model (KQ3) and exposes `query.scale` to Molang (KQ3).
- GeckoLib loads models and animations through the vanilla resource manager from `assets/<ns>/geckolib/{models,animations}` (KQ3).

### Inferences

**(a) Compositing genome colours onto layers**

| Option | Per-frame cost per animal | Memory | Notes | Rating |
|---|---|---|---|---|
| Per-frame tinting with full-model passes (today; GeckoLib 5 `TextureLayerGeoLayer` is the same pattern) | 1 + N geometry emissions, N buffer switches | none | Measured 26 to 28 fps at 20 animals with 11 layers; GeckoLib 5 removes the second animation evaluation but not the geometry | Poor |
| Baked texture per colour key (the spec) | 1 geometry emission, 1 texture | 4 MB per key, 32-slot LRU | Bake 1 to 2 ms plus upload on key change only; GeckoLib 5 `getTextureLocation(renderState)` returns the slot name; `getRenderColor` becomes white; the layer list is empty | Good |
| One texture with mask channels and a custom tint shader (a `RenderPipeline` like GeckoLib's emissive one) | 1 emission, no bake | none | Needs a custom pipeline and shader defines on both loaders, and shader-mod compatibility work (EMF's Iris special cases show the burden); not needed for Beta | Fair, higher maintenance |
| Per-bone texture layers (`CustomBoneTextureGeoLayer`) | 1 emission plus one small re-emit per decorated bone | none | Only for bone-local decoration (frill, crest), not body-wide colour layers | Good for one or two bones |

Recommendation: ship the bake (B09, B25). Keep the GeckoLib layer path only as the fallback while a key bakes, exactly as the spec says. Avoid the 1.20.1 `DynamicTexture` path; port the uploader against the 26.2 GPU API that GeckoLib's own animated texture already uses. Vanilla feel: none lost; translucent versus cutout sorting is the one visible choice and is already a lead decision with a switch.

**(b) Culling and LOD of animation evaluation by distance**

- GeckoLib 5 has no LOD, so Nublar implements it in `DinosaurRenderer`: (1) at extraction, store the camera distance (or reuse `query.distance_from_camera` logic) in a ticket; (2) in an override of `applyAnimationControllers`, if the animal is beyond the LOD distance and its countdown is non-zero, copy the 9 floats per bone from a per-entity cache back into the snapshots and decrement; otherwise run the normal `createBoneSnapshots` and store the 9 floats per bone; (3) size the countdown like EMF: distance / 20, divided by (largest box side / 2) for animals over 2 blocks, so a Brachiosaurus keeps detail; (4) never skip inside 32 blocks, where leg IK is active, so near herds stay smooth. Cost: 12 to 17 bones x 9 floats per animal of cache, one array copy on skipped frames. Rating: good. Risk: relies on overriding a `default` method of the internals interface (gap in KQ3); the fallback is a Molang-free `PlayState.PAUSE` far away, which stops the clock but still evaluates keyframes. **B25.**
- Entity-level culling stays vanilla; B09's "culling box follows scaled size" is the one piece Nublar must do, or a 12.5-block Brachiosaurus pops when its 1-block default box leaves the frustum. Aquamirae's per-segment culling is the same idea for very long bodies. **B09, B25. Rating: good.**
- Leg IK already has its own distance rule (16 and 32 blocks); align the animation LOD thresholds with it so one distance query feeds both. **B27.**

**(c) Scaling a model smoothly with growth**

- Set the vanilla `scale` attribute from the growth fraction on the server; GeckoLib 5 reads `entity.getScale()` into the render state and multiplies it into the pose stack with the species base factor from `withScale`; vanilla refreshes dimensions from the same attribute. Per-frame client cost: one multiply. Clip speed by scale: one `setAnimationSpeed` write in the state handler, or `query.scale` in the animation file. Rating: good. Vanilla feel: identical to how vanilla scales babies and the 1.20.5+ scale attribute. **B16, B09.**

**(d) Variant textures in resource packs without code**

- Models and animations: already overridable by path through the vanilla resource manager (GeckoLib loader). Textures: resolve `Identifier`s from `SpeciesData.variants` (id, biome group, texture set) once per species at reload, and pick per animal at extraction from `DinoData`; the bake key includes the variant id so each skin bakes once. Artists add `textures/entity/<species>/<variant>/<gender>/<layer>.png` and one JSON line. EMF's `.properties` random-rule system and ETF dependency are more than Nublar needs and cost a per-entity LRU re-check; a data list plus a reload-time existence scan (as `EMFResourceCaching` does) gives the same artist workflow at zero per-frame cost. Glow masks, if a species ever needs them, follow GeckoLib's `_glowmask.png` convention with no code. **B09, B24. Rating: good.**
