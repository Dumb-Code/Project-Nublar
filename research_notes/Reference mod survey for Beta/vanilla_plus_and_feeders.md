## Key question 1: How Mutant Monsters makes large mobs with complex animations and attack patterns without GeckoLib, and how it is built for 26.x on Fabric plus NeoForge

### Takeaway
Mutant Monsters runs a tiny server-authoritative state machine per mob (one `EntityAnimation` record plus an integer tick, broadcast by index only when it changes) and lets vanilla `Goal` subclasses own each attack: the goal fires its hit, knockback or teleport at an exact tick of the animation. The client is plain vanilla `EntityModel` plus hand-written piecewise sine easing on `ModelPart` angles. Hitboxes are one `AABB` per mob (up to 1.2 by 4.2 blocks); melee reach is a distance plus head-angle cone test around the mob, not a multipart box. The 26.2 build is three modules (Common, Fabric, NeoForge) driven by Fuzs's convention Gradle plugins and Puzzles Lib for lifecycle, events, networking, config and data attachments; only two mixins exist.

- The reusable algorithm for Nublar attacks is: (1) the brain/behaviour chooses an attack and writes `animation` plus `tick = 0` on the server; (2) one packet of (entity id, animation index) goes to tracking players; (3) a dedicated behaviour with the same lifetime as the animation performs the hit at a fixed tick with a distance plus head-angle cone test; (4) the add-entity packet carries (index, tick) so late joiners resume mid-animation; (5) on stop, broadcast NONE. With GeckoLib 5, step 2 can be replaced by reading the synced state in the controller predicate, which costs one synched-data entry instead of a custom packet [inf].
- Hit windows for Nublar bites and tail swings should be a single tick inside the animation, chosen from the exported clip, and should use `bbox.inflate(reach)` plus distance plus cone rather than B27 section parts; B27 parts are for receiving hits, not dealing them [inf].
- Mutant Monsters confirms that a 4.2-block mob works with one AABB and vanilla `GroundPathNavigation` when step height is raised to 1.0 to 1.4 by attribute and the mob is allowed to break leaves and jump when blocked; this is the minimum B26 needs before anything smarter [inf].

## Key question 2: What vanilla-plus changes Vanilla Refresh makes to mobs and animals and how it stays compatible

### Takeaway
Vanilla Refresh is not a Java mod: the repository is a data pack (1,067 `.mcfunction` files, 138 predicates, 222 advancements, 161 tags, zero classes) wrapped with `fabric.mod.json`, `quilt.mod.json` and `lowcodefml` TOML files so it loads from the mods folder. Its mob changes (half-health sprint-jumping baby zombies, 25 to 50 percent trimmed armour on piglins, echo-shard silencing, a mob health action bar, admin wands) are implemented with selectors, scoreboards, tags, predicates, item modifiers and NBT storage toggles; compatibility comes from touching no classes, using `replace: false` tags, per-feature toggles and exclusion tags. Its one transferable engineering lesson is cadence discipline: per-tick work is 44 commands, everything else runs on self-rescheduled 2, 5, 10, 20-tick and 2-minute clocks and is gated by player distance.

### Inferences
- Vanilla Refresh contributes no reusable Java to Project Nublar. It is a model for three disciplines that do transfer: (1) every optional behaviour has a single toggle read at one place (Nublar: Forge Config API Port TOML values read once into fields, not per tick); (2) work is tiered by cadence (every tick, 2, 5, 10, 20 ticks, 2 minutes) with the slow tiers self-scheduling — this is the shape B17 and B25 want for needs decay, sensors and herd logic; (3) foreign entities are left untouched except through tags or memories, with explicit exclusion tags for other mods — this is the right discipline for B20's live-bait feeder holding a vanilla animal [inf].
- The player-distance gates (`if entity @p[distance=..32]`) are cheap for cosmetic features and inappropriate for simulation that must continue (dinosaur needs must tick without players nearby); Nublar should gate only particles, sounds and display work by player proximity [inf].
- Its mob changes conflict with vanilla feel only mildly (opt-in, small numbers); none is a model for dinosaurs beyond "variants chosen once at spawn and recorded by tag" (B09 variants) [inf].

## Key question 3: How the Animal Feeding Trough block feeds animals, as a direct model for Project Nublar's feeders

### Takeaway
The trough is a one-slot `Container` block entity; hoppers insert into it because it is a `Container`, Fabric Transfer and NeoForge item capabilities are registered in two lines each, and a plain one-slot menu opens on right-click. Detection is two-track: every vanilla `Animal` with a `TemptGoal` gets a `SelfFeedGoal` (a vanilla `MoveToBlockGoal` with search radius 8, re-searching every 100 to 200 ticks) injected by one mixin at construction, reusing the tempt food predicate; the five brain-driven animals get a sensor that scans a Manhattan radius 10 (1,561 positions, every 20 ticks) for trough block entities and a behaviour that walks within 2 blocks, removes one item and calls `setInLove(null)`. Breeding is pure vanilla love mode; babies never eat and do not grow faster. There is no config. The copper golem integration shows the cheap way to find block entities: iterate loaded chunks' block-entity maps instead of scanning blocks.

### Inferences
- Detection for B20 should not scan blocks. Three options, cheapest first, all consistent with "no new dependency": (a) iterate `LevelChunk.getBlockEntities().values()` for the chunks within range (the copper golem mixin pattern) every 20 ticks — cost proportional to block entities in 9 to 25 chunks, not to volume; (b) keep a per-`ServerLevel` set of feeder positions maintained by the feeder block entity on load and removal, queried by distance — O(feeders) per query and zero scanning; (c) register the feeder blocks as a vanilla POI type and query `PoiManager` — the vanilla mechanism for beds and job sites, persisted and section-indexed. Option (b) is the simplest to implement and test; option (c) is the most vanilla [inf].
- Memory should store a `GlobalPos` (or `BlockPos`), not the block entity; the eating behaviour re-fetches the block entity at use time and checks `isRemoved`, exactly as the goal track's per-tick re-validation does [inf].
- Intervals: a 20-tick sensor cycle (Animal Feeding Trough) is adequate for walking animals; with option (a) or (b) 100 dinosaurs cost well under a millisecond per tick [inf].
- Eating: one item per eat event, hunger increased by a diet value keyed by `Item` or item tag, a fixed delay for the eat animation (Nublar) instead of instant (Animal Feeding Trough); range check against the same close-enough distance the walk target uses (2.0 to 2.5 blocks for a trough; larger for big-bodied species, computed from the species width) [inf].
- Container: implement vanilla `Container` so hoppers work with no code; the plan's Balm storage covers pipes on both loaders; filter slots with `mayPlace` by diet tag on the Nublar side since the feeder is species-specific, unlike the trough which filters on the eater [inf].
- Fill level as a block-state integer property (0 to 4) updated only on change gives free client visuals without a GeckoLib block animation; keep the GeckoLib open/close animation only if the lead wants it [inf].
- Do not copy the XP-orb magnet: two AABB entity queries per trough per tick is per-tick waste under the Nublar code standards [inf].
- Live-bait feeder (B20): the trough mod never modifies the animal beyond vanilla `setInLove`; Vanilla Refresh's discipline of tagging rather than editing foreign entities suggests the held animal should be marked with a persistent tag or a Nublar memory and released untouched [inf].
