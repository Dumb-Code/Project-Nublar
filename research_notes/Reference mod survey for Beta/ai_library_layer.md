## KQ1. SmartBrainLib 2.x core: brain tick, sensor scheduling, activities and priorities, memory expiry

### Takeaway
SBL 2 replaces the vanilla brain with `SmartBrain`: one mixin ticks it after `Mob.customServerAiStep`; each sensor keeps its own `nextTickTime` and rescans every `scanRate` ticks (default 20) only if `onlyScanIf` passes; behaviours are grouped by integer priority and by `Activity` through `ActivityBuilder` (which replaced `BrainActivityGroup`); memories expire only when set with an expiry (`setMemoryWithExpiry` / `BrainUtil.setForgettableMemory`), otherwise they stay until cleared.

### Inferences
- [inf] Because `onlyScanIf` is evaluated once per `scanRate` period, a sensor gated on "is hungry" costs one predicate call per period while not hungry, which is the cheapest possible gate SBL offers; Nublar's feeder and water sensors should use it.
- [inf] Whether `randomlyDelayStart` actually offsets SBL sensors depends on vanilla `Sensor` internals that SBL's final `tick` does not read (`nextTickTime` is SBL's own field); the changelog claims the offset works. Not verified here because vanilla sources were not inspected (rule: public sources only). If offsets do not apply, all sensors of all dinosaurs spawned in the same tick rescan in the same tick; Nublar can add its own jitter through `scanRate(entity -> base + (entity.getId() % k))`, which the API supports.
- [inf] Priority in SBL is iteration order, not pre-emption; "a travelling follower leaves the line only for a critical need" style exclusivity (Nublar's `HerdNeeds`) must keep being expressed through memory conditions, `startCondition` and `stopIf`, exactly as Nublar does now.
- [inf] The 60-tick default runtime applies to every `ExtendedBehaviour` that does not call `runFor`/`noTimeout`; group behaviours, `DelayedBehaviour`, `HeldBehaviour`, `Panic`, `BreedWithPartner` and `MoveToWalkTarget` set their own.

### Gaps
- No brain-level tick-rate or tick-skipping option exists in SBL 2.0.3 (grep for `tickRate`, `skipTick`, `shouldTick` across `common/src/main/java` found none; the only hits are `randomlyDelayStart`). Reducing brain cost below one pass per tick would need Nublar's own gate around `customServerAiStep` or a vanilla-side change, which was not researched.
- Vanilla `Brain`, `Sensor.randomlyDelayStart` and `EntityGetter` internals were not read (Minecraft is commercial; only public sources were used).

## KQ2. SmartBrainLib 2.x built-in sensors and behaviours that cover Nublar needs

### Takeaway
SBL 2.0.3 ships 24 sensors and about 45 behaviours. For Nublar the directly reusable ones are: `NearbyLivingEntitySensor` (one entity query feeding `NEAREST_LIVING_ENTITIES` and a lazily line-of-sight-cached `NEAREST_VISIBLE_LIVING_ENTITIES`), `NearbyPlayersSensor`, `HurtBySensor`, `ItemTemptingSensor`, `NearestItemSensor`, `NearbyBlocksSensor` (with `onlyScanIf`), `GenericAttackTargetSensor` + `SetAttackTarget` + `InvalidateAttackTarget`, `FollowEntity`/`FollowParent`, `SetRandomWalkTarget` + `MoveToWalkTarget`, `AvoidEntity`/`FleeTarget`, `Panic`, `BreedWithPartner`, `Idle`, the look behaviours and `SmartBrainSchedule.byDaytime`. Nest laying, stamina, scent trails, dominance contests and formation travel have no built-in and stay custom.

## KQ4. SBL 2 performance features, the sensor cost model, and Nublar's 150k-block scan

### Takeaway
SBL 2's performance levers are per-sensor: `scanRate` (fixed or per-entity), `onlyScanIf`, memory-list caching per entity type, zero-memory behaviours, cooldowns and the SBL-side line-of-sight memo. There is no brain tick-rate or tick-skip option. The only built-in block scanner is brute force (`NearbyBlocksSensor`, (2r+w)(2r_y+h)(2r+w) block reads per scan); the only coded "cheap large scan" is `NearestBabyBedSensor`, which queries the vanilla POI spatial index at radius 48 and caps candidates at 5. Nublar's current three block sensors read 147,103 blocks per 20-tick cycle per dinosaur; the same information can be had for under 100 block reads per tick per animal or for none by registering feeders and remembering water.

### Inferences
- [inf] Cost model for one sensor with square radius r (xz) and r_y at rate n on an entity with box w×h: block sensor ≈ (2r + w)(2r_y + h)(2r + w) block reads per scan, so (2r + w)(2r_y + h)(2r + w) / n reads per tick; entity sensor ≈ (sections touched ≈ ((2r / 16) + 1)^2 · ((2r_y / 16) + 1)) section visits plus one predicate per entity in those sections, plus a hash-set insert and one sort of k results, per scan (vanilla stores entities in 16-block sections; not inspected here). Line-of-sight: 0 per scan for `NearbyLivingEntitySensor` (memoised on demand), 1 per candidate item per scan for `NearestItemSensor`.
- [inf] Budget for 100 dinosaurs at 20 TPS: keeping total block reads at or below roughly 5k per tick (50 per animal) is comfortable. - [inf] Feeders (B20) should not be found by scanning at all: a feeder block entity knows its own position, so a per-level registry (the same `WeakHashMap<ServerLevel, …>` pattern as Nublar's `GroupManager.BY_LEVEL`, `GroupManager.java` L34-L36) or a registered POI type lets a sensor answer "nearest feeder within 48" with the `NearestBabyBedSensor` pattern (POI query, 5 candidates, rejected-position memo). - [inf] If `randomlyDelayStart` does not offset SBL timers (KQ1 gap), 100 dinosaurs spawned together will all rescan in the same tick; a per-entity `scanRate(e -> 60 + (e.getId() & 15))` spreads the load with no extra state.

## KQ5. TslatEntityStatus: data, sync, rendering, culling, cost, and reuse for dinosaur status

### Takeaway
TES is client-side first: every client-side `LivingEntity` gets a `TESEntityState` (health, previous health, a 30-tick damage-ghost value, synced potion effects) ticked once per client tick; rendering hooks the 26.2 render-state extraction and `EntityRenderDispatcher.submit` to draw a billboarded bar stack above each rendered living entity that passes a configurable activation rule (default: damaged and within 16 blocks). The server part is optional and only adds potion-effect sync, floating text or number "particles", and a configuration-phase handshake. Nublar can either register one `TESHudElement` that reads its own synced dinosaur data, or copy the pattern (client state + render-state snapshot + billboard text) inside its own GeckoLib layer.

## KQ6. boids: flocking algorithm, neighbour search, tunables, application to movement, cost, herd reuse

### Takeaway
boids 2.0 replaces the whole server AI step of configured mob types (default: salmon, cod, tropical fish) with one velocity update per tick: separation (inverse-distance repulsion inside 2.5 blocks and a 70° cone), alignment (mean of neighbours' normalised velocities inside a 100° cone) and cohesion (vector to the neighbours' mean position inside a 70° cone), weighted 0.6 / 0.4 / 0.4 plus Gaussian noise 0.005, then speed clamped to 0.2-0.3 and the mob turned to face its velocity. Neighbours are the same-type mobs in a 6-block inflated box, re-queried every 40 ticks and pruned of dead ones in between. It is cheap but it cancels `serverAiStep`, so goals, navigation and brains do not run; land dinosaurs need the math as a steering input, not as the mover.

### Cited Findings
- Hook [v]: `MobMixin` injects at `Mob.<init>` tail to enable boids for affected types and at `serverAiStep` HEAD with `cancellable = true`; for an affected mob it cancels vanilla AI, applies `addDeltaMovement(SETTINGS.apply(mob, nearbyMobs.tick()))`, ticks a `StayInWaterGoal` (aquatic types) and a `LimitSpeedAndLookInVelocityDirectionGoal` — [MobMixin.java L33-L74](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/mixin/MobMixin.java#L33-L74). The 1.20.1 line instead cancelled `AbstractSchoolingFish.registerGoals` and added goals (BoidGoal priority 5, StayInWater 3, LimitSpeed 2), so vanilla look/jump controls still ran — [1.20.1 AbstractSchoolingFishMixin.java L23-L35](https://github.com/Tomate0613/boids/blob/0f50dca0d344dc2a1ef6287023e09728679338e7/src/main/java/dev/doublekekse/boids/mixin/AbstractSchoolingFishMixin.java#L23-L35).
- Algorithm [v], `BoidsSimulation.apply(mob, nearby)` per tick: (1) `random` = Gaussian per axis times `randomness`; (2) for each other mob (skip self): `delta = other.pos - self.pos`, `dist = max(1e-5, |delta|)`, `angle = dot(self.lookAngle, normalize(delta))`; (3) if `dist < separationRange` and `angle >= cos(separationAngle)`: `separation += -delta * (1/dist - 1/separationRange)`; (4) if `angle >= cos(alignmentAngle)`: `alignment += normalize(other.velocity)`, count; (5) if `angle >= cos(cohesionAngle)`: `cohesion += other.pos`, count; (6) `alignment /= count`; `cohesion = mean - self.pos`; (7) result = `alignment*alignmentInfluence + separation*separationInfluence + cohesion*cohesionInfluence + random` — [BoidsSimulation.java L26-L77](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/BoidsSimulation.java#L26-L77). Angles are stored as cosines (`degrees()` = cos(radians)) — L22-L24.
- Defaults [v]: separationInfluence 0.6, separationRange 2.5, separationAngle 70°; alignmentInfluence 0.4, alignmentAngle 100°; cohesionInfluence 0.4, cohesionAngle 70°; minSpeed 0.2, maxSpeed 0.3 blocks per tick; randomness 0.005; `defaultEntities` DEFAULT (salmon, cod, tropical fish) or NONE; `includedEntities`, `excludeEntities` by id; json5 file `config/boids.json5` — [BoidsConfig.java L21-L57](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/config/BoidsConfig.java#L21-L57). Loaded at `SERVER_STARTING`; `/boids config reload` needs gamemaster permission — [Boids.java L24-L43, L69-L86](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/Boids.java#L24-L86).
- Neighbour search [v]: `NearbyMobTracker.tick`: a countdown; when it reaches 0 it resets to 40 and runs `level.getEntities(EntityTypeTest.forClass(Mob), box.inflate(6), other -> other.getType() == mob.getType())`; otherwise it only `removeIf(isDeadOrDying)` on the cached list — [NearbyMobTracker.java L20-L36](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/NearbyMobTracker.java#L20-L36). Positions used in the steering are live each tick; only membership is 40 ticks stale.
- Speed and facing [v]: if `|v|² < 0.01` do nothing; else clamp `|v|` into [minSpeed, maxSpeed] and `lookAt(EYES, eyePos + v*3)` — [LimitSpeedAndLookInVelocityDirectionGoal.java L24-L41](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/goals/LimitSpeedAndLookInVelocityDirectionGoal.java#L24-L41). Bounds: `StayInWaterGoal` reads the block 2 above and 1 below and pushes by `max(0.1, |vy|)` toward water — [StayInWaterGoal.java L21-L45](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/goals/StayInWaterGoal.java#L21-L45); `HeightBoundsGoal` pushes toward a min/max Y the same way (unused by the mixin) — [HeightBoundsGoal.java L20-L44](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/goals/HeightBoundsGoal.java#L20-L44).
- 1.20.1 differences [v]: neighbours were `getEntitiesOfClass(mob.getClass(), box.inflate(4))` every 40 ticks (`adjustedTickDelay`), no view cones; separation = plain sum of `-(delta)` for `|delta| < 0.9`; alignment = mean velocity minus own velocity; cohesion = mean position minus own; influences 0.5 / 0.4 / 0.05; speed 0.3-0.8; a random ±0.2 xz kick only when nearly stopped; behaviour disabled itself if the list was empty — [1.20.1 BoidGoal.java L26-L123](https://github.com/Tomate0613/boids/blob/0f50dca0d344dc2a1ef6287023e09728679338e7/src/main/java/dev/doublekekse/boids/goals/BoidGoal.java#L26-L123), [1.20.1 BoidsConfig.java L20-L38](https://github.com/Tomate0613/boids/blob/0f50dca0d344dc2a1ef6287023e09728679338e7/src/main/java/dev/doublekekse/boids/config/BoidsConfig.java#L20-L38).
- Compat [v]: a mixin into Fishing Real's `convertItemStack` disables boids on the converted mob (`@Local Mob`) — [RealFishingMixin.java L17-L23](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/src/main/java/dev/doublekekse/boids/mixin/compat/RealFishingMixin.java#L17-L23).
- README [doc]: "This mod replaces the vanilla fish behavior of flocking fish with a boids simulation" and names the three rules (separation, alignment, cohesion) — [README.md](https://github.com/Tomate0613/boids/blob/dbfd724d9155e29d952a4b90a91bceac851fa5a6/README.md).
- Nublar's herd code today [v]: `GroupManager.bodiesOf` builds one `HerdBodies` snapshot per herd per tick on first use (ids, x, z, width, resting, tight, walking, rank, plus previous positions for velocity) by resolving each member UUID; arrays are reused and grow only when the herd grows — `entity/ai/behaviour/social/GroupManager.java` L92-L109, `HerdBodies.java` L40-L71. `HerdSpacing.away(neighbours)` is an inverse-distance repulsion over members inside the hard minimum — `HerdSpacing.java` L190-L234, `HerdBodies.java` L308-L322. `HerdMoveControl` picks a heading from `ContextSteering` arrays (interest and danger per heading) and feeds the vanilla move control — `HerdMoveControl.java` L187-L201, L685-L850. `JoinGroup` is the only world scan: radius 24 (+ 2 × body width) `EntityRetrievalUtil.getEntities`, every 40 ticks when groupless and 200 ticks in a group — `JoinGroup.java` L44-L46, L73-L77.

### Inferences
- [inf] Per-tick cost of boids per mob: O(k) neighbour iterations with roughly six immutable `Vec3` allocations per neighbour, two block reads (StayInWater), one `lookAt`; one entity box query (radius 6) per 40 ticks. For 100 land dinosaurs this arithmetic is negligible; the real cost in Nublar is elsewhere (pathfinding, block scans).
- [inf] Mapping to B18/B26: Nublar already has the three boids terms in a cheaper form. Separation = `HerdSpacing.away` over `HerdBodies` (no world query); cohesion = vector to the group's spot or centroid (`DinoGroup` spots, `HerdArea`); alignment = the leader's heading or the mean of `HerdBodies` per-tick velocities (already computed for "walking"). The boids cone tests (ignore neighbours behind you for cohesion and separation, wide cone for alignment) are the one idea worth adding: they stop a trailing animal from being pulled backward and make lines form naturally.
- [inf] Avoiding a fight with the navigator: boids 26.2 avoids it by deleting the navigator, which is not an option for B26 (slopes, water, fences). Two safe ways: (a) feed the boids vector as the "interest" direction into `ContextSteering.pick` so the move control, not `addDeltaMovement`, carries it (this is what `HerdMoveControl` already does for formation); (b) apply it only as a lateral offset to the navigation's next node position before `MoveControl.setWantedPosition`, scaled so the per-tick displacement stays below the animal's speed. Direct `addDeltaMovement` on a ground mob fights friction, step-up and the path follower and produces jitter [inf].
- [inf] Cheap neighbour queries for 20-100 animals: the boids pattern (cache the neighbour list for 40 ticks, prune dead each tick) is the right shape for `JoinGroup`-style discovery, but Nublar can do better: `NearbyLivingEntitySensor` already produces `NEAREST_LIVING_ENTITIES` for every dinosaur each period; `JoinGroup` can filter that memory for same-type groupless dinosaurs within 24 blocks and drop its own `getEntities` call. Inside a herd, `HerdBodies` is O(members) UUID lookups per herd per tick with no allocation and is already the cheapest form.
- [inf] Vanilla feel: velocity-driven boids on fish reads as natural; applied to land animals it conflicts with vanilla ground movement unless routed through the move control as above.

### Gaps
- `level.getEntity(UUID)` cost in `GroupManager.resolve` (one lookup per member per herd per tick) was not inspected; if it is a hash lookup it is fine, if it is a scan it is the first thing to measure at 100 animals.

## KQ7. skeleton-ai-fix: the vanilla defect and the targeted-fix pattern

### Takeaway
skeleton-ai-fix removes the vanilla skeleton's strafing and restores distance-scaled reload time without a single mixin: an access widener exposes two vanilla goal fields, and an end-of-entity-tick event handler, gated by an entity-type tag, writes `strafingTime = Integer.MIN_VALUE` and recomputes `minAttackInterval` every tick from a server config. The pattern (tag-gated, config-driven, poke vanilla fields each tick, no goal replacement) is the lowest-conflict way to tune vanilla mobs and is a model for Nublar's villager and illager tweaks.

### Cited Findings
- Fix logic [v]: on `EntityTickEvents.END` (Puzzles Lib), for an `AbstractSkeleton` in tag `skeletonaifix:well_behaved_skeletons`: (1) `bowGoal.strafingTime = Integer.MIN_VALUE` ("disable strafing behavior"); (2) if it has a target: `attackInterval = (difficulty == HARD ? getHardAttackInterval() : getAttackInterval()) × attackIntervalMultiplier`; `minInterval = attackInterval × (1 − distanceScale) + attackInterval × distanceScale × easeOutQuad(min(d² / attackRadiusSqr, 1))`; `bowGoal.setMinAttackInterval(minInterval)`, where `easeOutQuad(x) = 1 − (1 − x)²` — [SkeletonAIFix.java L30-L78](https://github.com/Fuzss/skeleton-ai-fix/blob/7dac096b81519b582d7410649e551050e62ec1d3/Common/src/main/java/fuzs/skeletonaifix/common/SkeletonAIFix.java#L30-L78). Mod description: "Eliminates awkward strafing-Skeletons now stay focused and shoot faster the closer you get" — [gradle.properties](https://github.com/Fuzss/skeleton-ai-fix/blob/7dac096b81519b582d7410649e551050e62ec1d3/gradle.properties) [doc].
- Config [v]: server config `attackIntervalMultiplier` 1.0 (0-4) and `attackIntervalDistanceScale` 0.5 (0-1); comment: vanilla interval is "between 1-2 seconds depending on difficulty" — [ServerConfig.java L7-L23](https://github.com/Fuzss/skeleton-ai-fix/blob/7dac096b81519b582d7410649e551050e62ec1d3/Common/src/main/java/fuzs/skeletonaifix/common/config/ServerConfig.java#L7-L23).
- Access, not mixins [v]: class tweaker makes `AbstractSkeleton.bowGoal`, `getAttackInterval`, `getHardAttackInterval` (also on Bogged and Parched) and `RangedBowAttackGoal.attackRadiusSqr`, `strafingTime` accessible — [skeletonaifix.classtweaker](https://github.com/Fuzss/skeleton-ai-fix/blob/7dac096b81519b582d7410649e551050e62ec1d3/Common/src/main/resources/skeletonaifix.classtweaker). No mixin json exists in the 26.2.x tree [v by `find`].
- Opt-in by data [v]: tag `well_behaved_skeletons` is generated to contain `#minecraft:skeletons` — [ModEntityTypeTagProvider.java L17-L20](https://github.com/Fuzss/skeleton-ai-fix/blob/7dac096b81519b582d7410649e551050e62ec1d3/Common/src/main/java/fuzs/skeletonaifix/common/data/tags/ModEntityTypeTagProvider.java#L17-L20), [ModRegistry.java L9-L15](https://github.com/Fuzss/skeleton-ai-fix/blob/7dac096b81519b582d7410649e551050e62ec1d3/Common/src/main/java/fuzs/skeletonaifix/common/init/ModRegistry.java#L9-L15).
- 1.20.1 line [v]: same design with `LivingEvents.TICK`, hard-coded intervals 40 (hard) and 20 (else), Forge and Fabric directories, and mixin json files present — [1.20.1 SkeletonAIFix.java L31-L80](https://github.com/Fuzss/skeleton-ai-fix/blob/f54d7fac473839b90e333314a7532a48af1a4dcb/Common/src/main/java/fuzs/skeletonaifix/SkeletonAIFix.java#L31-L80).

### Inferences
- [inf] Setting `strafingTime` to `Integer.MIN_VALUE` works because vanilla increments the counter and only strafes once it passes a positive threshold; the fix relies on vanilla's goal code never being replaced, so it coexists with other mods' goal mixins. Cost: one tag test per living entity tick for non-skeletons, a handful of arithmetic operations for skeletons.
- [inf] For Nublar: B21 (paleontologist villagers, Paleo-Illager behaviour) and B25 cleanup can follow this pattern for small vanilla-AI adjustments: access widener (Fabric) / access transformer (NeoForge) in the MultiLoader common module, an entity-type tag so packs can opt mobs in or out, numbers in TOML, applied at the end of the entity tick through the loader's tick event. No `Goal` replacement and no mixin into goal classes. Nublar's own dinosaurs do not need it (they are SBL brains).
- [inf] Vanilla feel: the fix changes vanilla combat balance, which is why it is tag- and config-gated; Nublar should keep the same gates for any vanilla mob tweak.

### Gaps
- Puzzles Lib's `EntityTickEvents.END` implementation (which loader hook it wraps) was not read; the cost statement assumes one callback per entity tick.

## KQ8. Map of findings to Nublar's known problems and Beta modules

### Takeaway
Six of the seven listed problems have a direct remedy in the material above; the seventh (cheap herd neighbour queries) is already solved better in Nublar's uncommitted `HerdBodies` than in boids, and only `JoinGroup` should switch to the SBL memory.

### Cited Findings
- Problem: three block sensors scan ~150k blocks per cycle. Verified total 147,103 reads per 20 ticks per dinosaur (KQ4) [v]. Remedy (B17, B20, B25): `onlyScanIf(need)` + small `detectionRadius` + rate 40-100 on `NearbyBlocksSensor` 2.x; feeders by registry or POI (`NearestBabyBedSensor` pattern); drop `NearbyDinosaurSensor` in favour of `NEAREST_LIVING_ENTITIES`; remove the `System.out` print in `NearestFeederSensor` L68 [v].
