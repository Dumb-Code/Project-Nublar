# Game-AI and Robotics Techniques for Large, Elongated Agents and Herds (fit for a 20-TPS Minecraft block world)

Scope note: public sources only, retrieved 2026-10-09. "Cited Findings" are facts from the linked sources. "Inferences" are my reasoning, and every statement about fit with Minecraft is an inference unless it has a source. The Minecraft background (A* over 1-block cells, one non-rotating square AABB, 20 TPS, herds of up to 20) comes from the task brief, not from a cited source.

## 1. Clearance-based pathfinding for agents of different sizes on grids (Annotated A*, HAA*, clearance maps), and the cost of keeping clearance current in a changing voxel world

### Takeaway
Annotated A* is plain A* plus one extra test: open a tile only if its clearance value is at least the agent's size. Use "true clearance" (the largest free square anchored at the tile), not distance-to-obstacle (Brushfire). Brushfire values wrongly close bottlenecks that a 2x2 agent can pass. HAA* adds a hierarchical abstraction for speed, but the source describes it for static maps. In a changing voxel world, compute clearance on demand or cache it per region and drop the cache on block change.

### Cited Findings
- HAA* (Harabor & Botea, IEEE CIG 2008, "Hierarchical Path Planning with Multi-Size Agents in Heterogenous Environments") uses one abstract graph to plan for agents of different sizes and terrain abilities. The authors report near-optimal paths, an exponential reduction in search effort over low-level search, and a fraction of the gridmap's storage. — [ANU research portal](https://researchportalplus.anu.edu.au/en/publications/hierarchical-path-planning-for-multi-size-agents-in-heterogeneous/); [Harabor publications](https://users.cecs.anu.edu.au/~dharabor/publications.html)
- The AiGameDev article reports HAA* as "an order of magnitude faster than low-level A* search", with near-optimal solutions and little memory overhead. It describes the method for "a static multi-terrain environment". — [Harabor, AiGameDev 2009 (PDF)](https://users.cecs.anu.edu.au/~dharabor/data/papers/harabor-aigamedev09.pdf)
- Brushfire clearance works like this: tiles next to an obstacle get 1, their neighbours get 2, and so on. With square agents, a tile is traversable if its clearance is at least the agent size. Company of Heroes (Relic, GDC 2007, Chris Jurney) used a variant of Brushfire for variable-sized units. — [Harabor, AiGameDev 2009 (PDF)](https://users.cecs.anu.edu.au/~dharabor/data/papers/harabor-aigamedev09.pdf)
- Brushfire (minimum-obstacle-distance) clearance "do[es] not accurately represent the amount of traversable space". A 2x2 agent fails to find a path through a bottleneck it can actually pass. — [Harabor, AiGameDev 2009 (PDF)](https://users.cecs.anu.edu.au/~dharabor/data/papers/harabor-aigamedev09.pdf)
- True clearance: start a 1x1 square on a traversable tile, then expand it down and to the right while every tile inside stays traversable. The clearance value is the final square size. Harabor states that with true clearance the method is complete: it finds a path for any agent size if a path exists. — [Harabor, AiGameDev 2009 (PDF)](https://users.cecs.anu.edu.au/~dharabor/data/papers/harabor-aigamedev09.pdf)
- Annotated A* needs only two changes to A*: pass in the agent size and capability, and open a neighbour only if its clearance (for that capability) is at least the size. Terrain types are handled by one clearance map per capability set. — [Harabor, AiGameDev 2009 (PDF)](https://users.cecs.anu.edu.au/~dharabor/data/papers/harabor-aigamedev09.pdf)
- For memory-constrained cases, the article notes you can "compute true clearance on demand for each tile, thus trading off a little processing" instead of storing an annotation per capability. — [Harabor, AiGameDev 2009 (PDF)](https://users.cecs.anu.edu.au/~dharabor/data/papers/harabor-aigamedev09.pdf)
- The HAA* abstraction divides the map into square clusters. It finds entrances between clusters, picks a transition point per entrance that maximises clearance, and keeps only the edge with the largest clearance among duplicate edges ("strong dominance"). — [Harabor, AiGameDev 2009 (PDF)](https://users.cecs.anu.edu.au/~dharabor/data/papers/harabor-aigamedev09.pdf)
- Vanilla Minecraft: a Mojang bug report states that entity width is applied in two places (pathfinding and path following), and that both are hard-coded to extend only toward positive X and Z. Iron golems (width 1.4) get stuck going north or west on downward stairs. Status: community-reported, not confirmed by Mojang. — [MC-169105](https://bugs.mojang.com/browse/MC-169105)
- A Forge forum user reports that a mob with a 3-block bounding box "will not work well", mainly when chasing toward negative X/Z, and that the vanilla Ravager also has pathfinding trouble. — [Forge forum 159517](https://forums.minecraftforge.net/topic/159517-bad-pathfinding-for-big-mobs-1211/)
- A UW/Microsoft student project reports that the vanilla pathfinder's search cost grows with mob size. — [UW ECE capstone PDF](https://www.ece.uw.edu/wp-content/uploads/2021/05/Microsoft3_Pathfinding_Rocky-Zhenxiang-Fang-Sisir-Kadiveti-Arman-Kazi-Hanze-Simon-Zhang.pdf)
- AzureLib's AzureNavigation (a third-party mod library) replaces the default pathfinder with one that checks the full bounding box instead of only the centre, and sweeps the box along the path. — [AzureNavigation 101](https://moddedmc.wiki/en/project/azurelib/latest/docs/misc/azurenavigation_101)

### Inferences
- Inference (Minecraft fit): "true clearance" maps directly onto the candidate's "path nodes re-centred for box width". Harabor anchors the square at the top-left tile. That anchoring is the same asymmetry MC-169105 describes as a vanilla bug. A symmetric, centre-anchored clearance test (or explicit re-centring of the node by half the box width) removes the direction-dependent failures.
- Inference (cost): an on-demand true-clearance test for an agent of width w costs at most w x w block-state reads per node, times the body height in blocks for 3D. For w = 3 that is 9 reads per layer, which is cheap. For a sauropod-class w = 5 to 7 it is 25 to 49 reads per layer per node. That is still acceptable for one path request every few seconds, but not for every follower every tick. Caching per chunk section, with invalidation on block-update events, is the standard voxel-world approach. I found no published source that measures it for Minecraft.
- Inference: the HAA* hierarchy (cluster entrances) adds the most value on large static maps. Minecraft terrain changes (players break blocks, trees grow, gates open), so keeping the abstraction current adds work. A flat Annotated A* with on-demand clearance, plus a node cap, is the simpler fit. Hierarchy is a later optimisation only if profiling shows long-range paths are the bottleneck.
- Inference: a square clearance value fits Minecraft because the hitbox is a non-rotating square AABB. It does not capture length, so a long animal needs a separate check (see Question 2).

### Gaps
- I did not find a published "true-distance heuristic" paper specific to multi-size agents. The only distance-aware heuristic found is Dolgov's 2D obstacle-aware heuristic (Question 2).
- No measured cost data for clearance maintenance in voxel games.
- I could not read the Company of Heroes GDC 2007 talk (Jurney) itself. Only Harabor's summary of it was available.

## 2. Planning for non-circular, non-holonomic or long agents (Hybrid A*, heading in configuration space, turning radius, turn-in-place vs arcs), and what shipped games do for big creatures

### Takeaway
Hybrid A* searches (x, y, heading). Each discrete cell stores a continuous vehicle state, and nodes are expanded by simulating short arcs. Two admissible heuristics and analytic Reeds-Shepp shots to the goal make it practical. The cost is 50 to 300 ms per replan on a 2008 PC for a 160 m area, which is far above a 50 ms tick budget. So in Minecraft it fits only as a short-horizon local manoeuvre planner (for example, turning around a corner or in a pen), not as the main pathfinder. For shipped games, the only well-sourced pattern is "one navmesh per size class" plus animation-driven locomotion (Horizon Zero Dawn). I found no public technical sources for Monster Hunter, Shadow of the Colossus, ARK, JWE, Planet Zoo or Total War big-creature navigation.

### Cited Findings
- Hybrid A* (Dolgov, Thrun, Montemerlo, Diebel) applies A* to the 3D kinematic state (x, y, theta). Each grid cell has an associated continuous 3D state, so paths are "guaranteed to be drivable", but optimality is not guaranteed because continuous states in the same cell are merged. — [Dolgov et al., "Practical Search Techniques in Path Planning for Autonomous Driving", AAAI workshop 2008 (PDF)](https://cdn.aaai.org/Workshops/2008/WS-08-10/WS08-10-006.pdf)
- Hybrid A* plans forward and reverse motion, with penalties for reversing and for switching direction. — [Dolgov et al. 2008 (PDF)](https://cdn.aaai.org/Workshops/2008/WS-08-10/WS08-10-006.pdf)
- Heuristic 1, "non-holonomic-without-obstacles", is precomputed offline and translated/rotated to the goal. It gave "close to an order-of-magnitude improvement" in nodes expanded over Euclidean distance. Heuristic 2, "holonomic-with-obstacles", is 2D dynamic programming on the obstacle map, and it steers the search away from U-shaped dead ends. The planner uses the max of the two. Example node counts: 21,515 nodes with Euclidean, 1,465 with heuristic 1 in an open case, 68,730 with heuristic 1 in a dead-end case, and 10,588 with both heuristics combined. — [Dolgov et al. 2008 (PDF)](https://cdn.aaai.org/Workshops/2008/WS-08-10/WS08-10-006.pdf)
- Analytic expansion: every Nth node tries an exact Reeds-Shepp curve to the goal and accepts it if collision-free. N decreases as the node gets closer to the goal. — [Dolgov et al. 2008 (PDF)](https://cdn.aaai.org/Workshops/2008/WS-08-10/WS08-10-006.pdf)
- Parameters and cost: a 160 m x 160 m area, 0.5 m x-y resolution, 5 degree heading resolution (72 headings), and typical full replan times (search plus smoothing) of 50 to 300 ms. — [Dolgov et al. 2008 (PDF)](https://cdn.aaai.org/Workshops/2008/WS-08-10/WS08-10-006.pdf)
- The "Voronoi field" path cost pushes the path away from obstacles in open areas. Unlike a plain potential field, it does not block narrow passages. Plain potential fields "create high-potential areas in narrow passages, thereby making those passages effectively untraversable". — [Dolgov et al. 2008 (PDF)](https://cdn.aaai.org/Workshops/2008/WS-08-10/WS08-10-006.pdf)
- The method was validated on Stanford's "Junior" in the 2007 DARPA Urban Challenge (parking lots, U-turns). — [Dolgov ISER 2008 page](https://ai.stanford.edu/~ddolgov/dolgov08gppISER.html)
- Reynolds' vehicle model is a point mass with velocity-aligned orientation. Reynolds notes that it "can turn at zero speed", which real non-holonomic vehicles cannot, and suggests orientation constraints or low-speed lateral limits as fixes. — [Reynolds, "Steering Behaviors for Autonomous Characters", GDC 1999](https://www.red3d.com/cwr/steer/gdc99/)
- Horizon Zero Dawn uses six navmeshes. Four are by character size (small, medium, large, extra-large). The other two are a swimming mesh and a mesh for positioning machines for mounting. Navmeshes are built at runtime only around the player, and "the system recomputes changes in real-time". — [Game Developer, "Behind the AI of Horizon Zero Dawn (Part 2)"](https://www.gamedeveloper.com/design/behind-the-ai-of-horizon-zero-dawn-part-2-)
- In HZD, small rocks and trees are normally impassable. Behemoth, Rockbreaker and Thunderjaw can smash rocks and uproot trees only when angered or chasing. Otherwise they treat them as obstacles. Obstacle cost depends on AI state (patrolling machines avoid stealth grass, but investigating machines walk through it). — [Game Developer, HZD Part 2](https://www.gamedeveloper.com/design/behind-the-ai-of-horizon-zero-dawn-part-2-)
- HZD locomotion is animation-driven. The toolchain "adjusts root bones of animations and warp[s] them" to match the travel distance and timing chosen by navigation and combat. — [Game Developer, HZD Part 2](https://www.gamedeveloper.com/design/behind-the-ai-of-horizon-zero-dawn-part-2-)
- Julian Berteling's GDC 2018 talk covered the move from one human enemy in corridors to 25+ very different characters in an open world, including changes to navigation and animation. — [GDC news, 2018](https://gdconf.com/news/get-inside-look-ai-driving-horizon-zero-dawn-gdc-2018)
- Game AI Pro 360 (Movement and Pathfinding) contains "Animation-Driven Locomotion with Locomotion Planning" (Ciupiński), "Collision Avoidance for Preplanned Locomotion" (Anguelov), and "Steering against Complex Vehicles in Assassin's Creed Syndicate" (Martel). I did not read their content. — [Routledge listing](https://www.routledge.com/products/9780367151133); [Tenlong TOC](https://tenlong.com.tw/products/9780367151133)
- Planet Zoo: Frontier says animals had to traverse player-built terrain naturally, and species are tuned by idle behaviour (zebra and elephants herd). Planet Zoo's character team came from Jurassic World Evolution. No algorithm details are given. — [Game Developer, Planet Zoo simulation design](https://www.gamedeveloper.com/game-platforms/designing-the-simulation-of-the-wild-and-wonderful-i-planet-zoo-i-); [Frontier developer journal](https://forums.frontier.co.uk/threads/developer-journal-how-to-manage-animal-behaviours.513152/)

### Inferences
- Inference (Minecraft fit, cost): a full Hybrid A* over (x, z, heading) multiplies the state space by the number of headings. At 72 headings that is 72 times the nodes of a 2D grid search. With 8 headings (45 degree steps, which match Minecraft's 8-neighbour grid) it is 8 times. Dolgov's 50 to 300 ms per replan is already one to six full server ticks of time, on a smaller search than Minecraft's. Hybrid A* is not suitable as the default pathfinder for 20 herd members.
- Inference: what Hybrid A* gives the candidate hybrid is two ideas, not the full algorithm. (a) Its "holonomic-with-obstacles" 2D heuristic is what vanilla A* already is. So run vanilla-style 2D A* with box clearance first, then (b) validate only the sharp corners with a short (x, z, heading) check of the full body length. This is exactly the candidate's "body-length clearance check only at sharp path corners", and the Dolgov results support it: 2D search finds the corridor, and the expensive heading-aware check runs only where heading matters.
- Inference: turn-in-place vs arcs. Reynolds' model can turn at zero speed, Dolgov's car cannot. Animals are between the two: a theropod or gallimimus can pivot on its feet. Turn-in-place (pivot about the hips, while the swept tail and neck stay inside a checked circle) is much cheaper to plan than arcs, because it needs one swept-circle clearance check (radius = half body length) instead of a heading search. For a sauropod, a full pivot circle may not fit in forests. A short reverse-and-turn manoeuvre (like a 3-point turn, as in Reeds-Shepp) is the fallback. That is the only place a tiny local Hybrid A* (for example a 16 x 16 block window with 8 headings) is worth its cost.
- Inference: the HZD pattern (a navmesh per size class, and destructible obstacles only in aggressive states) maps to Minecraft as size-class clearance thresholds (Question 1) plus an optional "big animal breaks leaves/saplings when enraged" rule. Vanilla Minecraft's Ravager already breaks leaves, and that comes from general knowledge, not a source retrieved here.
- Inference: HZD's animation warping hides small navigation errors visually. Minecraft renders client-side from server positions, so a mod can do the same: render the neck and tail along a smoothed spine even when the server box moves jerkily.

### Gaps
- No public technical sources found for big-creature navigation in Monster Hunter, Shadow of the Colossus, ARK, Jurassic World Evolution, or Total War (formation and large-entity pathing). Searches returned only marketing, player forum posts, or nothing. The report writer should not claim specifics for these games.
- I did not access the Berteling GDC 2018 talk video/slides or the Game AI Pro locomotion chapters' full text.
- Not found: a published turn-in-place planner for long legged creatures in games.

## 3. Crowd and herd avoidance (Reynolds steering/boids, RVO/ORCA, capsule/ellipse agents, formation slots and reassignment, personal space, and deadlock handling at bottlenecks)

### Takeaway
Boids (separation, cohesion, alignment) and leader following are cheap and match the current herd design. Their obstacle probe assumes a sphere, so it underestimates long bodies. ORCA is cheap (a few ms for thousands of agents), but it assumes disc agents and "performs very poorly for anything less than a circle". Extensions exist for ellipses, convex polygons with rotation (RRVO) and capsule-like shapes, but they add cost. For bottlenecks, the most game-proven technique is Pottinger's priority system (units in place get top priority, pushed units inherit the driver's priority and step aside, and units wait). The ORCA literature adds symmetry-breaking (noise or a fixed tie-break) and deadlock detection with a fallback.

### Cited Findings
- Reynolds' separation is a sum of repulsive forces with 1/r weighting from neighbours, chosen by distance and field-of-view angle. Cohesion steers to the neighbours' average position. Alignment matches the average velocity. Flocking blends the three and needs nine parameters (a weight, a distance and an angle for each component). — [Reynolds, GDC 1999](https://www.red3d.com/cwr/steer/gdc99/)
- Reynolds' leader following: arrive at a point slightly behind the leader. A follower that is inside a rectangular zone in front of the leader steers sideways out of the leader's path. Followers use separation among themselves. — [Reynolds, GDC 1999](https://www.red3d.com/cwr/steer/gdc99/)
- Reynolds' obstacle avoidance: an imaginary cylinder projects forward. Its diameter is the bounding-sphere diameter and its length scales with speed. Obstacles are approximated as spheres. Path following treats the path as a spine with a radius (a tube) and corrects only when the predicted position leaves the tube. — [Reynolds, GDC 1999](https://www.red3d.com/cwr/steer/gdc99/)
- Reynolds notes that linear blending of steering forces can cancel out, and that prioritised blending or dithering are alternatives. The neighbour search may be exhaustive or use spatial partitioning. — [Reynolds, GDC 1999](https://www.red3d.com/cwr/steer/gdc99/)
- ORCA gives each agent "half of the responsibility" for avoiding each pairwise collision. Each agent solves a low-dimensional linear program with no communication. The project page reports collision-free actions for dense scenes "in only a few milliseconds", with tests up to 25,000 agents. RVO2 is the open-source C++ library. — [UNC GAMMA ORCA page](https://gamma.cs.unc.edu/ORCA/)
- Classical VO and ORCA assume circular holonomic agents. Inflating the radius to cover a non-circular robot "reduce[s] the capability to plan through narrow passages". — [EPFL RDS paper (PDF)](https://infoscience.epfl.ch/record/284026/files/09385856.pdf), as summarised in search results
- RRVO extends ORCA to any convex polygon and lets agents rotate to avoid each other. Its project page reports that plain ORCA performs very poorly for non-circular shapes. RRVO "does not suffer from as much deadlock". — [RRVO (Parasol Lab)](https://parasollab.web.illinois.edu/research/rrvo/), via search-result summary (the page returned 404 when fetched directly)
- ERVO (Best, Narang, Manocha, ICRA 2016) handles elliptical agents. CTMAT/MATRVO builds tight shapes from arcs and line segments (based on the medial axis). With one tuple per agent it is 1.5 to 2 times slower than circular ORCA and 2 times faster than ERVO. — [Yuexin et al., AAMAS 2018 (PDF)](https://gamma.cs.unc.edu/CTMAT/files/Yuexin_AAMAS_2018.pdf)
- The EPFL RDS method extends velocity obstacles to non-holonomic, non-circular robots, and its figures use a capsule approximation that fits through gaps a same-width circle cannot. — [EPFL RDS (PDF)](https://infoscience.epfl.ch/record/284026/files/09385856.pdf)
- Formations (Pottinger, Age of Empires, 1999): slots are stored as offsets from the formation's orientation. Slots fill from the inside out, and a heuristic (distance, expected collisions, travel time) chooses the unit for each slot. A unit moving to its slot has medium priority. A unit in place has the highest priority so later units cannot dislodge it. — [Pottinger, "Implementing Coordinated Movement"](https://gamedeveloper.com/programming/implementing-coordinated-movement)
- Pottinger on bottlenecks: when a driving unit pushes units in a "stacked canyon", its priority propagates and each pushed unit steps aside. Afterwards, pushed units return in reverse order. Compound collisions are resolved pairwise, highest priority first. Units wait for slower members. — [Pottinger 1999](https://gamedeveloper.com/programming/implementing-coordinated-movement)
- Pottinger on obstacles: scale formation offsets down to fit gaps (this fails for shoulder-to-shoulder lines). Or break the formation, walk around, and reform at the first clear spot. If that spot is far away, "you should just repath your formation". Or split into two halves and rejoin. A shared high-level path is kept on a LIFO path stack with temporary avoidance paths pushed on top. Also: "No matter what you do, units will overlap." — [Pottinger 1999](https://gamedeveloper.com/programming/implementing-coordinated-movement)
- ORCA deadlocks: symmetric configurations and narrow passages cause them. Standard fixes inject noise into the perceived velocity. AVOCADO adapts the noise to collision proximity. — [AVOCADO, arXiv 2407.00507](https://arxiv.org/pdf/2407.00507)
- V-RVO flags a deadlock when an agent is far from its goal but nearly stationary, then holds neighbours and has an agent switch with a neighbour. — [V-RVO, arXiv 2102.13281](https://arxiv.org/pdf/2102.13281)
- ORCA-MAPF detects deadlock when an average-speed buffer drops below a threshold, then switches to a multi-agent path-finding mode, then reverts to ORCA. Its authors report a safety rate going from 15% to 99% in some tests. — [AAAI SoCS paper](https://ojs.aaai.org/index.php/SOCS/article/download/43087/50647/47192), via search-result summary; I did not read the full paper
- A Robotica paper addresses the ORCA deadlock problem in distributed multirobot navigation. — [Robotica](https://www.cambridge.org/core/journals/robotica/article/abs/addressing-the-deadlock-problem-of-the-optimal-reciprocal-collision-avoidance-algorithm-in-distributed-multirobot-navigation/70CEA27CFAE13D30DD3ABCD189F9019D) (abstract-level only)

### Inferences
- Inference (Minecraft fit): the current herd design (leader pathfinds, soft wedge slots, flocking, circle spacing) is a Reynolds leader-following plus Pottinger formation pattern. The research says what it lacks is (1) a slot assignment that adapts, (2) priority rules at bottlenecks, and (3) a non-circular spacing shape.
- Inference: circle spacing on a long animal has the same failure as ORCA with an inflated radius. A circle large enough to cover snout to tail makes the herd spread too wide to pass gaps (wasted space at the flanks). A torso-sized circle lets necks and tails overlap. A snout-to-tail capsule (the candidate's "spine") is the correct shape. The capsule-to-capsule distance is a segment-segment closest-point test (a few dozen floating-point operations), which is trivial at 20 agents (190 pairs).
- Inference: a full ORCA/RVO linear-program solver is not needed for 20 animals at 20 TPS, and it would fight vanilla Minecraft's own entity pushing and collision. Capsule separation (Reynolds-style) plus Pottinger-style priorities is cheaper and simpler. Use ORCA only if testing shows separation forces oscillating head-on.
- Inference (bottleneck rule set for a herd): give each animal a herd rank (leader highest, then by distance along the leader's path). At a corridor, a lower-rank animal yields: it stops or steps aside when a higher-rank animal's capsule is ahead within its forward probe. Break ties by entity ID, which is the deterministic version of the noise/tie-break fix from the ORCA literature. Followers should take slots in single file (slot offsets collapse to a line behind the leader) when the leader's path clearance drops below the herd's width. That is Pottinger's "scale the formation" idea, applied by switching to a line formation, because scaling fails for tight lines.
- Inference: slot reassignment (Pottinger) fixes the observed clustering. When the formation turns, reassign the nearest free slot to each follower (a greedy approach is fine at n = 20) instead of keeping fixed slot IDs. Otherwise followers cross through each other to reach their old slots.

### Gaps
- No public herd-specific deadlock studies for animal games.
- I could not read the RRVO and ERVO full papers, so no cost numbers for those.
- "Personal space" models (for example social-force models) were not researched in depth here.

## 4. Stuck detection and recovery strategies (repath, back up, wiggle, teleport, local unstick)

### Takeaway
The practitioner consensus is: detect "stuck" with progress over a time window (low displacement and near-zero commanded velocity, to avoid false positives while turning). Then escalate: repath, then steer to the next path corner, then nudge/back up, then snap or teleport to the nearest valid point, with a cooldown. Recovery must change the path or the state, not only the position. Agent-to-agent jams (circular dances under RVO) need their own handling. These sources are engine docs, forums and one paper. I found no studio postmortem.

### Cited Findings
- Space Station 14's NPC steering has anti-stuck logic: an NPC that stays in the same spot for a while re-paths. — [SS14 NPCSteeringSystem docs](https://spacestation14.com/space-station-14/api/Content.Server/Content.Server.NPC.Systems.NPCSteeringSystem.html)
- A 2026 arXiv paper treats an agent as stuck only when its position change is below a threshold AND its navmesh velocity is near zero, "to reduce false positives". Recovery moves the agent forward, snaps it to the nearest valid navmesh point, clears the path, and then applies a cooldown to prevent repeated recovery. — [arXiv 2605.01783](https://arxiv.org/pdf/2605.01783)
- A Godot user checks the distance covered since the last periodic check. A door closing mid-route left the NPC pushing against it. — [Godot forum](https://forum.godotengine.org/t/use-of-navigation3d-tools-when-a-character-gets-stuck-en-route-to-its-target-location/140661)
- OpenMW's obstacle handling first checks whether the blocker is a door (and opens it if untrapped). If the blocker is another NPC, it takes an evasive action. — [OpenMW commit](https://git.cijber.net/mirror/openmw/commit/a8bee257572a0ddbf28fcd2449bef5f30f120ca8)
- Practitioner guides recommend repath, nudge off the obstacle, or teleport to the nearest valid navmesh point. For agents jammed on wall corners: seek the next corner of the path, not the final goal. A navmesh that hugs walls too tightly traps agents in corners. Followers should path to a spaced point near the target, not its exact position. These are vendor blogs, weigh them accordingly. — [Bugnet: AI stuck on geometry](https://bugnet.io/blog/how-to-fix-ai-getting-stuck-on-geometry); [Bugnet: stuck in a corner](https://bugnet.io/blog/how-to-fix-ai-agent-stuck-in-a-corner-not-reaching-target); [Bugnet: companion stuck](https://bugnet.io/blog/how-to-fix-companion-or-follower-ai-getting-stuck)
- Roblox case: teleporting a stuck AI back to the start did not help, because it then took the same failing path again. — [Roblox DevForum](https://devforum.roblox.com/t/horror-pathfinding-ai-stuck/1733583)
- Aron Granberg A* Pathfinding Project forum: agents with RVO can end up in a "circular dance" around each other at the end of a path. Other threads report stalls that repathing did not fix. — [A* Pathfinding Project forum](https://forum.arongranberg.com/t/seeker-gets-stuck-for-no-apparent-reason/4054); [RichAI stuck thread](https://forum.arongranberg.com/t/fixed-richais-getting-stuck-when-pathing-in-certain-circumstances-also-funnel-simplification-bug/4285)
- Pottinger's path stack lets temporary avoidance paths sit on top of the main path, and he recommends repathing when the reform point is too far. — [Pottinger 1999](https://gamedeveloper.com/programming/implementing-coordinated-movement)

### Inferences
- Inference (Minecraft fit): a cheap stuck detector costs one distance comparison per animal every N ticks (for example, a 40-tick window). The "and the commanded speed is above zero" condition matters for turn-in-place: an animal that pivots on the spot must not count as stuck.
- Inference: a suggested escalation ladder for the mod, cheapest first: (1) skip to the next path node / corner; (2) repath with a blacklisted node (mark the blocking node as costly for this animal, so the new path differs — the Roblox lesson); (3) back up along the reverse of the last few positions by about half a body length, then turn in place; (4) for followers only, drop out of the formation slot and path straight to the leader's trail; (5) last resort, snap to the nearest position with valid clearance within a few blocks. Add a cooldown on (5) and only allow it while no player is watching (no player within render distance or line of sight — this visibility rule is my design suggestion, not a sourced practice).
- Inference: for trees specifically, the candidate's torso-sized box plus a clearance-aware path should prevent most tree snags. The remaining snags come from followers off the path (formation slots placed inside trunks). So slot positions should also be validated against clearance before a follower targets them. This is the Bugnet "path to a spaced valid point" advice applied to slots.

### Gaps
- No AAA studio postmortem on stuck recovery was found.
- No data on how often each recovery level fires in shipped games.

## 5. Unity NavMesh / Unreal (Recast) approaches to multiple agent sizes and long creatures, and what fails

### Takeaway
Recast/Detour (used by Unreal and the basis of similar systems) bakes the agent radius into the navmesh by eroding walkable space. So the standard answer is one navmesh per size class, with agents bucketed into classes, as HZD did with four size meshes. The radius is a circle, so long creatures still need extra handling. The Detour crowd manager effectively works with one mesh, which makes mixed-size crowds hard. Developers report workarounds such as RVO2 with a custom movement component, or forking the library.

### Cited Findings
- Recast docs: an ogre, a human and a mouse can use different spaces, so it is "often necessary" to build multiple navmeshes for the same environment. Radius and height are the most important agent attributes. — [Recast Navigation docs](https://recastnav.com/md_Docs__1_Introducation.html)
- Recast parameter guidance (as quoted in search results): the radius should be a close median for the agents on that mesh. Agents significantly larger should use a different mesh built with a larger radius. Max slope and max step-up height also matter per agent type. — [Recast Navigation docs](https://recastnav.com/md_Docs__1_Introducation.html); [GameDev.net thread](https://www.gamedev.net/forums/topic/623727-how-do-navmesh-work-with-agents-in-different-sizes/)
- The common approach is a fixed number of size categories, one navmesh each, so that the search itself needs no polygon culling by size. — [GameDev.net thread](https://www.gamedev.net/forums/topic/623727-how-do-navmesh-work-with-agents-in-different-sizes/)
- Unreal: the Detour crowd manager caches one NavMeshData for batch queries, so in practice only one mesh is used. Normal-size agents worked, larger ones did not. Workarounds: RVO2 with a custom movement component, or forking Detour/Recast (the needed methods were not virtual). — [Unreal answers: Detour Crowd with multiple agent sizes](https://answers.unrealengine.com/questions/741862/view.html)
- A developer with two meshes (radius 70 to 150, and a boss mesh at radius 400) reported it got stuck on "Rebuild nav mesh" at startup, and some agents went to wrong positions. — [Unreal forum: multiple navmeshes](https://forums.unrealengine.com/t/ai-multiple-nav-meshes-for-multiple-agents/334486)
- A* Pathfinding Project: one graph per agent size. Dynamic obstacle cuts must be configured per graph, and making progressively larger cuts per size has performance implications. — [Aron Granberg forum](https://forum.arongranberg.com/t/navmeshcuts-not-working-with-agent-radius/13045)
- Horizon Zero Dawn: four size-class navmeshes, built at runtime near the player and updated in real time. — [Game Developer, HZD Part 2](https://www.gamedeveloper.com/design/behind-the-ai-of-horizon-zero-dawn-part-2-)

### Inferences
- Inference (Minecraft fit): Minecraft already searches on the raw voxel grid, so "one navmesh per size class" becomes "one clearance threshold per size class" in the node evaluator (Question 1). The voxel grid has no navmesh build step, so it avoids the Recast rebuild and crowd-manager problems.
- Inference: the engine pattern sizes navigation for the body's width (radius) only. It does not encode length. Long creatures in engines with a radius-only navmesh have the same limitation as a square AABB in Minecraft. This supports the candidate's split: width for the path (the torso box), and length checked separately at corners.
- Inference: bucket the dinosaurs into a few size classes (for example widths 1, 2, 3 and 5 blocks) and share cached clearance results per class. Do not compute clearance per species.

### Gaps
- I did not find official Unity documentation describing failure modes for long (non-circular) agents. Unity's NavMesh agent types are radius-based by general knowledge, but I did not retrieve a source in this session.
- No source describes how any engine handles a creature whose length greatly exceeds its width, other than inflating the radius.

## 6. Which techniques fit a 20-TPS server with 20+ agents in a voxel world, their rough computational cost, and which would most improve or replace the candidate hybrid

### Takeaway
Most of the candidate hybrid has research support. Clearance-thresholded A* (Annotated A*) on a torso-sized box, centre-anchored to avoid MC-169105-style asymmetry; a heading-aware body-length check only at sharp corners (the cheap part of Hybrid A*); capsule/spine spacing instead of circles; and Pottinger-style slot reassignment plus herd-rank priorities at bottlenecks. Add a time-window stuck detector with an escalation ladder. Do not adopt full Hybrid A*, full ORCA/RVO, or HAA* hierarchy as defaults: they cost too much or do not suit a changing voxel world at this scale.

### Cited Findings
- Hybrid A* full replanning took 50 to 300 ms per cycle on a 2008 PC (160 m area, 72 headings). — [Dolgov et al. 2008 (PDF)](https://cdn.aaai.org/Workshops/2008/WS-08-10/WS08-10-006.pdf)
- ORCA computes actions for dense crowds "in only a few milliseconds", with tests up to 25,000 agents. — [UNC GAMMA ORCA](https://gamma.cs.unc.edu/ORCA/)
- MATRVO (non-circular) is 1.5 to 2 times slower than circular ORCA. — [AAMAS 2018 (PDF)](https://gamma.cs.unc.edu/CTMAT/files/Yuexin_AAMAS_2018.pdf)
- Annotated A* adds only a clearance comparison per opened node. True clearance can be computed on demand. — [Harabor, AiGameDev 2009 (PDF)](https://users.cecs.anu.edu.au/~dharabor/data/papers/harabor-aigamedev09.pdf)
- The vanilla Minecraft pathfinder's search cost grows with mob size, and wide-mob width handling is asymmetric (community report). — [UW capstone PDF](https://www.ece.uw.edu/wp-content/uploads/2021/05/Microsoft3_Pathfinding_Rocky-Zhenxiang-Fang-Sisir-Kadiveti-Arman-Kazi-Hanze-Simon-Zhang.pdf); [MC-169105](https://bugs.mojang.com/browse/MC-169105)
- HZD buckets agents into four size classes. Shipped engines (Recast) do the same. — [Game Developer, HZD Part 2](https://www.gamedeveloper.com/design/behind-the-ai-of-horizon-zero-dawn-part-2-); [Recast docs](https://recastnav.com/md_Docs__1_Introducation.html)

### Inferences
All items in this section are inferences about fit and cost. The cost figures are order-of-magnitude estimates, not measurements.

Budget frame: one server tick is 50 ms for everything (worlds, chunks, all entities). A herd of 20 should take a small fraction of that, for example well under 1 ms per tick on average, with path requests spread over ticks.

Fit table (technique, rough per-tick cost for 20 agents, verdict):

| Technique | Rough cost | Fit | Role |
|---|---|---|---|
| Annotated A* / true-clearance test on the torso box (centre-anchored) | +w² block reads per opened node. Only the leader (and stragglers) pathfind, on a cooldown | High | Keep. This is the candidate's "re-centred nodes for box width", made complete per Harabor |
| Size-class buckets + per-chunk-section clearance cache, invalidated on block change | Memory per class. Recompute only dirty sections | Medium (optional) | Add only if profiling shows clearance reads dominate |
| HAA* hierarchy | Abstraction rebuild on terrain change | Low | Skip. Designed for static maps |
| Full Hybrid A* (x, z, heading) | 8 to 72 times the nodes of 2D A*. Dolgov: 50 to 300 ms per replan | Low as default | Replace with a corner-only check |
| Corner-only heading check (swept capsule over the turn) + turn-in-place, with a tiny local (x, z, 8-heading) search as a fallback for sauropods | A few dozen block reads per sharp corner. A local search only when the pivot fails | High | Keep and formalise. This is the cheap half of Hybrid A* |
| Reynolds separation/cohesion/alignment + leader following | O(n²) = 190 pairs at n = 20. Trivial | High | Keep |
| Capsule (snout-to-tail spine) separation instead of circles | Segment-segment distance per pair. Trivial at 190 pairs | High | Keep. Fixes the ORCA-style "inflated circle" problem |
| Full ORCA / RVO2 | LP per agent. Cheap, but discs only and conflicts with vanilla push | Low to medium | Skip unless separation oscillates. If adopted, a capsule variant is needed |
| Pottinger slots: inside-out fill, greedy reassignment on turns, line formation at narrow clearance | O(n²) greedy at turns only | High | Add. Targets the observed clustering and corridor jams |
| Herd-rank priority + deterministic tie-break (entity ID) + yielding at bottlenecks | Per-pair compare | High | Add. Targets corridor and gap deadlocks |
| Time-window stuck detector + escalation (next node, then repath with a penalised node, then back up and pivot, then leave the slot, then snap) with cooldown | One distance compare per agent every N ticks | High | Add |
| Teleport / snap | Negligible | Last resort only | Only while no player is near |

Recommended changes to the candidate hybrid, ranked by expected impact (inference):
1. Make the box-width clearance test symmetric (centre-anchored true clearance) and validate formation slot targets against the same clearance. This targets "stuck on trees and walls" and the asymmetric vanilla width bug.
2. Replace circle spacing with capsule/spine spacing, and add Pottinger-style greedy slot reassignment plus a narrow-clearance line formation. This targets clustering and corridors.
3. Add herd-rank priority with deterministic tie-breaks and yielding at bottlenecks. This targets deadlocks at gaps and corridors.
4. Keep the corner-only body-length check, but implement it as a swept capsule over the turn, with turn-in-place as the first manoeuvre and a tiny local heading search (or a 3-point reverse turn) only for the longest animals.
5. Add a stuck detector and escalation ladder whose recovery changes the path (penalised node), not only the position.
6. Defer HAA*, full Hybrid A* and ORCA. None of them fixes a failure mode that the five changes above leave open at a herd size of 20.

No surveyed technique wholly replaces the candidate hybrid at better cost. The research supports it, with the corrections above.

### Gaps
- No measured Minecraft-specific costs (block-read cost per node, vanilla node cap behaviour for wide mobs) were found in public sources. The cost figures above are estimates and need profiling in the mod.
- No public source covers herds of long-bodied animals through forests in any shipped game. The herd-specific recommendations are synthesis from RTS formation and crowd-robotics work, not from a direct precedent.
