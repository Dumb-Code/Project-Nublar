## Navigation: node evaluator, navigator, move control, turning and stuck handling

### Takeaway
Dinosaurs use a vanilla `GroundPathNavigation` subclass whose `WalkNodeEvaluator` subclass adds electric-fence typing and a herd-only clearance-box test at each node's standing position; there is no node re-centring beyond vanilla's own `node + floor(width+1)/2`, no full-body swept check between nodes, and no turn-before-move logic: the body turns at most 10 degrees per tick (a global `setYRot` clamp) while vanilla `MoveControl` already applies forward input, and a per-tick "guard" zeroes the speed when the box 0.6 blocks ahead along the actual yaw does not fit. H2, H3 and H4 are all absent today; the guard is the only thing that ever stops a turning body, and it does so as a hard stop, not a planned turn.

### Cited Findings
**Navigator and evaluator**
- Every dinosaur's navigation is `FenceAwareNavigation` — [DINO/Dinosaur.java:470-472](common/src/main/java/net/dumbcode/projectnublar/entity/dinosaur/Dinosaur.java). It extends vanilla `GroundPathNavigation`, installs `FenceAwareNodeEvaluator` and `setCanPassDoors(true)` in `createPathFinder` — [AI/FenceAwareNavigation.java:10-21](common/src/main/java/net/dumbcode/projectnublar/entity/ai/FenceAwareNavigation.java). No other override (no `followThePath`, `canMoveDirectly`, `getTempMobPos`, stuck-detection or waypoint-distance override).
- `FenceAwareNodeEvaluator extends WalkNodeEvaluator` — [AI/FenceAwareNodeEvaluator.java:35](common/src/main/java/net/dumbcode/projectnublar/entity/ai/FenceAwareNodeEvaluator.java). Two changes (Javadoc :16-34): (1) electric fence posts and wire type as `BlockPathTypes.FENCE` unless all the animal's needs are zero, then `OPEN` (:76-90); (2) for a herd member, a node vanilla accepted (malus >= 0) becomes `BLOCKED` if the member's clearance box does not fit at the node's standing position (:59-68).
- The box probe is created once per path in `prepare` and dropped in `done` (:42-53); it is `null` (no box test) for solo animals or animals with an attack target, via `HerdSpacing.applies` — [SOC/BodyFit.java:157-167](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/BodyFit.java), [SOC/HerdSpacing.java:47-49](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/HerdSpacing.java).
- "Box-aware node": `PathProbe.fitsAt` tests the box at `ClearanceBox.nodeCentre(node, hitboxWidth)` with feet at the computed rest height, reading through the path's region — [SOC/BodyFit.java:142-148](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/BodyFit.java). `nodeCentre = node + floor(width + 1) * 0.5`, documented as reproducing vanilla `Path.getEntityPosAtNode` (a 1.2-wide Gallimimus stands a whole block past the node) — [SOC/ClearanceBox.java:88-96](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/ClearanceBox.java); covered by `nodeCentreIsWhereVanillaWalksTheBody` — [TEST/ClearanceBoxTest.java:76](common/src/test/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/ClearanceBoxTest.java).
- Only the node standing positions are tested, not the body between nodes: "The investigation found no inconsistency between the path node test and the guard at the node centres themselves … The inconsistency is between the node centres and where vanilla actually puts the body between them" — [LEDGER/playtest2-geometry-investigation.md:31-35](.superpowers/sdd/2026-10-08-herd-movement-redesign/playtest2-geometry-investigation.md).
- Vanilla path-following behaviour as recorded by the worktree's own investigation (it was obtained earlier by inspecting the game jar, which the ledger flags for the lead's review — [LEDGER/progress.md:287](.superpowers/sdd/2026-10-08-herd-movement-redesign/progress.md)): `maxDistanceToWaypoint = bbWidth / 2 = 0.6` measured from `node + 0.5` while the body is driven to `node + 1.0`, so a body counts as on the node up to 1.1 blocks off the node line; corner cutting is allowed on WALKABLE/OPEN; on a 90-degree turn the box corner sweeps an inner-corner column no footprint covered, "typically the trunk the path is turning around" — [LEDGER/playtest2-geometry-investigation.md:89-125](.superpowers/sdd/2026-10-08-herd-movement-redesign/playtest2-geometry-investigation.md).
- The 2-wide-gap arithmetic: on a path the guard tolerates about +-0.2 blocks of lateral error at a gap entrance against vanilla's 0.6-1.1 of slop — [LEDGER/playtest2-geometry-investigation.md:119-125](.superpowers/sdd/2026-10-08-herd-movement-redesign/playtest2-geometry-investigation.md).

**Move control and steering**
- Every dinosaur's move control is `HerdMoveControl` (installed in the constructor), with vanilla pushing left on as a backstop — [DINO/Dinosaur.java:147-151](common/src/main/java/net/dumbcode/projectnublar/entity/dinosaur/Dinosaur.java). Step height is 1.0 via `setMaxUpStep(1.0F)` (:147).
- `HerdMoveControl extends MoveControl` — [SOC/HerdMoveControl.java:64](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/HerdMoveControl.java). Modes in its Javadoc (:18-63): Stop, Steer (12-heading context steering every 2+ ticks), Path (navigation always wins), Unstack, Side step / make way, Ghosting on fallback paths.
- `tick()` order: path in progress cancels steering (:595-600); herd layer runs (refresh tight ground, unstack, side step or `moveToward`) (:604-613); then `super.tick()` (vanilla MoveControl turns the body and sets forward input) (:614); then `guard`, `makeWay`, `holdPath` (:615-623) — [SOC/HerdMoveControl.java:590-647](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/HerdMoveControl.java).
- Steering sets a wanted position `WANTED_AHEAD = 2.0` blocks along the chosen heading (:84, :726-727); headings are scored by `ContextSteering.interest` = cosine minus `TURN_COST_PER_DEGREE` (0.002) per degree beyond one tick's turn — [SOC/ContextSteering.java:16-22, 110-117](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/ContextSteering.java). Probes: 1 block (mask), 2 (mask), 3 (danger) ahead along the heading from the body centre (`PROBE_NEAR/MID/FAR` :72-74). Probes are box placements along a line from the body's current position; they do not sweep the turning arc.
- The guard: if forward input > 0, test the box `GUARD_AHEAD = 0.6` ahead along the **actual yaw**; if it does not fit (or enters a herd mate's hard minimum), `setSpeed(0)` and keep 20% of horizontal velocity — [SOC/HerdMoveControl.java:837-875](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/HerdMoveControl.java), constants :69-71.
- Turn rate: `Dinosaur.MAX_TURN_PER_TICK = 10F` — [DINO/Dinosaur.java:115](common/src/main/java/net/dumbcode/projectnublar/entity/dinosaur/Dinosaur.java); enforced by overriding `setYRot` to clamp every yaw change to +-10 degrees — [DINO/Dinosaur.java:500-516](common/src/main/java/net/dumbcode/projectnublar/entity/dinosaur/Dinosaur.java). Head turn speed is 2 (`getHeadRotSpeed`, :481-483). Vanilla MoveControl turns with `rotlerp(..., 90)`, which the clamp cuts to 10 — [LEDGER/playtest2-geometry-investigation.md:110-112](.superpowers/sdd/2026-10-08-herd-movement-redesign/playtest2-geometry-investigation.md).
- Turn-before-move: none. The only yaw-alignment checks are diagnostic: `ContextSteering.walksHeading` (yaw within 15 degrees of the heading) decides whether a guard stop masks the heading (`guard`, :862-868), and `ContextSteering.facesDirection` excludes turning ticks from the path-hold count (`holdPath`, :908-929) — [SOC/ContextSteering.java:219-236](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/ContextSteering.java). **Stuck handling**

- Fallback paths are requested by setting `WALK_TARGET` (SmartBrainLib `MoveToWalkTarget` then calls vanilla navigation) — [SOC/FollowFormation.java:564-572](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/FollowFormation.java).

- Members on a fallback path "ghost": herd mates do not stop them; vanilla pushing separates bodies — [SOC/HerdMoveControl.java:36-38](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/HerdMoveControl.java).

### Inferences
- H1 (torso main box for collision and pathing): for Gallimimus this is already roughly the case for vanilla collision and pathing (hitbox 1.2 x 2.6, model 0.69 wide). The real "box" problem is the herd `ClearanceBox` (width = max(hitbox, model width), height = max(hitbox, model top) + 0.25), which the evaluator and the guard both use. For Brachiosaurus and Triceratops the clearance box (about 3.5 wide; 19.5 and 6.25 high, computed from [SOC/ClearanceBox.java:40-75](common/src/main/java/net/dumbcode/projectnublar/entity/ai/behaviour/social/ClearanceBox.java)) is far larger than the 2 x 3 hitbox, so H1 for those species is a decision to drop or shrink the model-derived clearance box, not to change `EntityInit`.
- H2 (re-centre node targets): vanilla already offsets the target by floor(width+1)/2; what is not centred is the acceptance window (`node + 0.5`, radius 0.6) and the corner chord. H2 would need a `GroundPathNavigation` override of path following (waypoint reached test and/or the temp target position) in `FenceAwareNavigation`, which today overrides only `createPathFinder`. With a box narrower than 1.0 (footprint 1 column), vanilla's own centre is node + 0.5 and the window mismatch largely disappears; this is the cheaper form of H2 for Gallimimus.
- H3 (turn in place): fits cleanly into `HerdMoveControl.tick` after `super.tick()`, where the guard already zeroes speed; a rule "if tight ground (already measured, `tightGround`, :462-464) and |yaw - target heading| > N degrees, set speed 0 until aligned" reuses existing state. It would also remove the cause-4 pattern (guard firing on the turning arc). The global `setYRot` clamp applies to every caller of `setYRot`, including vanilla repositioning; whether it delays yaw after teleport/load was not checked.
- H4 (body-length clearance at sharp corners): nothing comparable exists; `PathProbe.fitsAt` tests only an axis-aligned box at one point. A corner check would naturally live in `FenceAwareNodeEvaluator` (neighbour generation, comparing parent and child direction) or in a post-pass over the `Path` in `FenceAwareNavigation.createPath`, reading blocks through `BodyFit` (the spec makes `BodyFit` the only herd block reader — [docs/superpowers/specs/2026-10-08-herd-movement-redesign.md:147](docs/superpowers/specs/2026-10-08-herd-movement-redesign.md)).

### Gaps
- Whether vanilla 26.2 `PathNavigation.followThePath`, `Path.getEntityPosAtNode` and the waypoint distance rule are unchanged since 1.20.1: no public source found (decompiled-source viewers were deliberately not used).

## Spacing: HerdSpacing circles, side-stepping, personal space, and where a capsule would go

### Takeaway
All herd spacing is centre-to-centre circle distance built from `getBbWidth()` (half of each width plus a gap of 1.0, or 0.5 when resting or in tight ground), used by masks, guard, unstack, side-step, passage test and herd radius through one function, `HerdSpacing.hardMinimum`, called from `HerdBodies.minimum`. That single choke point is where a spine/capsule distance would replace the circle, but the pure tests and several geometry derivations (tight-ground threshold, herd radius, travel slots) assume circle distances.

### Inferences
- Replacement point for H5: `HerdSpacing.hardMinimum` / `HerdBodies.minimum` become a segment-to-segment distance test; `HerdBodies` must also carry each member's yaw and spine (front and back offsets, radius), and `wouldCrowd` / `stepCrowds` / `freeDistance` / `away` must use closest points on segments rather than centres. `blockerAt` would test the walker's own moved capsule, not a point 0.6 ahead.
- Scale of the change: a Gallimimus is about 6.1 blocks long and 0.69 wide (see Models). Today two members in single file 2.2 apart centre-to-centre overlap visually by roughly 3.9 blocks (snout 3.18 ahead of one centre vs. tail 2.95 behind the other). A capsule with a 1.0 gap would push in-line spacing toward about 7 blocks while side-by-side spacing could fall to about 1.7. Travel slot spacing (5 / 4), herd radius, graze spacing and the tight-ground threshold were all tuned on circles and would need re-deriving; `HerdSpacingTest` expectations change accordingly.
- Head-on and side-step logic stays geometrically valid (perpendicular to the walker's line), but "clear of the line" must become "capsule clear of the walker's swept capsule".

### Gaps
- No measurement exists in the worktree of how often jams are mate-to-mate vs. terrain after the P8 fixes; playtest 3 results are not recorded in the ledger (last entry: client launched, [LEDGER/progress.md:324](.superpowers/sdd/2026-10-08-herd-movement-redesign/progress.md)).

## Hitboxes: EntityDimensions per species, growth scaling, the spec's Task 22, and the dead T. rex head part

### Takeaway
Hitboxes are fixed per `EntityType` in `EntityInit` (only Gallimimus was changed, to 1.2 x 2.6); `Dinosaur` does not override `getDimensions` or call `refreshDimensions` (T. rex calls it every tick), so growth stages change the rendered model (0.25/0.5/0.75/1) but not the hitbox, apart from whatever vanilla's baby scale does. The T. rex head part is dead: `resetParts` is never called, so `head` stays null, and the head position it would read is written only by client renderers.

### Inferences
- Growth vs hitbox: since nothing in the mod scales dimensions, the hitbox is the type size at every stage, except for vanilla's baby scaling. From public knowledge of 1.20.1 (not verified here), `LivingEntity` scales dimensions by 0.5 while `isBaby()`, refreshed when vanilla's baby data flag changes at age crossing 0. With the mod's `isBaby()` = age <= -18000, juveniles and sub-adults could keep a half-size hitbox until adulthood, while T. rex (refreshing every tick) would switch at the baby/juvenile boundary. This should be checked in game with F3+B before any spine is scaled by growth stage.
- `ClearanceBox` growth math differs from the renderers for species whose adult scale C is not 1: renderer scale = (C + g/100) x f, box = C x (1 + g/100) x f. Brachiosaurus at gene +10% renders at 2.6 but the box assumes 2.75. A shared per-species "render scale" function would be needed before H5/H6 spines can match the model.
- H1 needs no `EntityInit` change for Gallimimus; for the large herbivores the lead has twice chosen not to enlarge hitboxes, which fits H1's "torso-sized vanilla box" direction. Using the spine (H5/H6) for length and a torso box for terrain is consistent with the spec's statement that length is not in the box.
- H6 replaces, rather than reuses, the current part code. Nothing working exists to preserve.

- Exact vanilla baby-dimension behaviour for these entities was not verified (no public source fetched; local game files are off-limits).

### Inferences
- Spine sampling for H5/H6: a 3-to-5-point polyline per species (snout tip, head pivot, neck base, hips, tail mid, tail tip) in rest pose, rotated by body yaw and scaled by C x growth factor (+ gene), is enough for spacing and coarse hit sections. Rest-pose offsets ignore animation (neck dip while grazing, tail sway), which matters little for spacing but would put hit sections off the visible head during eating or roaring animations.
- Brachiosaurus's neck is nearly vertical: its horizontal spine is hips/tail-dominated (tail 11.7 behind vs. 5.7 ahead), so a horizontal capsule centred on the entity origin is badly off-centre; the spine must be asymmetric front/back, not a symmetric capsule of half-length L/2.
- Length/width ratios (6.13/1.2 = 5.1 Gallimimus; 10.87/1.0 = 10.9 T. rex; 13.11/2 = 6.6 Triceratops; 17.41/2 = 8.7 Brachiosaurus) show why turning in place (H3) sweeps a large circle: an adult Gallimimus turning about its centre sweeps a radius of about 3.2 blocks; an adult Brachiosaurus about 11.7 (its tail). H3 "turn in place" therefore only removes the forward chord, not the tail sweep; H4 would need to check the sweep at corners.

### Gaps
- Bone pivots in Bedrock geo are in the model's own space with the entity origin at (0,0,0); I did not verify GeckoLib's exact yaw convention (which of −z/+z maps to the entity's look direction) from a public source. The head bones are at −z in every model, which is the usual Blockbench "north = front" convention.
- Velociraptor and Dilophosaurus spines were not tabulated (not herd species in the current work).

### Inferences

This is also the natural home for H4.
- H2 depends on overriding `PathNavigation` path following; that code was not verified for 26.2 and is the riskiest vanilla-coupled piece of the hybrid. H3 (inside `HerdMoveControl.tick`) and H5 (pure geometry in `HerdSpacing`/`HerdBodies`) carry little port risk.
- `Dinosaur.setYRot` clamp and `getHeadRotSpeed` are plain vanilla overrides; low risk, but should be re-checked against 26.2 signatures.
- H6 on GeckoLib 5: a GeckoLib model is a client resource and v5 renderers do not hand the entity to `scaleModelForRender`, so the current pattern (renderer writes `DINOSAUR_HEAD_POS` into synced entity data) cannot be ported as is and never worked on the server anyway. A server-authoritative spine must come from per-species data (offsets from the geo files, scaled by the same render-scale function on both sides), not from live bones. This matches the earlier report's finding that MoreHitboxes uses fixed offsets on the server.
- H6 on loaders: NeoForge parts (`PartEntity` with `getParts()`) are unspawned and parent-driven, a better base than the current spawned Ice-and-Fire-style `PartEntity` with UUID re-rolls. Fabric needs a custom solution (for example per-section AABB checks in the dinosaur's own hit/ray logic, or a mixin into entity lookup), which doubles the H6 work and the test surface. H5 needs no loader API.
- GeckoLib Fabric builds for 26.2 trail NeoForge by one patch release (5.5.5 vs 5.5.6) as of the Modrinth data; pinning one version across both loaders avoids divergence.

### Gaps
- No public 26.2 source was found for `PathNavigation.followThePath`, `Path.getEntityPosAtNode`, `MoveControl.tick` or `GroundPathNavigation` (mappings.dev has no 26.x pages; decompiled-source viewers were not used to respect the no-reverse-engineering rule). Whether the waypoint window and corner-cutting rules changed since 1.20.1 is unknown.
- Whether 26.2 entity dimensions for babies use a `scale` attribute or an age scale, and how `refreshDimensions` is triggered, was not verified.
- GeckoLib 5's server-side model or bone availability was not confirmed from GeckoLib's own documentation (wiki.geckolib.com not fetched); the inference rests on the renderer API and the earlier report.
- No Fabric multipart library for 26.x was researched.
