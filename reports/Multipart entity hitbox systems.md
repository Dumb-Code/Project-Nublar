# Multipart hitboxes fix hits, not herd jams

> **Superseded on 2026-10-10** by [Dinosaur hitboxes and movement design.md](Dinosaur%20hitboxes%20and%20movement%20design.md). That page holds the current design and the lead's decisions. This page stays as history. Some of its claims are wrong or replaced. The corrections log in the new page lists them.

No. A T. rex-style multipart hitbox system synced to animation and rotation would not largely fix the herd getting stuck in gaps and corridors. In every system studied, parts are **hit-detection ghosts**. This covers the vanilla Ender Dragon, Forge/NeoForge `PartEntity`, Ice and Fire, Alex's Mobs, Alex's Caves, Fossils with MoreHitboxes, Countered's Accurate Hitboxes and the original Project Nublar. Parts never collide with blocks and never enter pathfinding. Movement and A* use the single main box. Mowzie's Mobs has no parts at all. Only CustomHitboxLib makes parts collide, and even it still plans paths with the main box width. It also cancels any turn that would push a part into a block, and its own FAQ warns that colliding parts confuse the pathfinder. A multipart system fixes the other half of the "hitbox problem": players and arrows hitting the visible head and tail, bite reach, render culling and rider seats. The stuck-herd fix belongs in the navigator and in herd-mate spacing. Three changes help there: width-aware path following with centred nodes, size-aware passability checks, and an oriented capsule along the body axis instead of an axis-aligned box. For hit detection, MoreHitboxes 1.20.1 (MIT, used by Fossils) fits Project Nublar's Forge 1.20.1 and GeckoLib stack best. It follows bones only on the client, though. The server always uses the rest pose, and no studied mod except the original DumbLibrary-era Project Nublar poses models on the server. Project Nublar's current T. rex head part is dead code: nothing ever creates it. If it were turned on, it would sit at world coordinates (0, 0, 0) on the server. It should be removed before any of these options goes in.

## Every mature system keeps parts out of movement

The systems studied fall into four designs. The dominant one is the **unspawned part held in the parent's array**. Vanilla's dragon owns 8 `EnderDragonPart` objects that are never added to the world, never saved and never sent as entities. Both sides place them each tick from the dragon's position and a 64-entry yaw/Y history ([V EnderDragon.java](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L90-L105)). Forge generalises this design as `PartEntity` plus `isMultipartEntity()`/`getParts()`, and keeps a per-level part map so that `Level.getEntities` finds parts. Forge does **not** sync part IDs or positions, save parts, or give them block collision ([F IForgeEntity.java](https://github.com/MinecraftForge/MinecraftForge/blob/0ec923d7307eb15bef70d6916329642b733a21ed/src/main/java/net/minecraftforge/common/extensions/IForgeEntity.java#L183-L207); [F Level.java.patch](https://github.com/MinecraftForge/MinecraftForge/blob/0ec923d7307eb15bef70d6916329642b733a21ed/patches/minecraft/net/minecraft/world/level/Level.java.patch#L161-L200)). Alex's Caves, Alex's Mobs' cachalot, MoreHitboxes and CustomHitboxLib all build on this design. Citadel 1.21 adds no multipart API at all ([Citadel 1.21 tree](https://github.com/AlexModGuy/Citadel/tree/1.21/src/main/java/com/github/alexthe666/citadel)).

The second design makes **every part a real, tracked, saved entity**. Ice and Fire does this with `EntityMutlipartPart extends Entity`, spawned with `addFreshEntity` and linked to its parent by UUID ([IaF EntityUtil.java](https://github.com/AlexModGuy/Ice_and_Fire/blob/0526aad94119b705a86207623481b087c4d052ca/src/main/java/com/github/alexthe666/iceandfire/entity/util/EntityUtil.java#L15-L38)). Alex's Mobs uses the same design for its anaconda, centipede and void worm segments, and the original Project Nublar used one real entity per model cube, 15 to 17 per adult dinosaur ([PN master Tyrannosaurus.java](https://github.com/Dumb-Code/ProjectNublar/blob/e525ed7b69aaaa9de5234de9875f50d3822a25af/src/main/java/net/dumbcode/projectnublar/server/dinosaur/Tyrannosaurus.java#L56-L62)). This design has the longest bug record, covered below. The third design is **no parts at all**: Mowzie's Mobs gives each boss one vanilla box. Body regions are rules inside `hurt()`, such as the Wroughtnaut's 220° frontal armour arc ([MM EntityWroughtnaut.java](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/entity/wroughtnaut/EntityWroughtnaut.java#L183-L207)). The fourth is **render-time virtual geometry**. Countered's Accurate Hitboxes 1.0.1 turns each vanilla `ModelPart` cuboid into world-space triangles on the client. It then replaces one raycast function, so only the client crosshair benefits ([Countered ModProjectileUtilMixin.java](https://github.com/Coun7ered/countereds-accurate-hitboxes-template-1.21.1/blob/711b0b561b5d7f0dd703a9a430bdb0c112e919a9/src/main/java/net/countered/counteredsaccuratehitboxes/mixin/server/ModProjectileUtilMixin.java)).

## Animation sync stops at the server boundary

How a mod positions its parts decides whether the server and the client agree on where the hitboxes are. **Procedural placement on both sides** is the most robust approach. The dragon, Alex's Mobs' cachalot and Alex's Caves all run the same deterministic function on each side, using inputs that vanilla already syncs: position, yaw, head yaw, animation ID and tick. No part data crosses the network. Alex's Caves pushes this furthest. Its sauropod neck and tail parts follow a 128-entry yaw ring buffer and per-animation target angles, for example −140° neck pitch during ROAR and ±70° tail yaw during whips. The client model then reads its neck and tail bone rotations **from the part positions**, which reverses the usual direction ([AC SauropodBaseEntity.java](https://github.com/AlexModGuy/AlexsCaves/blob/1.21.1/src/main/java/com/github/alexmodguy/alexscaves/server/entity/living/SauropodBaseEntity.java#L247-L305); [AC SauropodBaseModel.java](https://github.com/AlexModGuy/AlexsCaves/blob/1.21.1/src/main/java/com/github/alexmodguy/alexscaves/client/model/SauropodBaseModel.java#L432-L461)). The cost is fidelity. The hitboxes match the animation only as well as the hand-tuned targets copy the keyframes, and legs and jaw get no boxes.

**Client bone capture** gives the best visual match but no server truth. MoreHitboxes reads `bone.getLocalPosition()` inside GeckoLib's `renderRecursively`, once per game tick, and stores it as a part "override". On the server, which never renders, it falls back to the static JSON offset rotated by `yBodyRot` and scaled by `getScale()` ([MH21 MultiPart.java](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/common/src/main/java/com/github/darkpred/morehitboxes/api/MultiPart.java#L43-L64); [MH21 GeoEntityRendererMixin.java](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/common/src/main/java/com/github/darkpred/morehitboxes/mixin/GeoEntityRendererMixin.java#L23-L52)). The two sides therefore **disagree whenever an animation moves a hitbox bone**, for example a lowered drinking head, a sleeping pose or a tail swing. Player melee follows the client's animated boxes, because the client sends the part ID. Arrows, explosions and AI queries on the server hit the rest-pose boxes. The override is never cleared, so an off-screen mob keeps a stale pose on the client. Only position and scale come from the bone. Bone rotation is ignored, and each box stays axis-aligned; the author's own wiki says the rotation "has no effect on the actual hitbox in game" ([MoreHitboxes wiki](https://github.com/DarkPred/MoreHitboxes/wiki/Blockbench-plugin)). Mowzie's Mobs captures bones the same way but uses them only for particles. Its gameplay uses hard-coded mouth offsets rotated by yaw ([MM EntityFrostmaw.java](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/entity/frostmaw/EntityFrostmaw.java#L366-L390)). Countered's captures vanilla `ModelPart`s only, so GeckoLib dinosaurs fall back to the vanilla box. This is an inference from GeckoLib's renderer hierarchy and was not tested.

**Server-side posing** appears in only one studied codebase: Project Nublar's own predecessor. DumbLibrary loaded the Tabula `.tbl` (1.12) or DumbCode Studio `.dcm` (1.16) model on the server. The server re-posed it every 3 ticks in 1.12, or every 5 ticks with a 0.25 s step in 1.16. Each part became the bounding box of one animated cube's 8 corners, rotated by yaw ([PN master MultipartSystem.java](https://github.com/Dumb-Code/ProjectNublar/blob/e525ed7b69aaaa9de5234de9875f50d3822a25af/src/main/java/net/dumbcode/projectnublar/server/entity/system/impl/MultipartSystem.java#L52-L133); [DL master AnimationComponent.java](https://github.com/Dumb-Code/DumbLibrary/blob/791ada6afea65e284e4f9e534dd64b15a1815afe/src/main/java/net/dumbcode/dumblibrary/server/ecs/component/impl/AnimationComponent.java#L144-L160)). The team turned the server animation off in March 2022 and back on at a lower rate in April 2022 ([commit 6d32dd27](https://github.com/Dumb-Code/ProjectNublar/commit/6d32dd27); [commit c24f8ce3](https://github.com/Dumb-Code/ProjectNublar/commit/c24f8ce3)). That churn is the only public evidence of what server posing costs in practice. GeckoLib has no server-side bone pose, so reviving this approach means writing the evaluator.

**Part IDs and damage routing are where most bugs live.** A Forge `PartEntity` takes a fresh entity-counter ID on each side, and Forge does not align them. The client therefore sends attack packets with part IDs the server cannot resolve. Vanilla's own dragon gets this wrong by one: [MC-158205](https://mojira.dev/MC-158205) made dragon melee unreliable from 1.14.4 until 24w44a, after 1.20.1. Mods work around this in three ways. MoreHitboxes uses a `setId` mixin that sets each part's ID to `parentId + i + 1` on both sides, so vanilla packets resolve correctly ([MH EntityMixin.java](https://github.com/DarkPred/MoreHitboxes/blob/012edbb4258120161c96103e51dac6374b78cab8/forge/src/main/java/com/github/darkpred/morehitboxes/mixin/EntityMixin.java#L68-L76)). The other two use custom client-to-server relays that open exploits. Alex's Mobs' `MessageHurtMultipart` accepts **a damage amount from the client** with no reach check ([AM MessageHurtMultipart.java](https://github.com/AlexModGuy/AlexsMobs/blob/09755dade2cfbdf14839e026d3af446f9d3ff843/src/main/java/com/github/alexthe666/alexsmobs/message/MessageHurtMultipart.java#L59-L90)). Alex's Caves' relay accepts an attack on any multipart parent within 16 blocks ([AC MultipartEntityMessage.java](https://github.com/AlexModGuy/AlexsCaves/blob/1.21.1/src/main/java/com/github/alexmodguy/alexscaves/server/message/MultipartEntityMessage.java#L47-L63)). Alex's Caves' older part classes also return false from `hurt`, so code reading suggests an arrow that hits only a sauropod's neck deals nothing ([AC SauropodPartEntity.java](https://github.com/AlexModGuy/AlexsCaves/blob/1.21.1/src/main/java/com/github/alexmodguy/alexscaves/server/entity/living/SauropodPartEntity.java#L79-L120)). Damage localisation itself is simple wherever it exists. The dragon gives the head full damage and reduces hits on all other parts. Ice and Fire multiplies (head ×1.5, wings ×0.5). MoreHitboxes passes the part to `partHurt` but defines no multiplier, and Fossils adds none.

Real-entity parts fail differently. Ice and Fire's "UUID of added entity already exists: EntityDragonPart" spam has been reported from 1.18 to 1.20.1. One report describes logs past 200 MB ([#5412](https://github.com/AlexModGuy/Ice_and_Fire/issues/5412)), and the reports continued after PR #5117. That PR also introduced a hydra loop typo (`HEADS + 1`) and flattened the sea-serpent chain by re-parenting segments every tick ([IaF EntityHydra.java](https://github.com/AlexModGuy/Ice_and_Fire/blob/0526aad94119b705a86207623481b087c4d052ca/src/main/java/com/github/alexthe666/iceandfire/entity/EntityHydra.java#L263-L269); [PR #5117](https://github.com/AlexModGuy/Ice_and_Fire/pull/5117)). A maintainer there wrote that the system should ideally become Forge's own. Performance is modest everywhere it was examined, with one scaling cost. Forge's `Level.getEntities` loops over **every part in the level for every AABB query**, so the cost grows with total loaded parts times queries, not with parts near the query ([F Level.java.patch](https://github.com/MinecraftForge/MinecraftForge/blob/0ec923d7307eb15bef70d6916329642b733a21ed/patches/minecraft/net/minecraft/world/level/Level.java.patch#L161-L200)). None of the projects published profiling data.

## Stuck herds are a navigation problem that parts cannot reach

The lead's symptom is herd members wedging in gaps and corridors, and it comes from the code that moves the animal. Every system studied leaves that code to the main box. Alex's Caves' sauropods carry long necks and tails as parts, yet they navigate with Citadel's `AdvancedPathNavigate` using `getBbWidth()` and `getBbHeight()` of a 5×8 main box ([AC AdvancedPathNavigateNoTeleport.java](https://github.com/AlexModGuy/AlexsCaves/blob/1.21.1/src/main/java/com/github/alexmodguy/alexscaves/server/entity/ai/AdvancedPathNavigateNoTeleport.java#L8-L22)). Necks and tails pass through walls. The research note on Alex's Caves reads this as a deliberate trade: no stuck AI, at the cost of visual clipping. Ice and Fire caps its dragon's main box at 0.78×1.2 scaled by at most 7, sizes path checks from that box, and breaks blocks around it ([IaF EntityDragonBase.java](https://github.com/AlexModGuy/Ice_and_Fire/blob/0526aad94119b705a86207623481b087c4d052ca/src/main/java/com/github/alexthe666/iceandfire/entity/EntityDragonBase.java#L2911-L2924)). MoreHitboxes sets `noPhysics = true` on every part and has no navigation code ([commit e772727d](https://github.com/DarkPred/MoreHitboxes/commit/e772727d)).

CustomHitboxLib is the counter-example, and it shows the risk. It runs a real compound-box sweep inside `Entity.collide` for parts flagged `collision` ([CHL EntityMixin.java](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/EntityMixin.java#L69-L168)). Its rotation mixins **cancel any yaw change** that would push a clear part into a block ([CHL EntityRotationMixin.java](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/src/main/java/dev/customhitboxlib/mixin/EntityRotationMixin.java#L29-L133)). Its node evaluator still plans with the main width, and its FAQ warns that large colliding parts confuse the pathfinder ([CHL FAQ](https://github.com/gawrmonster/CustomHitboxLib/blob/17585f5d8ca9180e98f10485b6d94363d1c4d196/wiki/FAQ.md)). Applied to a T. rex in a corridor, colliding animated parts would let the planner route the animal into a space where it then cannot turn. That is more stuck, not less. A rotation-synced hitbox system therefore helps the herd only if the pathfinder plans in the same shape. No studied mod does that. Its cost is an oriented-footprint A* node evaluator, a large new subsystem.

The fixes the studied mods actually use for big bodies all live in navigation. Vanilla aims each path node at block centre +0.5, so a wide mob steers toward a corner of its footprint. Mowzie's `PatchedPath` and Fossils' `PrehistoricPathFinder` both re-centre node targets at `floor(bbWidth + 1) × 0.5` ([MM MMPathFinder.java](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/ai/MMPathFinder.java#L19-L43); [FA PrehistoricPathFinder.java](https://github.com/TeamFossilsArcheology/FossilsArcheologyRevival/blob/b400cf2423dc245f3d18c8c60122835d4be5c6e2/common/src/main/java/com/github/teamfossilsarcheology/fossil/entity/ai/navigation/PrehistoricPathFinder.java#L130-L140)). Mowzie's also shortcuts along the path with a voxel sweep of the mob's own box ([MM MMPathNavigateGround.java](https://github.com/BobMowzie/MowziesMobs-Public/blob/64d15248c4421fdf8555165134b306e8cfc0a6c6/src/main/java/com/bobmowzie/mowziesmobs/server/ai/MMPathNavigateGround.java#L17-L140)). Citadel and Ice and Fire size the passability volume per node from the entity (`ICustomSizeNavigator`) and run path jobs on worker threads ([Citadel AdvancedPathNavigate.java](https://github.com/AlexModGuy/Citadel/blob/1.21/src/main/java/com/github/alexthe666/citadel/server/entity/pathfinding/raycoms/AdvancedPathNavigate.java#L103-L129)). Alex's Caves' sauropods walk forward only when the body is within 15° of the move direction ([AC SauropodBaseEntity.java](https://github.com/AlexModGuy/AlexsCaves/blob/1.21.1/src/main/java/com/github/alexmodguy/alexscaves/server/entity/living/SauropodBaseEntity.java#L539-L686)). Fossils refuses to grow a dinosaur's box when the bigger box would end up inside blocks ([FA Prehistoric.java](https://github.com/TeamFossilsArcheology/FossilsArcheologyRevival/blob/b400cf2423dc245f3d18c8c60122835d4be5c6e2/common/src/main/java/com/github/teamfossilsarcheology/fossil/entity/prehistoric/base/Prehistoric.java#L419-L454)). This research did not audit Project Nublar's current navigator. Which of these fixes it already has is the next thing to check.

The herd change the lead describes, shrinking the clearance box to the hitbox, matches what every peer does for terrain. Herd-mate spacing is a separate question, and here an axis-aligned box is the wrong shape. Minecraft boxes never rotate with yaw: the dragon's parts, MoreHitboxes' parts and CustomHitboxLib's parts are all axis-aligned boxes placed by their centre ([V EnderDragon.java](https://github.com/Blackjack200/minecraft_client_1_20_1/blob/c129e3e3e6ca89a731d4cfc35bb606c6bd2cae2c/net/minecraft/world/entity/boss/enderdragon/EnderDragon.java#L351-L353)). A square sized to a long body's length over-reserves sideways, and a square sized to its width under-reserves fore and aft. A capsule is a line segment from tail to snout along `yBodyRot`, with a radius of half the body width. The distance between two capsules is a cheap segment-to-segment calculation, and it gives a correct gap at any heading. This is a design recommendation, not a pattern found in the studied mods. It stays separate from hit detection and from terrain clearance.

## Project Nublar's head part never spawns and would sit at world origin

The current code is not a working base for any option. The research notes found that the common `PartEntity` matches Ice and Fire's `EntityMutlipartPart` field for field and method for method. ## Five options, one recommended sequence

| Option | Hit accuracy | Server truth during animation | Effect on stuck herds | Cost and risk |
|---|---|---|---|---|
| **A. Single box for movement + MoreHitboxes 1.20.1 bone-bound parts** | Client boxes follow GeckoLib bones. ID alignment, picking redirect, reach, culling bounds and rider anchors are built in. | Rest pose only | None | Required dependency on both sides. One JSON file and empty `<name>_hitbox` bones per species. Growth must flow through `getScale()`. Boxes are axis-aligned. One author. The 1.21.1 line is alpha. |
| **B. Fork MoreHitboxes to evaluate bones on the server** | Full | Yes | None | GeckoLib has no server-side pose, and the evaluator must be written. The author's TODO already flags the GeckoLib coupling. The fork drifts from upstream. |
| **C. Revive DumbLibrary-style server posing** | Bounding box of each rotated cube (fat on diagonals) | Yes, at the cadence chosen | None | Rebuild a server model loader and animator for GeckoLib. The predecessor churned on cost. Never use one real entity per cube. |
| **D. Procedural chain (dragon / Alex's Caves style) on Forge `PartEntity`, no dependency** | Head, neck and tail follow yaw, head yaw, pitch and per-animation targets | Yes, deterministic on both sides | None | Hand-tuned targets drift from the keyframes. You must write ID alignment, picking and reach yourself, which is where the homemade systems broke. |
| **E. Oriented capsule spacing for herd mates** | n/a | n/a | Fixes mate-to-mate jams, not terrain | Small, self-contained steering change |
| **F. Navigation fixes (node centring, box sweep, size-aware passability, turn-before-move)** | n/a | n/a | Directly targets terrain jams | Moderate. Several peer implementations exist to study. |

Option A is the best fit for hit detection. MoreHitboxes is small (about 2.8k lines), MIT-licensed and compiled against GeckoLib 4.7. Its 1.20.1 Forge build has been shipped to about 181k downloads through Fossils, and its public API is byte-identical between 1.20.1 and 1.21.1, which eases a later port ([Modrinth versions](https://api.modrinth.com/v2/project/BOVAW87Z/version); [MH20 forge build.gradle](https://github.com/DarkPred/MoreHitboxes/blob/012edbb4258120161c96103e51dac6374b78cab8/forge/build.gradle#L66-L74)). It also solves the vanilla plumbing that broke the homemade systems: part ID alignment, client section indexing and picking redirection. Two caveats apply. The `renderRecursively` descriptor was checked against GeckoLib 4.8.4 only, not against Project Nublar's 4.7.3 tag. Project Nublar's renderers must also reach the base `renderRecursively`. Integration needs a `getScale()` override that matches the growth-stage render scale, because static server offsets scale only through that method ([MH21 MultiPart.java](https://github.com/DarkPred/MoreHitboxes/blob/88899b3e1c4ed881b1ea65b35104453fc6df592a/common/src/main/java/com/github/darkpred/morehitboxes/api/MultiPart.java#L59-L60)).

The server/client gap in option A shrinks without a fork in two ways. The first is to author the hitbox bones so that they barely move. The second is an untested hybrid. `MultiPart.updatePosition()` honours any non-null override, so Project Nublar could write a procedural, option-D-style head and tail estimate as the override on the server only. The client would keep the real bone. Options B and C only pay off if gameplay needs exact posed hitboxes on the server, for example arrows against a lowered head or a server-side bite volume. No studied mod outside Project Nublar's own past has found that worth the cost.

The recommended sequence follows from that. First, delete the dead head-part code, both `DinosaurPart` classes and the client renderer's write to `DINOSAUR_HEAD_POS`, so that nothing is left to collide with a future system. Second, treat the herd symptom as options E and F, measured against the stuck cases the lead reported. Third, adopt option A for hit detection when player-facing hit accuracy becomes the priority, starting with the T. rex, Brachiosaurus and the other long-bodied species, where the main box misses most.

## Conclusion

The survey changes the question. "Hitbox problems" combines two different jobs: deciding **what a hit touches** and deciding **where a body can go**. The Minecraft ecosystem has settled on giving them separate owners. Parts answer the first job, and the main box plus a size-aware navigator answer the second. That split is not laziness. The one library that merged the two jobs ended up cancelling turns and confusing its own pathfinder. The original Project Nublar, the only codebase that kept server hitboxes in step with animation, still moved a T. rex as a player-sized box.

For Project Nublar, the decision that matters is not which multipart library to use. It is whether any gameplay rule needs the server to know the animated pose. If none does, client-animated parts over a server rest pose are the field standard, and the effort belongs in navigation and herd spacing, where the lead's actual symptom lives. If some rule does need it, the cheapest server truth is a procedural estimate fed into an existing hook, not a GeckoLib evaluator on the server.
