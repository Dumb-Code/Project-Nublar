# M0.P2 Port to Minecraft 26.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Implementers and per-task reviewers run on Opus or Sonnet, never Fable (lead's rule). This plan was written on Fable, and after Task 24 the coordinator opens the PR and runs the final whole-PR code review on Fable (lead, 2026-10-25).

**Goal:** One codebase that builds and runs on Minecraft 26.2 with Java 25 on Fabric and NeoForge: the machine chain, fences, six species and the Gallimimus herd work as they did on 1.20.1, Balm carries energy and the Processor's water, the vanilla payload system carries the three packets, Architectury carries registration only, and the platform service layer gives Fabric what it lacked (reload listeners, client entrypoint, repair handler, item models). One behaviour addition is lead-approved (2026-10-25): the Processor's water is a Balm fluid tank that pipes can fill. The scale-attribute code and the corrected base hitboxes ship behind the config switch `size.use_scale_attribute`, default off until M2, so the default game has today's render scale and today's boxes.

**Architecture:** The build moves to the MultiLoader Template `26.2` layout (`common`, `fabric`, `neoforge`, an included `build-logic` build, `nublar-gui` kept as a module compiled like `common`). Task 0 installs Minecraft Dev MCP as a cross-check list. Tasks 2 to 11 are the "compile window": `common` does not compile until Task 11, and each task in the window is verified by the javac error list, not by a run. From Task 12 both loaders build, then the smaller 26.x items land one by one, each verified by a build, a unit test or a GameTest. Two headed checkpoints stop for the lead: one as soon as a NeoForge client renders a dinosaur (Task 15), one at the end for the whole acceptance list (Task 24).

**Tech Stack:** Gradle 9.8.2, Java 25, Minecraft 26.2, NeoForge 26.2.0.93 with ModDevGradle 2.0.148, Fabric Loader 0.20.1 and Fabric API 0.161.0+26.2 with the non-remapping Loom plugin `net.fabricmc.fabric-loom` 1.19.3, Balm 26.2.0.9, Architectury API 21.1.12 (registration only), GeckoLib 5.5.6 (NeoForge) and 5.5.5 (Fabric), SmartBrainLib 2.0.3, Forge Config API Port 26.2.1, Team Reborn Energy 5.0.0 (nested, optional), JUnit Jupiter 5.10.2, the vanilla GameTest framework, Minecraft Dev MCP 1.3.0 as a cross-check tool outside the repository. See the version table below for dates and URLs.

**Spec:** `docs/plan/engineering-backlog.md` section "M0.P2: Port to Minecraft 26.2" (lines 391 to 505), "Global constraints" (41 to 112), "Cross-cutting risks" (113 to 160, risk 2 is ours), "How to use this plan" (161 to 245) and "Definition of done" (203 to 218); register rows D263 (vanilla payloads, Balm for storage, Forge Config API Port for config; its "No Architectury" now reads "Architectury for registration only", lead 2026-10-25), D34 and D70; `docs/codebase-analysis.md` 3.1, 3.4, 11.17 and 12.2 ("26.2 availability", "Platform first"); `docs/performance-baseline.md` (D284, D285); handoff `docs/superpowers/handoffs/2026-10-25-m0.p1-done-m0.p2-next-handoff.md`.

## Review Focus

1. **The colour layers must look the same.** GeckoLib 5 reads the tint of a pass from `DataTickets.RENDER_COLOR` in the render state, and a `GeoRenderLayer` has no colour parameter; the per-layer gene colour must reach each layer's pass and the second "white" pass must still follow it (the current look depends on both). Pinned by Task 10 step 4 (javap check of `GeoRenderer.submitRenderTasks` overloads) and the lead's headed check in Task 15 (each species, both genders, against the 1.20.1 screenshots).
2. **A dedicated server must not load a client class** (risk 2). `IncubatorMenu` reads `Minecraft.getInstance()`, `ClientRegistrationHolder` and the renderers are referenced from loader entry points, and GeckoLib 5's `createGeoRenderer` pattern puts a client class behind a lambda in a common item. Pinned by the GameTest server runs of Task 20 on both loaders (the server loads every registered class) and the `runServer` steps of Task 24.
3. **Herd GameTests must pass on Fabric** (handoff F1: 13 of 13 fail today because no reload listener runs). Pinned by Task 20 step 6 (Fabric GameTest run: every herd test passes except `stackedmembersseparate`, which is recorded as flaky).
4. **A client packet with a closed menu, a slot out of range or a value out of range must be refused.** Pinned by the unit tests of Task 6 (`PacketValidationTest`) on the pure validators and the server-thread checks in each handler.
5. **Fence poles must keep their shape and rotation on Fabric.** Today only a Forge mixin computes `cachedRotation` and `cachedShape` (in `requestModelDataUpdate`), so a Fabric pole has neither. Pinned by Task 13 (the computation moves to common `triggerModelUpdate` and `setLevel`) and the lead's Fabric headed check of fences in Task 24.
6. **The 1.20.1→1.20.4 stretch has no primer.** NeoForge split from Forge there and reworked registries (20.2) and capabilities (20.3), so a legacy-Forge pattern can survive into the port without a primer line that names it. The plan avoids most of it (Task 3 binds registries through `DeferredRegister` only, Balm owns capabilities, Task 12 rewrites the entry points), but the implementers of Tasks 3, 5 and 12 read the three NeoForge posts under "Porting sources" first. Pinned by Task 12's build and dedicated-server smoke run and Task 20's NeoForge GameTest run.
7. **GeckoLib 5 has no upgrade guide.** The API table comes from branch `26.2` and the changelogs, not from a migration note, so a 4.x pattern with no 5.x equivalent shows up only at compile time or in the look. Pinned by Task 9 step 0 (discovery list), Task 10 step 1 (`javap` on the renderer classes) and the lead's look check in Task 15.
8. **The scale switch must be invisible when off and exact when on.** Off (default): `Attributes.SCALE` stays 1.0, the box is today's `sized()` constant and the renderer applies today's manual render scale, so nothing a player sees or collides with changes. On: the attribute carries `scaleFactor`, GeckoLib applies it (no double scaling), the box is the corrected base box times the attribute (a baby's is 0.25× the adult's), parts follow, and every herd reader (`BodyFit`, `HerdSpacing`, `FollowFormation`, `GroupManager`, `JoinGroup`) reads `getBbWidth()`/`getBoundingBox()`, which vanilla scales by the attribute. Client and server must pick the same base box, so the switch value travels in one synced entity boolean. Pinned by `DinoScaleTest` (Task 10), the `scaleFollowsGrowthStage` GameTest (Task 20: switch forced on for the scaled assertions, then off for the "today's box" assertion), the herd GameTests (switch off) and the lead's F3+B checks with the switch on in Task 15 and the spot check in Task 24.

**Balm facts the spec asked to record** (read from branch `26.2` of https://github.com/TwelveIterationMods/Balm on 2026-10-25):

- The storage API is in `net.blay09.mods.balm.platform.energy` and `net.blay09.mods.balm.platform.fluid`, not under `balm.api`. `BalmEnergyStorageProvider` is an interface the block entity implements: `@Nullable EnergyStorage getEnergyStorage()` and `default EnergyStorage getEnergyStorage(Direction side)`. `EnergyStorage` has `int fill(int maxFill, boolean simulate)`, `int drain(int maxDrain, boolean simulate)`, `int getEnergy()`, `void setEnergy(int)`, `int getCapacity()`, `boolean canDrain()`, `boolean canFill()`; `DefaultEnergyStorage` is the stock implementation. Amounts are `int` (Botarium used `long`). `BalmFluidTankProvider` (`@Nullable FluidTank getFluidTank()`, `default getFluidTank(Direction)`) and `FluidTank` (slot based: `fill(slot, fluid, max, simulate)`, `drain(...)`, `getFluid(slot)`, `getAmount(slot)`, `setAmount`, `getCapacity(slot)`, `canFill(slot, fluid)`, `canDrain(slot, fluid)`, `isEmpty(slot)`, `getSlotCount()`; `DefaultFluidTank` is the stock implementation) carry the Processor's water (D-b). The Sequencer reads a tank item, not a fluid; no other block holds a fluid (`grep -rln "fluidLevel\|FluidStack" common/src/main` lists the Processor only).
- NeoForge: `NeoForgeBalm` registers fallback block-entity providers for `Capabilities.Energy.BLOCK` and `Capabilities.Fluid.BLOCK`; `NeoForgeEnergyStorage implements net.neoforged.neoforge.transfer.energy.EnergyHandler`, fluids go through `ResourceHandler<FluidResource>`. Nothing in Nublar registers a capability.
- Fabric: `FabricBalm` registers `FluidStorage.SIDED.registerFallback(...)` (Fabric Transfer API) always, and `Balm.initializeIfLoaded("team_reborn_energy", ...RebornEnergy)` registers `EnergyStorage.SIDED.registerFallback(...)` only when Team Reborn Energy is present. Balm declares TRE `compileOnly`; it does not bundle it.
