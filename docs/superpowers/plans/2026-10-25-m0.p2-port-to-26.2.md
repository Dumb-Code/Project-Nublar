# M0.P2 Port to Minecraft 26.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Implementers and per-task reviewers run on Opus or Sonnet, never Fable (lead's rule). This plan was written on Fable, and after Task 24 the coordinator opens the PR and runs the final whole-PR code review on Fable (lead, 2026-10-25).

**Goal:** One codebase that builds and runs on Minecraft 26.2 with Java 25 on Fabric and NeoForge, with no gameplay change: the machine chain, fences, six species and the Gallimimus herd work as they did on 1.20.1, Balm carries energy storage, the vanilla payload system carries the three packets, and the platform service layer gives Fabric what it lacked (reload listeners, client entrypoint, repair handler, item models).

**Architecture:** The build moves to the MultiLoader Template `26.2` layout (`common`, `fabric`, `neoforge`, an included `build-logic` build, `nublar-gui` kept as a module compiled like `common`). Tasks 2 to 11 are the "compile window": `common` does not compile until Task 11, and each task in the window is verified by the javac error list, not by a run. From Task 12 both loaders build, then the smaller 26.x items land one by one, each verified by a build, a unit test or a GameTest. Two headed checkpoints stop for the lead: one as soon as a NeoForge client renders a dinosaur (Task 15), one at the end for the whole acceptance list (Task 24).

**Tech Stack:** Gradle 9.8.2, Java 25, Minecraft 26.2, NeoForge 26.2.0.93 with ModDevGradle 2.0.148, Fabric Loader 0.20.1 and Fabric API 0.161.0+26.2 with the non-remapping Loom plugin `net.fabricmc.fabric-loom` 1.19.3, Balm 26.2.0.9, GeckoLib 5.5.6 (NeoForge) and 5.5.5 (Fabric), SmartBrainLib 2.0.3, Forge Config API Port 26.2.1, Team Reborn Energy 5.0.0, JUnit Jupiter 5.10.2, the vanilla GameTest framework. See the version table below for dates and URLs.

**Spec:** `docs/plan/engineering-backlog.md` section "M0.P2: Port to Minecraft 26.2" (lines 391 to 505), "Global constraints" (41 to 112), "Cross-cutting risks" (113 to 160, risk 2 is ours), "How to use this plan" (161 to 245) and "Definition of done" (203 to 218); register rows D263 (vanilla payloads, Balm for storage, Forge Config API Port for config), D34 and D70; `docs/codebase-analysis.md` 3.1, 3.4, 11.17 and 12.2 ("26.2 availability", "Platform first"); `docs/performance-baseline.md` (D284, D285); handoff `docs/superpowers/handoffs/2026-10-25-m0.p1-done-m0.p2-next-handoff.md`.

## Review Focus

1. **The colour layers must look the same.** GeckoLib 5 reads the tint of a pass from `DataTickets.RENDER_COLOR` in the render state, and a `GeoRenderLayer` has no colour parameter; the per-layer gene colour must reach each layer's pass and the second "white" pass must still follow it (the current look depends on both). Pinned by Task 10 step 4 (javap check of `GeoRenderer.submitRenderTasks` overloads) and the lead's headed check in Task 15 (each species, both genders, against the 1.20.1 screenshots).
2. **A dedicated server must not load a client class** (risk 2). `IncubatorMenu` reads `Minecraft.getInstance()`, `ClientRegistrationHolder` and the renderers are referenced from loader entry points, and GeckoLib 5's `createGeoRenderer` pattern puts a client class behind a lambda in a common item. Pinned by the GameTest server runs of Task 20 on both loaders (the server loads every registered class) and the `runServer` steps of Task 24.
3. **Herd GameTests must pass on Fabric** (handoff F1: 13 of 13 fail today because no reload listener runs). Pinned by Task 20 step 6 (Fabric GameTest run: every herd test passes except `stackedmembersseparate`, which is recorded as flaky).
4. **A client packet with a closed menu, a slot out of range or a value out of range must be refused.** Pinned by the unit tests of Task 6 (`PacketValidationTest`) on the pure validators and the server-thread checks in each handler.
5. **Fence poles must keep their shape and rotation on Fabric.** Today only a Forge mixin computes `cachedRotation` and `cachedShape` (in `requestModelDataUpdate`), so a Fabric pole has neither. Pinned by Task 13 (the computation moves to common `triggerModelUpdate` and `setLevel`) and the lead's Fabric headed check of fences in Task 24.

**Balm facts the spec asked to record** (read from branch `26.2` of https://github.com/TwelveIterationMods/Balm on 2026-10-25):

- The storage API is in `net.blay09.mods.balm.platform.energy` and `net.blay09.mods.balm.platform.fluid`, not under `balm.api`. `BalmEnergyStorageProvider` is an interface the block entity implements: `@Nullable EnergyStorage getEnergyStorage()` and `default EnergyStorage getEnergyStorage(Direction side)`. `EnergyStorage` has `int fill(int maxFill, boolean simulate)`, `int drain(int maxDrain, boolean simulate)`, `int getEnergy()`, `void setEnergy(int)`, `int getCapacity()`, `boolean canDrain()`, `boolean canFill()`; `DefaultEnergyStorage` is the stock implementation. Amounts are `int` (Botarium used `long`). `BalmFluidTankProvider` and `FluidTank` (slot based) exist; this package does not use them, because no block entity stores a fluid through Botarium today (the Processor's water is a plain field).
- NeoForge: `NeoForgeBalm` registers fallback block-entity providers for `Capabilities.Energy.BLOCK` and `Capabilities.Fluid.BLOCK`; `NeoForgeEnergyStorage implements net.neoforged.neoforge.transfer.energy.EnergyHandler`, fluids go through `ResourceHandler<FluidResource>`. Nothing in Nublar registers a capability.
- Fabric: `FabricBalm` registers `FluidStorage.SIDED.registerFallback(...)` (Fabric Transfer API) always, and `Balm.initializeIfLoaded("team_reborn_energy", ...RebornEnergy)` registers `EnergyStorage.SIDED.registerFallback(...)` only when Team Reborn Energy is present. Balm declares TRE `compileOnly`; it does not bundle it.

## Decisions for the lead (also go into the PR)

Each row names the task where the decision lands. The default applies until the lead answers; the lead changes any of them in the plan review.

- **D-a. Registration without Architectury.** D263 and the backlog tech stack say "No Architectury"; section 11.17 still says Architectury "stays for the other functions" (registration). The plan follows D263: the 16 `*Init` classes keep their shape but use one small common collector, `J/platform/registry/ModRegistry<T>` with `RegistryEntry<T>` (a `Supplier<T>` with `id()`), and each loader entry point binds the collected entries in order (NeoForge `DeferredRegister`, Fabric `Registry.register`). The custom `projectnublar:gene` registry is created by `DeferredRegister.makeRegistry` on NeoForge and `FabricRegistryBuilder` on Fabric. About 120 lines, no third-party registration library. Alternative: keep Architectury API 21.1.12 for registration only (one dependency, zero code). [Task 3]
- **D-b. Balm scope in this package: energy only.** No block entity stores a fluid through Botarium today (the Processor's water is a `double` field, the Sequencer reads a tank item). The seven storage block entities implement `BalmEnergyStorageProvider`; `BalmFluidTankProvider` is adopted by the first package that exposes a fluid (F1.3 Processor). Energy amounts become `int`. [Task 5]
- **D-c. How energy moves between Nublar blocks.** Botarium's `EnergyApi.distributeEnergyNearby` is gone. The generator pushes to the six neighbours through `BalmEnergyStorageProvider.getEnergyStorage(side)` of a neighbouring Nublar block entity (direct Java lookup, no capability query); poles share with connected poles through their Java references as today. Third-party cables reach Nublar storages through the loader capability that Balm exposes (NeoForge `EnergyHandler` fallback provider, Fabric Team Reborn Energy fallback), and pull from the generator because its storage answers `canDrain() == true`. Nublar does not push into foreign blocks in this package; a pushing generator is a B14 item. Task 5 verifies whether Balm's `Balm.getProviders()`/capability lookup exists on 26.2 and, if it does, uses it for the neighbour lookup so foreign blocks also receive pushes. [Task 5]
- **D-d. Team Reborn Energy nested in the Fabric jar.** Balm bridges Fabric energy only when `team_reborn_energy` is loaded. The Fabric jar nests `teamreborn:energy:5.0.0` (`include`), so Nublar energy is visible to Fabric tech mods without a user-installed library. Alternative: leave it optional and tell players to install it. [Task 1]
- **D-e. Death message moves into `Dinosaur.die`.** The Forge `LivingDeathEvent` handler only calls `DeathMessageHandler.onLivingDeath(dinosaur, source)`; `Dinosaur.die(DamageSource)` is already overridden in common. The call moves there and both loaders lose the hook. Same message, same moment. [Task 12]
- **D-f. Fossil and test-tube item models become vanilla `select` item definitions.** The Forge geometry loaders (`FossilModelLoader`, `TestTubeModelLoader`, `IDynamicBakedModel`, `StackSensitiveItemOverrides`, the Fabric `ItemOverridesMixin`) go. Each item gets one custom `SelectItemModelProperty<String>` in common (`projectnublar:fossil_texture` returns `<piece>_<quality>`, `projectnublar:test_tube_overlay` returns the species path or `none`), registered per loader, and datagen writes the `items/fossil.json` and `items/test_tube.json` definitions with one case per texture plus the per-case `item/generated` models. The syringe's `filled` item property becomes a `minecraft:condition` on `minecraft:has_component projectnublar:dna_data`. Alternative: a custom `ItemModel.Unbaked` type that builds quads from the stack at bake time (closer to today's code, more code). [Task 14]
- **D-g. Dinosaur render scale stays render-only.** The spec says "remove manual entity scaling, because GeckoLib 5 applies the scale attribute", but no Nublar code sets `Attributes.SCALE`; the manual scale (gene `SIZE` plus growth stage) is render-only and the hitbox does not grow. Driving `Attributes.SCALE` would grow hitboxes, which is a gameplay change (M2). The plan keeps the per-entity render scale in `scaleModelForRender(RenderPassInfo, float, float)` and removes nothing else; the `DINOSAUR_HEAD_POS` client-side write keeps its TODO. Alternative: set `Attributes.SCALE` now and accept the hitbox change. [Task 10]
- **D-h. Fence model data is dropped, the side effects move to common.** The two Forge fence mixins produce `ModelData` that no baked model reads (`ProjectNublarModelData` has no consumer); their live effects are side effects in `requestModelDataUpdate` (pole rotation and shape cache, block update, collidable cache reset) and `onLoad`. These move into the common `triggerModelUpdate()` overrides and a `setLevel` override, so Fabric gets them too (Review Focus 5). No `RenderDataBlockEntity`/`getModelData` is added; B15 adds static fence geometry later and chooses its data path then. [Task 13]
- **D-i. GeckoLib versions differ per loader.** 5.5.6 exists for NeoForge only; Fabric stops at 5.5.5. `common` compiles against the NeoForge 5.5.6 jar (as it compiles against the Forge jar today), Fabric runs 5.5.5, and `fabric.mod.json` requires `>=5.5.5`. Alternative: pin both to 5.5.5. [Task 1]
- **D-j. Render boxes on Fabric use vanilla `shouldRenderOffScreen`.** NeoForge gets exact boxes through `getRenderBoundingBox` on each renderer (declared in common without `@Override`, so Fabric compiles it as a plain method). Fabric has no box API in Fabric API 0.161.0+26.2; the multiblock renderers return `shouldRenderOffScreen() == true` as today, recorded per renderer in the class Javadoc. EntityCulling's interface is a compat item for later (section 12.2). [Task 17]
- **D-k. Recipe sync hook now, recipe types later.** The only Nublar recipe is a `CraftingRecipe` serializer; vanilla does not send crafting recipes to clients since 1.21.2, and NeoForge syncs by `RecipeType`, so syncing `CRAFTING` would send every crafting recipe in the game. The package adds the common `ClientRecipeStore`, the NeoForge `OnDatapackSyncEvent.sendRecipes` + `RecipesReceivedEvent` pair and the Fabric `RecipeSynchronization` + `ClientRecipeSynchronizedEvent` pair, with an empty list of Nublar recipe types (`RecipeInit.SYNCED_TYPES`). The acceptance line "the client recipe map holds the Nublar machine recipes" is checked when the first machine recipe type exists (the machine packages add their type to the list); the backlog line gets that note. [Task 18]
- **D-l. GameTests become vanilla data.** The two annotated holder classes (`ForgeGameTests`, `FabricGameTests`) are replaced by 16 `test_instance` JSON files in `R/data/projectnublar/test_instance/` (type `minecraft:function`, written by datagen) and one `ModRegistry<Consumer<GameTestHelper>>` on `BuiltInRegistries.TEST_FUNCTION` in common. One definition serves both loaders; the `package-info` rule changes to "add a function and a JSON entry". Alternative: keep per-loader holders (NeoForge `RegisterGameTestsEvent`, Fabric `@GameTest` entrypoint). [Task 20]
- **D-m. `nublar-gui` stays a module.** The spec says "keep nublar-gui as a source set"; the plan reads this as "keep it as its own module, compiled like `common`" (its layout today). Folding its 17 classes into `common` is the alternative. [Task 1]
- **D-n. Mixins go to zero.** After Tasks 13 and 14 no mixin remains, so the three mixin configs and the mixin build lines are removed. The template's empty configs are not kept. [Task 14]
- **D-o. Dropped Forge-only files.** `forge/.../entity/DinosaurPart.java` (a Forge `PartEntity` subclass nothing references; the live `DinosaurPart` is in common), `BakedModelHelper`, `IStackSensitive`, `StackSensitiveItemOverrides` (both loaders), `FossilModel.java` stub, `ProjectNublarModelData`, `CommonModEvents.onConfigLoaded` (a debug no-op). [Tasks 1, 13, 14]
- **D-p. No 1.20.1 world migration.** Vanilla's data fixers move old item NBT into `minecraft:custom_data`, but Task 16 reads the Nublar components, so a Nublar item carried over from a 1.20.1 world loses its genome, DNA or drive data (block entities keep their data, because the key names stay). Nothing has been released, so the plan writes no item fixer. Alternative: a one-time fixer that reads `custom_data` into the components. [Task 16]
